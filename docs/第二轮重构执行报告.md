### R2-4 遗留：`Launch` 拆分设计

为什么不继续做“纯提取”：`Launch` 的三条路径（title / pid / path）共享 12 个可变局部状态，任何两段提取都需要 10 个以上 `ref` 参数；继续拆会先变成“参数搬运”，阅读性反而下降。正确做法是先引入 `LaunchState`，再按阶段拆：

```csharp
private sealed class LaunchState
{
    public string? Path;
    public string? WindowTitle;
    public string? Arguments;
    public int WaitMs;
    public bool NewInstance;
    public bool EnsureDocument;
    public int? Pid;
    public DisplayInfo Display = null!;
    public IntPtr UserForeground;
    public WindowInfo? Window;
    public bool Started;
    public int ContentPid;
    public string ContentPath = string.Empty;
    public bool CloseOnRelease;
    public bool Dedicated;
    public bool HadRunningInstance;
    public bool AdoptedExisting;
    public string? LaunchWarning;
    public string? TempProfile;
    public string ExeName = string.Empty;
}
```

拆分顺序与目标行数：

| 阶段 | 方法 | 目标 |
|---|---|---|
| 1 | `ResolveTarget`：title / pid / path 三选一 | ≤30 |
| 2 | `ResolveByTitle` | ≤70 |
| 3 | `ResolveByPid` | ≤30 |
| 4 | `ResolveByPath`：校验 + 分派 | ≤45 |
| 5 | `StartNewInstance`：ProcessStartInfo / Job / 启动 | ≤60 |
| 6 | `WaitNewInstanceOrAdopt`：等待新窗口 + 单实例降级接管 | ≤120 |
| 7 | `LaunchReusing`：已有实例 / 直接启动 | ≤90 |
| 8 | `TrackWindow`：allowlist / 归属校验 / 注册 TrackedApp | ≤105 |
| 9 | `EnsureDocumentReady`：Word / PowerPoint / Excel | ≤110 |
| 10 | `BuildView`：警告、对话框、`LaunchOrPlaceView` | ≤60 |

约束：

- 所有中文异常消息、`details` 字段、错误码必须逐字节保持不变；建议用“整段搬运 + 只改标识符”的方式，不要重打消息文本。
- 每完成 1 个阶段跑一次构建 + 单测 + 契约；涉及接管/归位的阶段（5–8）必须在 VDD runner 上跑 GUI 13/14 与 stability 14/14。
- `Launch` 是本轮唯一未达标项；如果无法在 VDD 环境验证，建议保持现状，不为了指标做未验证的搬迁。

### 审计说明

`bench_protocol.py` 全绿，说明协议、工具 schema、错误码、取消、超时、租约、release 清理在真实 MCP 会话下没有回退。

- 手工按 GUI-01 的相同顺序执行（`launch_or_place_app` Notepad + args → `type_text` → `Ctrl+S`）通过，文件内容正确；
- 手工对 UiTarget 执行 `snapshot`（13 节点）、`find_element(Submit)`、`type_text`、`press_keys` 全部通过；

- GUI-01 的 `title=记事本`（缺少文件名）与手工结果不一致，符合 Windows 11 Notepad 单实例/会话恢复的已知环境问题。

结论：**protocol 可以作为本轮回归证据；GUI 结论待自托管 VDD runner 重跑**。合并前必须补跑 GUI 13/14、stability 14/14、UIA 3/3 与 `compare_baseline.py`，尤其是 `Ensure`/`SnapshotCore`/`ExecuteAsync` 三个改动。

## 5. 偏差、风险与回滚

偏差：

- R2-3 采用 **partial 文件**而非独立类；满足“单文件 ≤600”，但组件的宿主依赖仍集中（`IInputHost` 26 个成员），独立测试能力改善有限。独立类抽取留到 R2-4b/R3。
- R2-4 只完成 2 个方法；最大方法仍为 542，DoD 第 5 条未达成。
- R2-7 未开始；`ResetUia` 仍是唯一恢复入口。
- 覆盖率未设阈值；仅保留内置 `--collect:"Code Coverage"` 的用法说明。

风险：

- `LogSink` 使用全局 `Trace` listener，测试与多 profile 进程会各写各的 `trace-<profile>.log`；文件句柄保持到进程退出。
- 37 处 catch 统一提升为 `Exception` 变量并记录 Debug，可能增加日志量；错误码与对外输出未变。
- partial 拆分是纯搬运，但仍建议在具备 VDD 的环境补跑 GUI/protocol/stability/UIA。

回滚：

- 整体回滚：`git checkout r2-baseline`（tag 指向 R2-0 提交前的起点）。
- 分阶段回滚：每个阶段一个提交，可单独 revert；R2-2 的类型搬迁与命名空间修正必须整体回滚。
- 分支：`refactor/r2`，未推送远端。
