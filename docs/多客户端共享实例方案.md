# 多客户端共享实例方案（A）——问题核对与修复设计

> 状态：核心方案已实现；实现范围见下方“实现状态”。
> 基线：`HEAD 5ad6d99`（`v0.1.0-7`），`ModelContextProtocol 2.4.0`，`net10.0-windows`。
> 结论：采用 **A（daemon + 瘦代理 + 屏幕租约）**；默认 profile 共享一块虚拟屏，非默认 profile 继续作为“独立屏”隔离模式保留。工具契约保持 22 个，不新增 MCP 工具，只做向后兼容的字段和错误码扩展。

> **实现状态（2026-11-18，第五轮 / 0.2.0）**：已落地 P0/P1、共享实例（首个进程自动 spawn 独立 `--daemon`，失败回退进程内 daemon；后续进程 `StdioProxy`）、per-client refs/apps/epoch/帧/artifacts、`ScreenLease`（TTL/等待/抢占/keep_foreground 延长/`ForceRelease`）、路径基准（P-33，含相对路径）、日志分离（P-34，server/client 文件 + `client_id` 过滤）、共享 TraceLog、单行/总缓冲预算、共享限流、完整性校验、按 device 的虚拟屏绑定、`VSP_DAEMON_IDLE_MS` 空闲退出。`CREATE_BREAKAWAY_FROM_JOB` 优先，Job 不允许时回退并记录。非默认 profile 的完整 slot 分配仍是后续项。

## 0. 一页结论

1. Issue 描述的现象成立：`Global\VScreenPilot_Session_0` 被第一个进程持有，第二个进程在 `Program.cs:75-89` 直接 `return 3`，MCP 客户端只能看到 `failed`。
2. `--cli env` 也被拒绝，因为 CLI 解析在抢锁之后（`Program.cs:73-105`）；`--doctor` 正常，因为它在抢锁之前（`Program.cs:66-71`）。
3. Issue 提出的“用 `--profile` 隔离”在当前代码里 **不能直接作为解法**：多 profile 的虚拟屏归属是按“第一个已挂载的 Parsec 屏”猜的，首次启动、没有自己 state 的第二个 profile 会撞 `E_ORPHAN_DISPLAY`，甚至可能接管并摘掉另一个 profile 的屏。
4. A 的**连接共享**不依赖 OpenCode 是否为每个工作目录设置独立 cwd：所有客户端默认连同一个 daemon，天然零配置。但**路径语义**依赖客户端 cwd（P-33）：`save_path`/`target_path`/相对 exe 必须按调用方 cwd 解析，否则第二个目录会被 `E_INVALID_ARG` 拒绝或落到第一个目录。
5. A 必须同时引入 **屏幕租约**：同一时刻只允许一个客户端执行 GUI/视觉操作。没有租约的“共享一块屏”会让两个 agent 的截图、断言、坐标点击互相污染，结果不可复现。
6. A 不是“真并行”。它解决的是“多个客户端都能连上、轮流操作同一块屏”；如果要求两个 agent 同时驱动 GUI，只能走非默认 profile 的独立屏模式（B′），或独立 Windows 会话。
7. 旧 0.1.0 实例没有 mcp/ctl 管道、没有 registry；升级后新 proxy 无法 attach/查询，需要先关闭旧实例一次（P-35）。

### 1.1 需要修正的说法

- “已有可复用基础设施，只需把进程级独占下沉为资源级独占”：显示归属、会话 refs、应用归属、epoch、trace、调度器都不是资源级，当前全部是进程级。A 的真实工作量主要在这里，不在管道本身。
- “第二个进程连接已有实例并共享它”：MCP 没有 server 之间的共享机制，必须由 VScreenPilot 自己做代理和会话复用。
- “`--profile <name>` 可以隔离”：在当前代码里，两个 profile 同时挂屏时会有一个（通常是首次启动、没有自己 state 的那个）撞 `E_ORPHAN_DISPLAY`；必须先修 P-04～P-06，才能把它作为 A 之外的隔离模式。
- “A 不需要 cwd”：只对连接共享成立；`save_path`/`target_path`/相对 exe 仍需要调用方 cwd（P-33），不能把 daemon 的 `Environment.CurrentDirectory` 当成客户端目录。

## 3. 方案选择

| 方案 | 最终形态 | 并发 | 资源 | 主要风险 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **A. daemon + 瘦代理 + 屏幕租约** | 默认 profile：一块屏，多客户端连接，轮流操作 | 观察/输入按租约串行 | 1 个进程、1 块屏 | 共享屏的视觉污染；daemon 单点 | **采用** |
| B′. 每客户端一块屏 | N 个进程、N 块屏、互相隔离 | 可真正并行（输入仍需跨进程租约） | N 倍内存、N 次黑屏、VDD 槽位限制 | 桌面 clutter、配置 profile、资源 | 作为非默认 `--profile` 隔离模式保留，不作为默认 |
| C. 单屏分区 tiling | 一块大屏切成 N 个区域 | 真并行 | 1 块屏 | 窗口管理复杂、单实例应用无法并行 | 不采用 |

### 3.1 为什么选 A

1. **直接解决 issue 的核心痛点**：第二个客户端不再因为互斥体退出，而是成为代理；所有目录零配置连到同一个 daemon。
2. **连接共享不依赖 OpenCode 的 cwd**：A 默认所有客户端共享同一个 profile/daemon；即使 OpenCode 给所有子进程相同的 cwd，也不影响连接。B′ 依赖“每个目录 cwd 不同”或项目级 `VSP_PROFILE`，不确定性更高。但注意：A 的 `save_path`/`target_path`/相对 exe 仍需要调用方 cwd（P-33），这是路径语义，不是连接语义。
3. **资源和桌面扰动最小**：只多一块虚拟屏、一套 focus/cursor guard、一份 daemon 日志；避免 N 次挂屏/N 次黑屏/N 倍内存。
4. **符合产品定位**：VScreenPilot 是“一块确定的虚拟屏 + 用完即走”，不是多桌面并行桌面农场。多客户端最常见的情况是“两个都连着，通常只有一个在真正调试”。

### 3.2 A 必须接受的限制

- 一块屏是共享可变资源。即使有租约，用户自己拖到虚拟屏上的窗口、上一个客户端留下的窗口，仍可能出现在截图里。
- 只有一个键盘焦点。租约保证同一时刻只有一个客户端执行 GUI 操作，但不能让两个客户端同时拥有前台。
- 不支持“两个 agent 同时驱动 GUI”。这是 B′/独立 Windows 会话的领域。
- 不同客户端想要不同分辨率时，daemon 只能选一个全局几何；差异会被忽略并告警。

### 3.3 不采用的做法

- **去掉单实例互斥体**：多实例会争抢同一块虚拟屏、光标和前台，破坏“不干扰用户”的核心承诺。
- **让第二个进程阻塞等待锁**：MCP 客户端有 startup timeout（issue 里是 120s），阻塞只会把“快速失败”换成“更慢的失败”。
- **依赖客户端 pool 复用**：MCP pool 只在特定协议版本生效，当前协商版本不可依赖。
- **默认多挂虚拟屏**：每次多一次黑屏、多占资源；只作为非默认 profile 的显式隔离模式。

## 4. A 的目标架构

```text
OpenCode 目录 A ──stdio──> proxy A ──┐
                                     ├── \\.\pipe\VScreenPilot-mcp-<profile>-<sid> ──> daemon（每 profile 一个）
OpenCode 目录 B ──stdio──> proxy B ──┘                                                   ├─ 持互斥体
                                                                                          ├─ 挂 1 块虚拟屏
VScreenPilot.exe --cli env ──> \\.\pipe\VScreenPilot-ctl-<profile>-<sid> ────────────────┤─ 1 个 SessionManager
                                                                                          ├─ 1 个共享 WriteScheduler
                                                                                          ├─ N 个 ClientContext
                                                                                          └─ 1 个 ScreenLease
```

### 4.1 角色

- **daemon**：默认由首个 MCP 进程优先 spawn 独立 `--daemon` 进程承担（`CREATE_BREAKAWAY_FROM_JOB`，失败回退普通启动）；spawn 失败时回退到首个进程内嵌 daemon。daemon 持互斥体、VDD、JobObject、SessionManager、共享调度器、共享 TraceLog、屏幕租约，并用 `PipeHost` 接受代理。独立 daemon 不保留 stdio MCP 会话。
- **proxy**：MCP 客户端启动的进程。只做三件事：连接/启动 daemon、转发 stdio ↔ 命名管道字节、处理自己的父进程退出。不碰互斥体/显示/会话。转发使用原始 `Console.OpenStandardInput/Output()` 字节流，不用 `Console.In/Out`（避免 UTF-8/换行转码），每块写后 `FlushAsync`；stdout 只承载 MCP 数据，日志一律走 stderr/文件。
- **CLI**：`--cli` 先连 `ctl` 管道；没有 daemon 时才走本地只读/临时会话路径。

### 4.2 不变量

1. 每个 profile 至多一个 daemon；默认 profile 是共享模式。
2. daemon 拥有互斥体、虚拟屏、VDD、JobObject、SessionManager、共享调度器、TraceLog。
3. proxy 不持有互斥体，不创建 JobObject，不碰显示。
4. 同一时刻至多一个客户端持有屏幕租约；只有租约持有者能执行 GUI/视觉工具。
5. refs、apps、epoch、能力、artifact 子目录、日志过滤按客户端隔离。
6. 工具数量保持 22；只新增错误码和可选输出字段。
7. 单客户端行为与 0.1.0 一致；唯一差异是最后一个客户端断开后 daemon 有一个短暂空闲宽限期。

## 5. 详细设计

### 5.1 启动与选主

`Main` 的新顺序：

```text
--help / --version
--doctor           -> 读取实例 registry；有 ctl 管道则查询，否则本地诊断
--cli <op>         -> 先连 ctl；没有 ctl 时按 2b/2c/2d 的等待规则，被占用则报 E_INSTANCE_BUSY/E_VERSION_MISMATCH，未被占用才走本地
MCP 客户端：
  1) 尝试连接 mcp 管道；成功 -> StdioProxy（不构造 SessionManager）
  2) 连不上：尝试抢互斥体
     a) 抢到 -> 当前进程成为 daemon：创建 SessionManager/ControlServer/PipeHost，写 registry，运行自己的 stdio MCP
     b) 未抢到，registry 是当前版本 -> 重试代理（最多约 12s，覆盖 daemon 启动）
     c) 未抢到，无 registry/旧版本 -> 重试约 2.5s，仍失败则按 state.json 报 E_INSTANCE_BUSY
```

- **角色初始化顺序（阻塞级）**：`StateStore`/`JobObject`/`SessionManager` 的构造、预热和父进程监听只在**抢到互斥体的 daemon 分支**；代理分支只创建 profile/LogRing 与管道客户端，绝不构造 `SessionManager`、不创建 JobObject、不调用 `EnsureEnvironment`。`--cli` 也必须在构造 `SessionManager` 之前分流；本地 `env` 用独立的只读 helper（见 §5.2）。
- **当前选主**：首个 MCP 进程优先 spawn 独立 `--daemon`；独立进程抢 `Global\` 互斥体并成为 daemon。spawn/启动失败时回退到首个进程内嵌 daemon。输家不能写 registry、不能挂屏。
- **daemon 启动**：拿到互斥体 → 写 `InstanceRegistry`（`ready=false`，仅 pid/started/profile，作为“正在启动”标记）→ 创建 `SessionManager` → 创建 `ServerCore` → 启动 `mcp`/`ctl` 管道监听 → 更新 registry `ready=true` → 后台预热虚拟屏 → 进入空闲循环。`ready=false` 让 proxy 等待而不是误报旧实例；管道开始监听后才把 `ready` 置 true。
- **proxy 重试**：连接使用 200ms 退避，总预算 10s；期间如果 daemon 退出，读取其退出码/stderr 日志，给出明确错误。
- **旧 0.1.0 实例**：旧版本没有 mcp/ctl 管道、没有 registry，但仍持有 Global 互斥体并可能留下 `state.json`。proxy 走上面 2d：从 `state.json` 读 pid/startedAt/display；state 缺失时枚举同名 `VScreenPilot` 进程作为候选（标注“不确定”），输出 `E_INSTANCE_BUSY` 并提示“这是旧版本实例，关闭其 MCP 客户端或结束 pid 后重试”；不要 spawn 一个注定失败的 daemon。P0 的 registry 信息在旧实例上不可用，必须保留 state/进程候选回退。
- **失败信息**：`E_DAEMON_UNAVAILABLE`，stderr 同时输出人类可读文本和一行 JSON；保留 exit 3。P0 阶段（还没有 `--cli stop`/`--profile` 修复）只给可执行的最小解法：

```text
VScreenPilot: 实例已被占用 (E_INSTANCE_BUSY)
  profile: default
  owner: pid=8344, started=2026-11-18T17:10:46, cwd=<registry，旧实例可能未知>, elevated=<registry，旧实例可能未知>
  mutex: Global\VScreenPilot_Session_0
  解法:
    1) 关闭占用实例的 MCP 客户端（旧版本需要关闭其父进程）
    2) 任务管理器结束 pid=8344（需相同权限）
```

> P1/P2 完成后，才在提示里增加 `--cli stop`；`--profile` 在 §5.11 的显示分配修复完成前不要作为可用解法宣传（当前会撞 `E_ORPHAN_DISPLAY`）。

- **spawn 方式**：`ProcessStartInfo` 使用当前 exe、`UseShellExecute=false`、`CreateNoWindow=true`；**必须重定向并异步排空 daemon 的 stdout/stderr**，不能让 daemon 继承 proxy 的 stdio 句柄，否则任何控制台输出都会污染 MCP 流。daemon 的日志仍写自己的文件；不要给 daemon 传 `--parent-pid`。spawn 时不要传客户端的 `--allow-script`，并从 `StartInfo.Environment` 显式移除 `VSP_ALLOW_SCRIPT`/`VSP_APP_ALLOWLIST`/`VSP_ALLOW_UNSAFE_SCRIPT`（否则环境继承会变成全局策略）；这些只作为握手能力。`--profile` 要显式传，`VSP_DISPLAY_*` 可由第一个客户端继承并作为全局几何。
- **Job 风险**：如果客户端（如 OpenCode）把子进程放进 kill-on-close 的 Job，spawn 出来的 daemon 可能被一起杀。实现时用 `CREATE_BREAKAWAY_FROM_JOB`（需要 P/Invoke `CreateProcess`，不引入新依赖）或验证 OpenCode 是否使用 Job；失败时在文档中标注“daemon 生命周期跟随首个客户端所在 Job”。这一点必须实测，不能假设。

### 5.2 IPC 与握手

#### 管道命名

```text
\\.\pipe\VScreenPilot-mcp-<profile>-<sid8>
\\.\pipe\VScreenPilot-ctl-<profile>-<sid8>
```

- `<profile>` 已由 `Profile.Sanitize` 限制为 `[a-z0-9_-]`；实现时再加 32 字符上限（超出截断 + 短哈希），避免 `state.<profile>.json` 和管道名超过 Windows 路径/名称限制。
- `<sid8>` 是当前用户 SID 的 8 位哈希，避免不同用户抢同名管道。
- 服务端一律 `PipeOptions.Asynchronous | PipeOptions.CurrentUserOnly`；`.NET 10` 参考程序集已确认存在 `CurrentUserOnly`。

#### MCP 管道

- 每个连接一个 `NamedPipeServerStream`，`maxNumberOfServerInstances` 设为客户端上限（默认 16，`VSP_CLIENT_LIMIT` 可调）。
- 连接后先做 VSP/1 握手，再进入 MCP 字节转发：

```json
// proxy -> daemon，一行 JSON，前缀 VSP/1
{"vsp":1,"client":"opencode","proxy_pid":1234,"cwd":"C:\\work\\a",
 "roots":["C:\\work\\a"],"version":"0.1.0",
 "capabilities":{"allow_script":false,"app_allowlist":["C:\\Tools"]},
 "display":{"width":1280,"height":720,"refresh":60}}

// daemon -> proxy
{"vsp":1,"ok":true,"client_id":"c1","protocol":1,"daemon_version":"0.1.0",
 "display":{"device":"\\\\.\\DISPLAY5","width":1280,"height":720,"x":3072,"y":0},
 "geometry_ignored":false}
```

- 握手行上限 64 KB，超时 5s；失败返回 `{ok:false,code,hint}` 并关闭。
- 握手内容只作策略/展示；不要信任客户端的 `elevated` 字段。服务端用 `GetNamedPipeClientProcessId` 取 proxy pid，再校验 token 完整性级别（见 5.7/P-32）。
- 版本不一致返回 `E_VERSION_MISMATCH`；如果 daemon 当前没有活跃客户端，可以自动 drain（停止接受新连接，空闲退出），proxy 等它退出后重新 spawn；有活跃客户端时直接报错，提示 `--cli stop`。
- 握手成功后，daemon 为该连接创建一个独立的 MCP Host，使用 `WithStreamServerTransport(pipeRead, pipeWrite)`（SDK 2.4.0 XML 已确认该扩展存在）。每个连接一个 `McpServer` 实例，持有自己的 `ClientContext`。连接有独立的 CTS：proxy EOF/管道断开时取消该 Host、终止在途调用并释放 `ClientContext`；共享的 `WriteScheduler`/`TraceLog` 不能随连接 Dispose。
- **待验证**：`NamedPipeServerStream` 同时作为读写流传入是否被 SDK 接受。如果不接受，用两个只读/只写包装流共享同一个管道，或在 daemon 内用一对匿名管道桥接。
- **待验证**：多个 `Host` 在同一进程内运行时，默认 `ConsoleLifetime` 会重复注册 Ctrl+C。为每个连接 Host 注册 no-op `IHostLifetime`，由 `DaemonHost` 统一处理退出。
- **消息上限/背压**：每个 MCP 连接套 limiting stream：单行上限 `VSP_MAX_MESSAGE_MB`（默认 16MB）、跨连接总缓冲 `VSP_TOTAL_BUFFER_MB`（默认 64MB），超限关闭连接并记录 `client_id`；`capture_screen`/`snapshot` 的大图应流式转发。超限使用连接级 `E_MESSAGE_TOO_LARGE`（不进入工具错误目录）。
- **`cwd`/`roots` 的用途**：握手里的 `cwd`/`roots` 只用于 P-33 的路径基准和诊断，不参与“是否共享”的判定。proxy 发送自身 cwd；如果配置了 `VSP_CLIENT_CWD`，用它覆盖 `cwd` 并作为 `roots` 的首项。MCP roots 是可选增强：当前 SDK 2.4.0 未发现 roots API，暂不作为默认依赖。daemon 只接受绝对路径，并做规范化/链接解析。

#### 控制管道

- 一连接一请求，请求/响应都是一行 JSON；请求上限 1 MB，响应上限 4 MB，超时 30s。
- 操作：

| op | 作用 | 是否只读 |
| --- | --- | --- |
| `env` | 返回 daemon 的 `GetEnvironment(false)`，附带全部 apps 与 owner | 是 |
| `snapshot` | 管理员视图：全部 apps 的语义树，`max_nodes` 可配 | 是 |
| `screen` | 截整屏，写到 `artifacts/<profile>/cli/`，返回路径/尺寸/耗时 | 是 |
| `status` | daemon pid、版本、display、clients、screen_lease、管道名、内存/句柄 | 是 |
| `stop` | 无活跃客户端时退出；有客户端时需 `{"force":true}` | 否 |

- 控制管道不暴露输入、不暴露 `run_script`、不接受任意 PowerShell；除 `stop` 外的 op 只调用 `SessionManager` 的只读方法，`stop` 只触发退出流程。控制连接不计入 MCP 活跃客户端，不阻止 daemon 空闲退出；`stop` 直接触发退出流程。
- 如果 ctl 在 2s 内无响应，`--cli stop --force` 从 registry 读 pid + 启动时间，二次校验后 `TerminateProcess`；这是最后手段，会带走该 daemon 的所有客户端和 apps。
- `--cli env` 在 daemon 存在时不再构造 `SessionManager`，因此不会清 state、不会挂屏。没有 daemon 时用 `CliEnvironment.ReadOnly()`（VddDevice/DisplayTopology/StateStore）读取；只有 `snapshot/screen` 的本地路径才需要互斥体和临时会话。
- ctl 连接失败时：registry `ready=false` -> 等 10s 等管道；无 registry/旧实例 -> 先查互斥体，被占用则 2s 后报 `E_INSTANCE_BUSY`（从 state.json 取 pid/startedAt）；`ready=true` 但 ctl 仍失败 -> 报 `E_DAEMON_UNAVAILABLE`。以上都不要回退本地构造 `SessionManager`。
- 如果互斥体被旧 0.1.0 实例持有且没有 ctl/registry，`--cli` 直接报 `E_INSTANCE_BUSY`（附带 state.json 的 pid/startedAt）；不要构造本地会话（本地也会撞锁）。
- `--cli snapshot/screen` 在没有 daemon 时仍按旧逻辑：抢互斥体、构造临时会话、执行后释放；文档要说明这可能会挂屏。

### 5.3 客户端上下文

```csharp
internal sealed class ClientContext
{
    public required string Id { get; init; }          // c1, c2...
    public required string Name { get; init; }        // opencode / claude / cli
    public required string Cwd { get; init; }
    public IReadOnlyList<string> Roots { get; init; } = Array.Empty<string>(); // proxy cwd/VSP_CLIENT_CWD；MCP roots 可选
    public int ProxyPid { get; init; }
    public string Version { get; init; }
    public ClientCapabilities Capabilities { get; init; } // allow_script/allow_unsafe_script/app_allowlist
    public RefStore Refs { get; } = new();
    public long Epoch;                                 // 每客户端
    public string ArtifactDirectory { get; init; }
    public DateTimeOffset ConnectedAt { get; init; }
    public long LastActivityTicks;                     // 租约空闲判定
    public bool ReadOnly { get; init; }                // ctl 合成客户端
}
```

- `SessionManager` 增加 `AsyncLocal<ClientContext?> _currentClient`，与现有 `_cancellation`、`ToolProgress` 的模式一致：`McpServer` 在每次工具调用开始时 `using var scope = session.UseClient(_client)`，`Task.Run` 会继承执行上下文。
- **路径基准（P-33）**：所有工具的用户路径都按 `ClientContext.Cwd`/`Roots` 解析，不用 daemon 的 `Environment.CurrentDirectory`；`Roots` 为空时退化为 `Cwd`。至少覆盖 `ValidatePngPath(save_path/target_path)` 的允许根、`launch_or_place_app` 的相对 `path`/`WorkingDirectory`、`EnsureAppAllowed` 的相对 allowlist、`FindRunningProcess` 的相对路径。允许根 = 当前客户端 `Cwd`/`Roots` + temp；跨客户端目录默认不允许写（同用户可通过 temp 中转）。`--cli` 的合成客户端用 CLI 自己的 cwd。
- 控制管道的合成客户端 `ReadOnly=true`，用于 `env/snapshot/screen`；它不参与租约，不修改 apps/refs。
- `RefStore` 迁移 `_elements`、`_elementKeys`、`_elementSeq`、`_snapshotSeq`、`_snapshotGeneration`、`_snapshotId`；互斥锁从 `SessionManager` 的全局 `_refGate` 改为每客户端一把，`_snapshotGate` 仍可全局串行化 UIA 建树。
- 帧缓存/基线（`_frames`、`_nextFrameId`）迁移到客户端上下文或按 client id 索引；`release_environment` 只清当前客户端的帧；`_uiaBlockedPids` 也按客户端隔离。全局保留一个总字节预算（默认 64MB），避免 N 个客户端线性放大内存。
- `McpServer` 不再自己 new `WriteScheduler`/`TraceLog`/限流器，而是接收共享的 `ServerCore`；`McpServer` 只保留自己的 `ClientContext` 和请求级状态。`RunAsync` 的 `finally` 只结束连接级资源，共享 core 由 `DaemonHost` 在 daemon 退出时统一 Dispose。

### 5.4 屏幕租约

#### 状态

```text
owner_client_id, owner_name, owner_cwd
acquired_at, last_gui_activity_at
active_gui_calls          // 长 wait_for/release 期间不因 TTL 被抢
idle_ttl_ms               // 默认 60000，VSP_SCREEN_LEASE_IDLE_MS 可调
```

#### 获取/释放

- 首次执行 GUI/视觉工具时自动获取；不新增 MCP 工具，不改变 22 工具契约。
- `release_environment` 释放调用者的租约；客户端断开、崩溃、工具超时且 handler 真正结束后释放。
- 获取顺序统一为：**屏幕租约 → WriteScheduler → SessionManager 会话读/写锁**；释放反序。租约必须在 `ExecuteToolAsync` 进入 `sessionRead`/`sessionWrite` 之前获取，不能等进入 handler 后再拿，否则两个客户端会先同时持有会话读锁、再在 handler 里争租约。`release_environment` 是特殊路径：若还有 live apps，先按同样顺序拿租约；只清 refs 时可跳过。
- 租约需求由 `RequiresScreenLease(tool, args)` 判定（例如 `snapshot.include_screenshot`、`wait_for.type`），在调度器之前求值，保证错误在进入 UI handler 前返回。
- 获取失败默认立刻返回 `E_SCREEN_LEASED`；可选 `VSP_SCREEN_LEASE_WAIT_MS`（默认 0）在返回前等待一小段时间。
- 租约持有者空闲超过 TTL 且没有活跃 GUI 调用时，下一个请求可以接管，并记录 `screen_lease_stolen` 日志；被抢的客户端下次调用会重新竞争，不会静默继续操作。
- 超时/取消时，租约和 WriteScheduler 都要在 handlerTask 真正结束后释放（`ContinueWith`），不能在返回 `E_TIMEOUT` 的同时释放，否则新客户端可能在旧 handler 仍在注入时拿到租约。`active_gui_calls` 就是为这个窗口准备的。
- `keep_foreground=true` 时延长租约并暂停 FocusGuard；租约释放/过期时恢复 FocusGuard。
- FocusGuard 只把租约持有者的 apps 当作“本会话应用”；没有租约时，不要因为另一个客户端的 app 占前台而恢复用户窗口。CursorGuard 仍按整块虚拟屏工作。
- `release_environment` 的 `keep_display` 只在最后一个客户端时生效；有其他客户端时返回 `display_kept_reason="other_clients"`，不摘屏。
- 租约只防并发注入，不防遮挡：最后放到前台的窗口会盖住其他客户端的窗口；重新获取租约后，`click_ref`/`type_text` 会重新切前台。这是共享一块屏的固有行为，文档要说明。

#### 工具矩阵

| 工具 | 需要租约 | 理由 |
| --- | --- | --- |
| `get_environment`、`get_log` | 否 | 只读元数据；`get_log` 默认只看自己的条目 |
| `find_element`、`get_ui_tree`、`get_element_text` | 否 | 语义读；只作用于本客户端 apps |
| `snapshot`（不含截图） | 否 | 语义树；只作用于本客户端 apps |
| `snapshot`（`include_screenshot=true`） | 是 | 视觉结果会被共享屏污染 |

### 5.5 应用/窗口归属

- `TrackedApp` 增加 `OwnerClientId`；`StartedProcess`/`Owned`/`DedicatedProcess` 语义不变。
- **操作路径**的 `_apps` 扫描按 OwnerClientId 过滤：
  - `GetEnvironment` 的 `apps`、`foreground`、`focused_element`；
  - `Snapshot` 的 `windows[]`、`foreground`（`SessionManager.Snapshot.cs:302/327`）；
  - `FindLiveTrackedApp`、`LastLiveTrackedApp`、`TryRelocateApp`（`SessionManager.cs:281/321/327/338`）；
  - `RequireTrackedApp`、`RequirePointInTrackedApp`（`SessionManager.Input.cs:1538-1599`）；
  - `wait_for{type:"text"}` 的候选窗口、`read_screen_text{scope:"tracked"}` 的 PID 集合（`SessionManager.Verify.cs:541/1039`）；
  - `element_ref` 的 PID 归属/默认动作/输入（`SessionManager.Elements.cs:331/884/1204`）；
  - `LaunchOrPlaceApp` 的窗口复用（`SessionManager.Apps.cs:300/301`）；
  - `ReleaseEnvironment` 的 apps 循环（`SessionManager.cs:1116`）。
- **daemon 维护路径保持全局**：`PruneDeadApps` 清理死亡条目（`SessionManager.cs:292-306`）；`SaveState` 持久化**所有客户端**的 apps（`SessionManager.cs:1709`），否则崩溃恢复会丢掉其他客户端的窗口位置。`SaveState` 可额外写 owner 供诊断，但恢复时不要依赖 owner。
- **FocusGuard 策略**：`IsTrackedWindow`（`SessionManager.Focus.cs:74`）不能把另一个客户端的 app 当作“本会话应用”。租约持有者的 apps 才参与护栏；没有租约时，护栏只负责把用户窗口归位，不因另一个客户端的 app 占前台而恢复用户窗口。
- `LaunchOrPlaceApp`：
  - 只复用自己拥有的 hwnd/pid；
  - 目标窗口属于其他客户端时返回 `E_APP_OWNED`，带 owner 信息；
  - 支持专用实例的应用（Edge 临时 profile）可以为第二个客户端起新实例；
  - 单实例应用（Word/Excel 等）无法为两个客户端提供独立窗口时，返回 `E_APP_OWNED`，提示先释放或改用 profile 隔离模式。
- 坐标点击：`RequirePointInTrackedApp` 只认自己的 apps；如果落点是别人的 app，返回 `E_FOREIGN_WINDOW`，带 `owner_client_id`。
- 强杀保护：`HasOtherWindows(pid, hwnd)` 之外，再检查同一 pid 下是否有其他客户端的 hwnd；有则只关窗口，不强杀进程树。
- `ReleaseEnvironment`：
  - 只关闭/归位自己的 apps；
  - 只清自己的 refs/epoch；
  - 不摘屏（除非是最后一个客户端且 `keep_display=false`）；
  - `on_dirty=abort` 仍保留自己的 apps 跟踪，便于后续 release。
- 客户端断开：
  - 立即释放租约，但如果该客户端还有 `active_gui_calls` 未结束（例如卡在 UIA），租约要等 handler 真正结束再转给下一个客户端，避免重叠注入；
  - 如果没有其他客户端持有租约：宽限期（默认 5s）后按 `force` 关闭/归位该客户端的 apps（与 0.1.0 进程退出一致；客户端已断开，无法询问保存），保留虚拟屏；
  - 如果其他客户端正在操作（持有租约）：先清理该客户端的 refs/registry，窗口留到租约释放后再按 `force` 处理，避免关闭窗口打断对方；
  - daemon 最终退出时再对剩余 apps 做一次全量清理。

### 5.6 生命周期

#### 正常

1. 第一个 MCP 进程优先 spawn 独立 `--daemon`（breakaway）；独立 daemon 持锁、挂屏、启动 `PipeHost`/`ctl`，后续 MCP 进程通过 `StdioProxy` 接入。spawn 失败时回退到首个进程内嵌 daemon。
2. proxy 握手、转发 MCP；客户端完成 `initialize/tools/list`。
3. 客户端执行工具；daemon 按客户端上下文路由。
4. 客户端断开：proxy 退出，管道 EOF；daemon 立即释放该客户端租约/refs，apps 按 5.5 的“租约是否被其他客户端持有”规则处理。
5. 最后一个客户端断开：启动空闲计时（默认 5s，`VSP_DAEMON_IDLE_MS` 可调）。
6. 空闲到期：停止接受连接，取消在途调用，`ReleaseEnvironment(keepDisplay:false, onDirty:"force", allowDataLoss:true)`，摘屏，清 state，释放互斥体，退出。

#### 崩溃/异常

- **proxy 崩溃**：管道断开，daemon 按断开处理；其他客户端不受影响。
- **daemon 崩溃**：所有 proxy 读到管道 EOF，退出 3 并在 stderr 说明；客户端重连时重新 spawn；新 daemon 通过 state/registry 接管孤儿屏。若 `state.Pid` 仍是存活的 daemon（命令行/registry 校验，不能只看进程名，因为 proxy 也叫 VScreenPilot），跳过接管，避免抢正在退出的 daemon 的屏（对应 P-08）。
- **客户端崩溃**：proxy 的 stdin EOF/父进程退出 → proxy 退出；daemon 释放该客户端。
- **release 卡住**：工具 90s 超时后返回 `E_TIMEOUT`，handler 可能仍在跑；租约交给 handler 结束再释放（类似 `WriteScheduler.ReleaseWhen`）。`--cli stop --force` 是最后手段。

#### 升级

- proxy 握手带版本；daemon 返回版本。
- 不一致且无活跃客户端：daemon drain 退出，proxy 重新 spawn 新版本。
- 不一致且有活跃客户端：返回 `E_VERSION_MISMATCH`，提示关闭其他会话或 `--cli stop`。
- 旧 0.1.0 没有 mcp/ctl 管道、没有 registry；新 proxy 按 §5.1 2c 从 `state.json` 报 `E_INSTANCE_BUSY`，用户关闭旧实例一次后新 daemon 才会启动。安装器不应直接杀旧实例（会丢未保存内容）。
- 不建议安装器直接杀 daemon：会中断正在调试的会话；宁可显式提示。

### 5.7 能力与安全

- **每连接能力**：`allow_script`、`allow_unsafe_script`、`app_allowlist` 由 proxy 在握手时上报；daemon 按连接存储。它们是同用户策略，不是安全边界；同完整性进程本来就能执行等价操作。
- **daemon 全局上限**：自动 spawn 的 daemon 不继承客户端的 `--allow-script`/`VSP_APP_ALLOWLIST`，也**不把“没传”解释成全局 false**；默认是无全局 script 上限，每个客户端握手里的 `allow_script` 独立生效。只有手动 `--daemon --allow-script` 才作为全局 allow 上限（AND）；如需全局禁用，使用可选的 `--daemon --deny-script`。`app_allowlist` 两者都有时取交集，只有一方时用该方。
- **控制管道**：`CurrentUserOnly`；除 `stop` 外的只读 op；不接受脚本/输入；请求大小上限。
- **默认 profile 只用 `Global\` 互斥体**：权限不足时返回 `E_INSTANCE_BUSY`（带“可能由另一个用户/会话持有”的提示），不再静默回退 `Local\`；否则会出现两个 daemon、两块屏。
- **完整性级别**：daemon 记录自身 elevated/integrity；连接时用 Win32 `GetNamedPipeClientProcessId` 获取 proxy pid，再读进程 token 的 integrity level。**两个方向不一致都拒绝**（低→高防止借 elevated daemon 绕过 UAC；高→低避免客户端误以为能操作 elevated 窗口），除非显式 `--allow-integrity-mismatch`；`mcp` 和 `ctl` 都校验，错误码 `E_INTEGRITY_MISMATCH`。握手里的 `elevated` 字段只能用于展示，不能作为判定依据。
- **管道名抢注**：SID 后缀降低跨用户冲突；同用户恶意进程本来就能注入输入，不构成额外安全边界。
- **隐私**：
  - `get_environment.apps` 默认只返回自己的 apps；`other_clients` 只给数量，不给标题；
  - `session.clients[]` 默认只给 `id/name/connected_at/holds_lease`；cwd 只在 `E_SCREEN_LEASED`、`E_APP_OWNED` 和 `--cli status` 中给出；
  - `get_log` 默认只返回自己的条目；
  - artifact/resource 只暴露自己的目录；
  - `focused_element` 二次校验 pid/hwnd 属于当前客户端。
- **不新增沙箱承诺**：README 继续声明 shared desktop，不是安全沙箱。
- **跨 profile 输入**：A 默认不需要 `VSP_FOCUS_LEASE`（进程内租约已串行化输入）；非默认 profile 的独立屏模式仍建议开启 `VSP_FOCUS_LEASE=1`，防止两个 daemon 同时 `SendInput`。

### 5.8 可观测性与产物

- **InstanceRegistry**：`%LOCALAPPDATA%\VScreenPilot\instances\<profile>.json`，daemon 持锁后先写 `ready=false`，开始监听管道后改 `ready=true`；daemon 启动失败/退出时删除，残留文件由 pid + 启动时间校验识别。
  ```json
  {"pid":8344,"started_at":"...","cwd":"...","version":"0.1.0","elevated":false,"mutex":"Global\\VScreenPilot_Session_0",
   "mcp_pipe":"...","ctl_pipe":"...","display_device":"\\\\.\\DISPLAY5","profile":"default","ready":true}
  ```
  退出时删除；读取时用 pid + 进程启动时间校验，避免 PID 复用。`cwd` 是 daemon 启动时的工作目录（通常等于第一个客户端 cwd）；每个客户端的 cwd 在 `clients[]`/`status` 中单独给出。虚拟屏首次挂载/重建/摘除后更新 `display_device` 字段；`ready=false` 表示 daemon 正在启动或 draining，proxy 应等待而不是报错。旧 0.1.0 没有 registry，P0 回退读 `state.json`（pid/startedAt/display），只能给出部分信息（P-35）。
- **日志**：`LogRing` 条目增加 `client_id`；proxy 和 daemon 必须写不同文件（proxy 用 `client-<pid>.log` 或只写 stderr，daemon 用 `server...log`），否则同一 profile 的 `server<profile>-<date>.log` 会被两边混写（P-34）。`get_log` 默认按当前客户端过滤，可选 `include_other_clients=true`（新增可选输入字段，不改变工具数量）。
- **Trace**：daemon 共享一个 `TraceLog`，文件名加 daemon pid + 启动时间；每条记录带 `client_id`、`client_name`；不再每个连接一个文件。
- **长生命周期清理**：daemon 不再只在启动时 `SweepOldArtifacts`/`CleanupOldSessions`；每 24h 或每 N 次连接触发一次 artifact/trace 清理与轮转，避免长时间运行后磁盘增长（P-30）。
- **Metrics**：保留全局；`get_environment.metrics` 可增加 `by_client` 视图（可选）。
- **Artifacts**：`artifacts/<profile>/<client_id>/<yyyyMMdd-HHmmss>/`；`--cli` 用 `artifacts/<profile>/cli/`；资源 URI 按当前客户端目录解析，禁止 `..`。
- **Doctor**：`--doctor` 读取 registry；如果 ctl 管道存在，查询 `status`（500ms 超时），输出 daemon、clients（含 cwd/roots/holds_lease）、lease、display、pipe；不占用 MCP 连接。没有 registry 时回退 `state.json`，并标注“旧实例/信息不全”。

### 5.11 非默认 profile：显示归属与分配

> 默认 profile 只有一块屏，不需要本节；但 `--profile` 的隔离模式（B′）和 issue 建议的 `--profile` 解法依赖本节。P-04～P-06 只给了方向，下面是落地算法。

- **身份**：`state.<profile>.json` 记录 `DisplayDevice` + `DisplayIndex` + 启动时间；`InstanceRegistry` 记录 `display_device`/`profile`/`pid`/`started_at`/`ready`。不再用 `FindParsecDisplay()` 的第一个匹配来认领。
- **启动顺序**：
  1. 读本 profile 的 state/registry；有 `DisplayDevice` 就按 device 查找。
  2. device 不存在但存在本 profile 的孤儿 state：校验 index/device 后接管；否则丢弃 state。
  3. 存在其他 **live + ready** profile 的屏：不要接管，走 `AddDisplay` 申请新屏。
  4. 存在无主屏（没有 live registry）：只有本 profile 上次 state 匹配才接管；否则 `E_ORPHAN_DISPLAY` 或显式 `--adopt-orphan`。
- **分配**：短时 `Local\VScreenPilot_DisplayAlloc` 互斥体包住“AddDisplay + 设坐标 + 写 registry/state”，避免两个 profile 同时启动抢同一个 slot；`DisplayOffset` 基于 registry 已占 slot，不基于 `FindParsecDisplay()`。
- **摘除**：`RemoveDisplay` 前校验 `_displayIndex` 对应的 device 仍等于本 profile 的 `DisplayDevice`；不匹配只清状态、不按 index 摘除。摘除后 `WaitForDisplayGone(device)`，不是 `WaitForNoParsecDisplay()`。
- **环境**：`get_environment.virtual_display` 只报本 profile 的 device；`owned` 以 device 匹配为准；`mutexHost` 用 `Profile.MutexName(ProfileName)`。
- **恢复**：`RecoverFromPreviousCrash` 只在旧 pid 不是存活 daemon 时恢复；存活时跳过全部（P-08）。
- **验收**：两个 profile 同时各一块屏；release B 不摘 A；B 崩溃不影响 A；A/B 的 `display`/`x/y` 不同且不重叠；旧 profile 的孤儿屏不会被另一个 profile 接管。

## 7. 测试计划

### 7.1 单元测试（不需要桌面）

- Profile/管道名：默认名、非默认名、非法字符、SID 后缀、长度。
- InstanceRegistry：写入/读取/删除；pid 复用；启动时间校验；stale 文件。
- 握手：合法/非法 JSON、版本不匹配、超长、缺字段、能力解析。
- 租约状态机：获取/续期/释放/空闲过期/断开/长 `wait_for` 保护/被抢后重新竞争。
- RefStore：两个客户端的 `e1` 互不影响；跨客户端 ref 返回未知/过期；快照代际独立；帧 id/基线独立。
- 帧缓存：A 的 `release_environment` 不清 B 的基线；全局字节预算生效；`assert_region{baseline:"last"}` 在 A release 后仍可用。
- 路径（P-33）：两个 `ClientContext` 不同 `Cwd`/`Roots` 时，`ValidatePngPath` 允许根只含调用方 cwd/roots + temp；相对 exe/allowlist 按调用方 cwd 解析；跨客户端目录被拒。

- 日志：proxy 与 daemon 的 `LogRing` 文件名不同；daemon 的 `get_log(source=file)` 不混入 proxy 条目。
- 旧实例：没有 registry 时从 state.json 读出 pid/startedAt；proxy 探测到“互斥体被占用 + 无管道/registry”返回 `E_INSTANCE_BUSY`，不 spawn。
- 消息上限：单行/单消息超过上限关闭连接并记录 `E_MESSAGE_TOO_LARGE`；正常大截图不被误杀。
- 完整性：低→高、高→低两个方向都拒绝；同完整性通过。
- App 归属：`RequirePointInTrackedApp` 拒绝别人的窗口；`LaunchOrPlaceApp` 返回 `E_APP_OWNED`；同一 pid 多窗口归属。
- Epoch：A 的 release 不丢弃 B 的在途结果；最后一个客户端 release 才全局递增。
- 能力：客户端 A 无 `allow_script` 得到 `E_DISABLED`；B 有则可用；allowlist 交集。
- 错误目录：新增错误码的 `code/hint/docs/retryable`。
- 输出 schema：新增字段不破坏旧字段；工具数量仍为 22。

### 7.2 无 GUI 协议集成（普通桌面可跑）

- 用唯一 `VSP_PROFILE=test-<pid>`、`VSP_NO_WARMUP=1` 启动 daemon，避免碰到用户实例；测试结束用 `--cli stop --force` 或显式 kill daemon，并清理 `instances/<profile>.json`、`state.<profile>.json` 与测试 artifact 目录。
- 两个 MCP 客户端同时 `tools/list`：都返回 22；`get_environment.virtual_display` 相同（无屏时都为 `enabled:false`）；`clients` 有 2 条。
- `--cli env` 在 daemon 运行时成功；state 文件内容和 mtime 不变。
- `--cli status` 显示 clients/lease/pipe；`--cli stop` 在无客户端时退出。
- 版本不匹配：模拟旧 daemon，proxy 返回 `E_VERSION_MISMATCH`；无活跃客户端时自动 drain 后重连。
- 旧 0.1.0：占住互斥体 + 写一个无 registry 的 `state.json`，不建管道；新 proxy 必须在 2s 内报 `E_INSTANCE_BUSY`（带 pid/startedAt），不能空等 spawn；`--cli` 同样明确报错。
- 完整性：管理员启动 daemon，普通权限 proxy 连接返回 `E_INTEGRITY_MISMATCH`；反向（低 daemon + 高 proxy）也拒绝；同权限连接成功（VM 中测）。
- 客户端上限：第 17 个连接被拒绝，已有客户端不受影响。
- 消息上限：发送超过 `VSP_MAX_MESSAGE_MB` 的 JSON 行，连接被关闭并记录 `E_MESSAGE_TOO_LARGE`；正常截图仍通过。
- 日志分离：proxy 与 daemon 的日志文件不同；daemon `get_log(source=file)` 不含 proxy 行。
- 两不同 cwd：客户端 A/B 分别在自己的目录下调用 `capture_screen{save_path}` / `match_visual{target_path}`（有屏的 VM）；两边都成功且文件落在各自目录；跨目录写入被拒。
- daemon 崩溃：kill daemon，proxy 得到明确错误；重启后新 proxy 能重新拉起。
- 首个 proxy 退出：A/B 两个客户端，kill A 的 proxy/父进程（含模拟 kill-on-close Job），B 仍能调用；失败则 A 的阶段 3 gate 不通过，需 breakaway 或改写生命周期。
- 50 次 attach/detach：内存/句柄无持续增长；daemon 空闲后退出。

### 7.3 GUI 集成（隔离 VM/独立账户；禁止真实桌面输入）

- 两个客户端各启动一个独立 UiTarget 实例（或两个独立进程的 Notepad）：refs 独立；A 的 `click_ref` 只作用于 A 的树；A 对 B 的坐标点击返回 `E_FOREIGN_WINDOW`。
- 租约：A 执行 `type_text`，B 同时 `capture_screen` 得到 `E_SCREEN_LEASED`；A `release_environment` 后 B 可获取。
- 截图：A 的截图会看到 B 的窗口（共享屏的已知行为）；`get_environment` 明确显示 `screen_lease` 和 `other_clients`。
- 遮挡/恢复：A 先操作并 release；B 获取租约并把自己的窗口放前台；A 再获取租约后，`click_ref`/`type_text` 仍能切回 A 的窗口并成功操作。
- release 归属：A release 只关闭 A 的 UiTarget；B 的窗口/进程保留；最后一个客户端 `keep_display=false` 才摘屏；A release 后 B 的 `assert_region{baseline:"last"}` 仍可用。
- 断开清理：kill A 的 proxy，B 不受影响；A 的窗口在宽限期后被强制关闭/归位，不残留孤儿。
- 前台/隐私：B 的窗口在前台时，A 的 `get_environment.foreground.tracked=false`，不返回 B 的标题；`focused_element` 不返回 B 的元素；`snapshot.windows[]/foreground` 也不含 B 的标题；`wait_for{type:"text"}`/`read_screen_text{scope:"tracked"}` 不扫 B 的窗口。
- 路径：A/B 在不同 cwd，各自 `capture_screen{save_path}`、`match_visual{target_path}` 成功且落在各自目录；`launch_or_place_app` 的相对路径按各自 cwd；跨目录被拒。
- SaveState/恢复：A/B 的 apps 都在 `state.<profile>.json`；daemon 崩溃重启后窗口位置恢复，且不会把 B 的窗口算到 A 头上。
- FocusGuard：A 持租约操作时，B 的 app 被切到前台，A 的 FocusGuard 不误把 B 当“本会话应用”；租约释放后用户窗口能正常归位。
- 能力：A 的配置没有 `--allow-script`，`run_script` 返回 `E_DISABLED`；B 有则可用；`VSP_ALLOW_UNSAFE_SCRIPT` 也按连接生效。顺序无关：先启动无 flag 的 A、再启动有 flag 的 B，B 仍可用；反过来 A 仍不可用。
- profile 模式：默认 daemon + 非默认 profile daemon 各一块屏；B 的 release 不摘 A 的屏；B 崩溃不影响 A；`WaitForDisplayGone` 不误等。
- soak：2 客户端 × 100 次 snapshot/click/release；无句柄/内存泄漏；租约不永久卡死。

### 7.4 性能目标

以 README 的历史数据为基线（启动握手 116ms、挂屏 1952ms、截图 30ms、release 2098ms、EOF 229ms、空闲 36.6MB）：

- 已有 daemon 时 proxy attach p95 < 200ms。
- 冷启动（spawn + 挂屏）p95 < 4s。
- 管道转发开销 p95 < 5ms/次（不含工具本身）。
- 单客户端工具延迟相对旧版增加 < 5%。
- 每增加一个客户端，常驻内存增加 < 20MB（Host/DI/连接缓冲）。
- 空闲 CPU < 1%（daemon 总计）。
- 50 次 attach/detach 后句柄数回到基线 ±10。
- 两客户端同时 snapshot 的 p95 与单客户端相比，串行化后的退化在可接受范围（记录数据，不设硬指标）。
