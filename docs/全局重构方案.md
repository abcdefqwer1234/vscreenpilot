# VScreenPilot 全局重构方案

> 文档状态：定稿（待执行）
> 适用代码基线：`3ddb85b`（0.2.2）
> 重构原则：**质量优先，不计执行时间成本；外特性零变更。**
> 本文中的“外特性”指第 5 章冻结清单中的全部内容；类型名、文件名、命名空间、目录结构不属于外特性，可以自由调整。

## 1. 结论摘要

现状的五个问题全部成立，且已经产生实质性影响：

1. **架构不明晰**：`VScreenPilot.Server` 一个程序集 25,462 行 / 61 个文件，`Core` 仅 1,097 行 / 3 个文件；18 个文件反向依赖 MCP 命名空间；两个组合根重复 wiring；5 个静态回调和多组静态实例替代依赖注入。
2. **文件组织混乱**：`SessionManager` 被拆成 14 个 partial、10,602 行（占 Server 41.6%），按工具名而非职责切分；10 个文件各自声明 `DllImport`。
3. **缺少层次**：`McpServer` 2,207 行同时承担工具目录、schema、参数绑定、限流、加锁、租约、超时、artifact、trace；`SessionManager` 有 21 个 `public JsonObject` 方法，领域层直接产出已序列化的响应。
4. **死代码与重复实现**：已确认 20+ 个无调用成员；3 份 `JsonElement` 参数读取器、3 份 driver/display JSON 组装、3 份 `IsElevated`、3 份 `IsTruthy`、6 份 region 解析、5 张工具名策略清单。
5. **风格不统一**：254 个 `catch`（约 46 个完全空捕获）、57 处 `Thread.Sleep`、17 处 `.Result/.Wait`、315 处 `new JsonObject`、82 处 `GetValue<T>()`；分析器处于 `latest-minimum` 且 `EnforceCodeStyleInBuild=false`。

影响是真实的：全局 `_gate` 在挂屏/自愈时可持有约 10 秒，期间阻塞其他客户端；工具策略分散导致漏改即破坏串行性；三份环境 JSON 已经出现字段不一致；热路径每次调用重复序列化 4–6 次。

**重构目标**：在保证外特性逐字节/逐字段不变的前提下，把系统重构为 4 个程序集、按职责划分的组件、单一工具描述符模型、无静态全局状态的显式依赖图。

### 1.1 已定决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 工程拆分 | 拆为 `Abstractions`/`Platform`/`Automation`/`Server` 四个程序集 | 只有编译期边界能长期阻止反向依赖；时间成本不计 |
| 重构范围 | 一次性执行 P0–P8 全部阶段 | 质量优先；分阶段只为控制风险，不为缩减范围 |
| UIA 线程模型 | 纳入 P7，改为单线程宿主 | 消除 `[ThreadStatic]`、退休队列泄漏与公寓风险；独立阶段便于回滚 |
| 内部专用重载 | 删除 `ReleaseEnvironment` 的 `forceRemoveDisplay/forceAllClients`，拆为 `Release()`/`ReleaseForShutdown()` | 外部行为不变；消除参数污染 |
| 测试依赖 | 不新增第三方包；架构断言用程序集引用反射 + 源文件扫描实现 | 满足 AGENTS.md 对新增依赖的约束；能力足够 |
| schema 来源 | 从当前 `tools/list` 一次性固化为 JSON 文件，之后手工维护；不做运行时/编译时代码生成 | schema 已被审计，生成器会引入契约漂移风险 |
| 兼容层 | `ControlServer` 的 legacy 顶层字段保留 | 属于外部契约，不能删除 |

## 3. 问题核实与证据

### 3.1 软件架构不明晰

**判定：成立。**

| 证据 | 位置 |
|---|---|
| 领域层反向依赖传输层 | `Session/*.cs`、`Uia/UiaService.cs`、`Input/InputInjector.cs`、`Infrastructure/InputLease.cs`、`Session/ScreenLease.cs` 共 18 个文件 `using VScreenPilot.Mcp;`，只为使用 `ToolException`/`ToolResponse` |
| 静态服务定位器 | `Program.cs:74-78` 注入 `LogRing.ClientIdProvider`、`LeaseHolderProvider`、`ScreenLeaseProvider`、`ScreenLease.LogSink`、`ScreenLease.ClientCwdProvider`；`SessionManager.Client.cs:36-38` 再暴露 `LeaseHolderProvider`/`ScreenLeaseProvider` |
| 两个组合根 | `Program.Main` 与 `DaemonHost.RunStandalone`/`Run` 各自创建 `SessionManager`/`Registry`/`ControlServer`/`PipeHost`，预热与空闲退出逻辑重复 |
| 无编译期边界 | 仅 2 个工程；`Session` → `Mcp` → `Session` 命名空间循环，编译器无法阻止 |

初始化顺序成为隐式契约：如果某个静态 provider 未注入，`GetEnvironment` 会静默缺少 `screen_lease` 字段，而不是启动失败。

### 3.2 文件组织混乱

**判定：成立。**

- `SessionManager` 的 14 个 partial 文件：`SessionManager.cs`、`.Input`、`.Elements`、`.Apps`、`.Verify`、`.Visual`、`.Snapshot`、`.Ocr`、`.Capture`、`.Script`、`.Client`、`.Artifacts`、`.Focus`、`.Observe`。切分依据是“工具/功能块”，不是“状态所有权”；14 个文件合计约 370 个成员声明，仅 `SessionManager.cs` 就有 142 个。
- 平台原语分散：`Program.cs`、`Infrastructure/IntegrityCheck.cs`、`Infrastructure/JobObject.cs`、`Input/ClipboardText.cs`、`Interop/NativeMethods.cs`、`Ipc/DaemonSpawner.cs`、`Perception/ScreenCapture.cs`、`Uia/MsaaService.cs`、`Uia/UiaService.cs`、`Core/Interop/Win32.cs`；`GetSystemMetrics` 在两个工程各声明一次。
- 目录职责重叠：`Session/ScreenLease.cs`（并发基础设施）、`Session/CursorGuard.cs`（平台线程）、`Apps/WindowManager.cs`（Win32 窗口原语）、`Perception/` 与 `Uia/` 边界模糊。

### 3.3 代码没有层次、可读性差

**判定：成立。**

`McpServer` 一个类承担 10 项职责：

1. 22 个工具的元数据与内联 JSON schema；
2. schema 生成辅助（`Out`/`Type`）；
3. `JsonElement` 参数读取（`OptionalString/Int/Bool/Double/NullableInt/NullableBool/RequiredInt`）；
4. MCP `list_tools`/`list_resources`/`read_resource`/`call_tool` 四个 handler；
5. 令牌桶限流；
6. 写操作调度；
7. 屏幕租约；
8. 超时/取消/epoch 校验；
9. artifact 落盘与 preview 生成；
10. trace/metrics 与 JSON→SDK 内容块转换。

`SessionManager` 同时是：显示控制器、窗口跟踪器、应用启动器/释放器、UIA 门面、ref 注册表、快照构建器、输入路由器、OCR/视觉/验证门面、脚本执行器、客户端注册表、artifact 管理器、焦点护栏、诊断序列化器。

数据流以 `JsonElement`/`JsonObject` 为全程 DTO：

```
SDK JsonElement
  → ToArguments（JsonNode → string → parse → clone）
  → ArgumentValidator
  → McpServer 参数读取
  → SessionManager 位置参数（8~11 个）
  → 业务逻辑
  → new JsonObject 手工拼装
  → ToolResponse.Text（DeepClone + 序列化）
  → SetRequestId（再次序列化）
  → ToResult（再次 parse 成 JsonDocument）
```

### 3.4 死代码、冗余代码、绕弯设计

**判定：成立。**

#### 3.4.1 已确认的死代码（全仓无调用点）

核实范围必须覆盖 `src/`、`tools/`、`tests/`——`VddProbe` 会用到部分 `DisplayTopology` 诊断方法，只扫 `src/` 会误判。

- `NativeMethods`：`ClientToScreen`、`GetDpiForWindow`、`GetGUIThreadInfo`、`GetWindowTextW`、`GetWindowTextLengthW`（以及仅供 `GetGUIThreadInfo` 使用的 `GUITHREADINFO`）
- `LogRing`：`LastErrorEntry`、`TailAsJson`（连带 `_lastError` 字段）
- `ToolResponse.AddText`
- `ScreenCapture.Diagnostics`（连带 `_captureCount`/`_slowCount`/`_lastMs` 统计）
- `SessionManager.ReadElementValue`
- `SessionManager.Ocr.IsAscii`
- `WindowManager.FindByTitle`、`WindowManager.IsForegroundOfProcess`
- `ControlClient.TryStop`
- `Win32.GetLastError`

曾误判为死代码、实际仍在使用（不要删）：

- `DisplayTopology.WaitForParsecAdapter/WaitForParsecDisplay/ExtendDesktopNoOptimization/SetModeAndPositionDeviceOnly`：`tools/VddProbe/Program.cs` 在用。
- `ArgumentValidator.ToText`：`enum` 校验的错误消息在用。
- `KeyMap.Canonical`：`Normalize` 在用。

> `ScreenLease.ReleaseHolder` 仅被单测使用，属于“测试专用别名”，与 `ReleaseHolderIfIdle` 合并。

#### 3.4.2 重复实现

| 逻辑 | 份数 | 位置 |
|---|---|---|
| `JsonElement`/`JsonObject` 参数读取 | 3 | `McpServer`、`SessionManager.Input`、`ControlServer`（另有 `ControlClient` 响应解析） |
| driver/display/virtual_screen JSON | 3 | `SessionManager.GetEnvironment`、`CliEnvironment.ReadOnly`、`Program.Doctor` |
| CLI 截图落盘 | 2 | `Program.RunCli`、`ControlServer.Capture` |
| `IsElevated` | 3 | `Program`、`SessionManager`、`InstanceRegistry` |
| `IsTruthy` | 3 | `Program`、`StdioProxy`、`SessionManager.Script` |
| `region` 解析 | 6 | `McpServer`(3)、`SessionManager.Verify`(2)、`SessionManager.Visual`(1) |
| 预览缩放 `0.25` | 6 | `McpServer`、`SessionManager.Snapshot` |
| 内联阈值 `128KB` | 2 | `McpServer.Snapshot`、`McpServer.CaptureScreen` |

已完成的不一致：`Program.Doctor` 的 `virtual_display` 缺 `scale_percent`，`CliEnvironment` 缺 `owned/self_healed/adopted_orphan`。三份实现已经开始漂移。

#### 3.4.3 绕弯设计

- `ReleaseEnvironment(keepDisplay, onDirty, allowDataLoss, forceRemoveDisplay, forceAllClients)`：后两个参数只服务 `Dispose`，污染公开语义。
- `LeaseHolderProvider`/`ScreenLeaseProvider`/`ClientIdProvider` 等静态回调：把“避免反向依赖”从编译期搬到了运行期。
- `ControlServer.Snapshot` 中 `foreach (legacy)` 把旧单 app 顶层字段复制到新结构，兼容层长期停留在主路径。
- `UiaService._lastFindTruncated` 使用 `[ThreadStatic]` 作为返回值通道；跨线程即读错，且不报错。
- `ResetUia` 的退休队列 `while (_retiredUia.Count > 4) _retiredUia.RemoveAt(0)` 直接丢弃实例，既不 `Dispose` 也不在会话结束时释放，造成 COM/RCW 泄漏。

#### 3.4.4 工具策略分散在 5 处

| 位置 | 内容 |
|---|---|
| `McpServer.MutatingTools` | 11 个写工具名 |
| `McpServer.RequiresScreenLease` | 按工具名与参数判断租约 |
| `McpServer.ExecuteToolAsync` | `tool.Name is not ("wait_for" or "get_log" or "release_environment")` 决定读锁 |
| `McpServer.ExecuteToolAsync.finally` | `release_environment` 的租约特判 |
| `McpServer.BuildTools` | `readOnly`/`destructive` 标注 |

新增工具若漏改任意一处，不会编译失败，只会偶发并发错误。

### 3.5 风格不统一、不够现代

**判定：成立。**

- 254 个 `catch`，约 46 个空捕获；故障现场缺失。
- 57 处 `Thread.Sleep`、17 处 `.Result/.Wait(`、5 处 `GetAwaiter().GetResult()`、14 处 `Task.Run`：同步阻塞与异步混用。
- `Directory.Build.props`：`AnalysisLevel=latest-minimum`、`EnforceCodeStyleInBuild=false`、`NoWarn CA1822;CA1859`。
- 29 处 `Environment.GetEnvironmentVariable` 分散读取；`SessionManager.VirtualWidth/VirtualHeight/VirtualRefresh` 为 `static readonly`，在类型初始化时读环境，进程内不可变、单测不可覆盖。
- 配置值、超时、阈值以魔法数字散落（`300`、`128*1024`、`0.25`、`5000`、`3000` 等）。

需要保留的优点（重构中不得丢失）：`ErrorCatalog` 的单一错误事实来源、`WriteScheduler`/`ScreenLease`/epoch 的并发语义、大量记录踩坑原因的注释（N1/N4/N5/S5 等）。

## 4. 影响评估

### 4.1 稳定性

| 风险 | 机制 | 后果 |
|---|---|---|
| 全局 `_gate` 长持有 | `EnsureEnvironment` 在锁内做 ADD 重试（最长约 5s）、等待新屏（3s）、激活（2s+3s） | 其他客户端的 `get_environment`/`snapshot`/`release` 排队；触发 `E_TIMEOUT` |
| 锁层次复杂 | `_gate`、`_sessionLock`、`_refGate`、`_frameLock`、`_artifactGate`、`_snapshotGate`、`_focusActionGate`、`_retiredUia`、`ScreenLease._gate`、`RateGate`、输入/显示互斥体 | 锁顺序靠注释约束，新增代码易死锁 |
| 工具策略分散 | 5 处清单 | 漏改导致写操作绕过调度器，或与另一客户端抢屏 |
| 延迟清理竞态 | `ScheduleClientCleanup` 轮询 30 分钟；`PipeHost.Dispose` 不等待连接；`SessionManager.Dispose` 3s 预算 + 最小清理 | “清理中 + 新连接”窗口内状态不可预期 |
| COM 泄漏 | `ResetUia` 丢弃退休实例 | 长会话句柄/内存增长 |
| `[ThreadStatic]` 截断标志 | 隐藏返回通道 | 结果字段静默错误 |

### 4.2 性能

1. **热路径重复序列化**：一次 `snapshot` 调用发生 4–6 次完整序列化/解析（`ToArguments`、`SummarizeArguments`、`ToolResponse.Text`、`SetRequestId`、`ToResult`）。返回体越大越明显。
2. **快照二次遍历**：`RedactJsonStrings` 全树遍历，`SnapshotFormat` 再遍历一次；`privacy_redactions` 在同一方法写 3 次。
3. **`get_environment` 无缓存**：每次枚举显示拓扑、IOCTL、UIA 焦点；限流上限 100/s，轮询时持续开销。
4. **preview 逐像素交换**：`TryCreatePreview` 全图 RGBA→BGRA 再编码，可复用现有 BGRA 通路。

### 4.3 维护难度

| 变更 | 需要改的地方 |
|---|---|
| 改一个输出字段 | `SessionManager` 某 partial、`Out("field:type")`、`docs`/README、audit schema 校验；三份 driver/display JSON 任一份漏改都会不一致 |
| 加一个工具 | `BuildTools`、handler、`MutatingTools`、`RequiresScreenLease`、`ExecuteToolAsync` 名单、`ErrorCatalog`、`docs/errors.md`、`Expected` 测试数组、`bench_contract`，共 8–9 处 |
| 加一个单测 | `SessionManager` 构造函数执行文件 I/O、删目录、崩溃恢复、启动维护线程；`VirtualWidth` 静态只读；设备接口无抽象，难以构造测试替身 |
| 回归验证 | CI 只跑 84 个纯函数单测；真实路径依赖发布前手动 Python audit |

## 5. 外特性冻结清单（重构不变量）

以下内容**必须逐字段保持不变**。任何一项变化都视为重构失败。

### 5.1 MCP 协议面

- 22 个工具名与大小写：`assert_region`、`capture_screen`、`click`、`click_ref`、`click_text`、`find_element`、`gesture`、`get_element_text`、`get_environment`、`get_log`、`get_ui_tree`、`invoke_element`、`launch_or_place_app`、`match_visual`、`press_keys`、`read_screen_text`、`release_environment`、`run_script`、`set_element_value`、`snapshot`、`type_text`、`wait_for`。
- 每个工具的 `title`、`description`、`inputSchema`、`outputSchema`、`annotations`（`readOnlyHint`/`destructiveHint`/`openWorldHint`/`idempotentHint`）。
- `serverInfo.name=vscreenpilot`、`serverInfo.version`、`instructions` 文本、`capabilities`。
- 内容块：`text`、`structuredContent`、`image`、`resource_link` 的结构与字段。
- `text` 与 `structuredContent` 语义一致；`request_id` 同时出现在两者中。
- 进度通知 `notifications/progress` 的 `progressToken/progress/total/message`。
- 错误包：`code`、`message`、`details`、`retryable`、`hint`、`stage`、`docs`（含小写锚点）、`request_id`。
- 未知工具、限流、参数校验、超时、epoch 取消的稳定错误码。
- 截图落盘规则：`save_path` 只允许 `.png`；相对路径按**调用方 cwd** 解析；允许根为调用方 cwd、客户端 roots、系统临时目录；解析符号链接/junction 后再做根校验；越界返回 `E_INVALID_ARG` 且 `details.allowed_roots` 完整。
- `type_text`：>100000 字符拒绝；`chunk_chars` 默认 32、范围 1–256；≥200 字符或含代理对走剪贴板；剪贴板含非文本格式时，显式 `channel=clipboard` 返回 `E_CLIPBOARD_UNSAFE`，`auto` 则退回按键注入。
- `run_script`：默认关闭（`E_DISABLED`）、`timeout_ms` 1000–120000、输出 64KB 截断、危险命令黑名单（`VSP_ALLOW_UNSAFE_SCRIPT=1` 绕过）。
- `match_visual`：`max_results` 1–100、`threshold` 0.3–1.0、`scales` 0.5–2.0 且最多 5 个、`max_area_ratio` 0.01–1.0。
- `read_screen_text`：`max_lines` 1–200；OCR 语言选择与回退顺序不变。
- artifact 资源：`vsp://artifacts/` 前缀、按修改时间倒序、50 条/页、排除 `.preview.png`、`?preview=1`/`?full=1`、>512KB 自动 preview、非法名拒绝规则。
- 内联阈值 128KB；preview 缩放 0.25。
- snapshot 代际语义：refs 仅在当前代有效；跨代 `E_STALE_SNAPSHOT`；未知/淘汰 `E_ELEMENT_STALE`；容量 2048；TTL 5 分钟。
- `release_environment` 的 `display_kept_reason`、`screen_lease_released`、`kept/closed/forced/saved/discarded/restored_pids` 语义。
- `get_environment` 的完整字段集，包括 `client_id`、`screen_lease`、`privacy_redactions`、`focused_element`。

### 5.2 CLI 面

- 参数：`--help`、`--version`、`--doctor`、`--cli env|snapshot|screen|status|stop`、`--force`、`--ensure`、`--all`、`--daemon`、`--profile`、`--parent-pid`、`--allow-script`。
- 退出码：0 成功、1 失败、2 参数错误、3 实例/连接错误。
- 输出 JSON 形状与 `ok=true` 合并规则；`--cli screen` 的文件路径与命名。
- `--cli env` 在无实例时走只读 helper（不挂屏、不清理 state），并带 `ensure_ignored` 语义。

### 7.3 应用跟踪与生命周期

`TrackedAppRegistry`：

- 维护 `TrackedApp` 列表（字段不变：`Pid/OwnerClientId/ExePath/ContentPid/ContentExePath/Hwnd/Title/StartedProcess/StartedAt/Owned/CloseWindowOnRelease/DedicatedProcess/TempProfile/Placement/PlacementSaved/DeadSince`）。
- `IsLiveTrackedApp`、重定位、3 秒死亡宽限、按客户端过滤。
- 对外只暴露 `IReadOnlyList<TrackedApp>` 快照，内部 `lock (_appsGate)`。

`AppLauncher`：

- 标题候选/歧义、pid 接管、UWP frame 解析、路径与白名单、新实例参数、文档就绪检测（Word `Ctrl+N`、PowerPoint 空演示文稿 tile）、`reused/warnings` 语义。
- 所有等待时间、重试次数与现状一致。

`AppReleaser`：

- `abort/save/discard/force` 策略矩阵；
- WM_CLOSE → UIA 关闭按钮 → 保存对话框（3s 超时 → 退休当前 UIA 代际）；
- 专用进程/共享进程/临时 profile 的终止规则；
- `ProtectedSystemProcesses` 与 PID 复用校验；
- placement 归位与 `restored/kept/closed/forced/saved/discarded` 分类。

`AppLauncher`/`AppReleaser` 只依赖 `IWindowSystem`、`IProcessSystem`、`IUiaHost`、`ITrackedAppRegistry`，可在单测中替换。

`AppReleaser` 对外只保留两个入口，替代现有的隐藏参数：

```csharp
public ReleaseReport Release(ReleaseOptions options);        // 工具调用
public ReleaseReport ReleaseForShutdown();                   // Dispose 路径：摘屏 + 全量客户端
```

两者的字段、分类与副作用与现有 `ReleaseEnvironment(..., forceRemoveDisplay, forceAllClients)` 完全一致。`display_kept_reason`、`screen_lease_released` 属于 Server 的调度视图，由 `release_environment` 工具在 `ReleaseReport` 之外补充，不进入 `AppReleaser`。

### 7.4 UIA 与元素引用

`UiaHost`：

```csharp
public interface IUiaHost
{
    UiaTreeResult BuildTree(IntPtr hwnd, TreeOptions options, CancellationToken ct);
    FindResult FindElements(IntPtr hwnd, FindQuery query, CancellationToken ct);
    InvokeResult Invoke(ElementHandle handle, UiaInvokePattern pattern);
    // ...
}
```

- 单一后台线程，`CoInitializeEx(MTA)`；
- 请求队列 + `TaskCompletionSource`，调用方带超时；
- 超时后**不杀线程**：将当前 worker 标记为退休，启动新 worker；退休 worker 在 COM 调用返回后自行释放并退出（修复现有泄漏）；
- 所有返回值显式携带 `Truncated`，删除 `[ThreadStatic]`；
- MSAA 在同一 worker 上执行，保证 COM 串行；
- `UiaService` 退化为纯 COM 封装（无重试、无策略），由 `UiaHost` 负责生命周期。

**线程边界**：`IUiaHost` 对外保持**同步方法**（内部 `ManualResetEventSlim`/`Task.Wait(timeout)`），因为现有工具 handler 全部是同步的，且 `ExecuteToolAsync` 依赖“超时后 handler 仍持有写锁”的语义。异步化不做顺手改造；若未来要改，必须单独设计超时/取消语义并重跑并发审计。

**规模约束**：原 `UiaService.cs` 1,976 行必须按职责拆成 7 个文件（`UiaService`/`UiaElementFactory`/`UiaTreeWalker`/`UiaPatterns`/`UiaText`/`UiaControlTypes`/`UiaConditions`），每个 ≤600 行；否则无法满足 DoD。

`ElementRefStore`：

- 容量 2048、TTL 5 分钟、保留当前与前一代；
- key = `clientId + "\0" + elementKey`；
- UWP 归属按 HWND 进程校验（现有规则）；
- 提供 `BeginSnapshot(clientId)`、`EnsureSnapshot(clientId)`、`Register`、`Resolve`、`DropClient`；
- 全部方法显式接收 `clientId`，不读 `AsyncLocal`。

`UiaElementInfo` 只保留数据（记录），不再自带 `ToJson`/`ToCompactJson`；由 Server 的 `ElementPresenter` 生成 `ElementView`。这样 `Automation` 不再为了序列化而引用 `JsonObject`。

`SnapshotBuilder`：

- 输入 `SnapshotRequest`（pid/maxDepth/interactiveOnly/maxNodes/includeValues/includeScreenshot/scale/annotate）；
- 输出 `SnapshotView`（tree/text/nodes/visited/pruned/truncated/windows/dialogs/foreground/screenshot/annotations/privacy_redactions）；
- 保留：空树重试（200ms + 放宽 `interactive_only`）、`root_is_dialog`、`bosa` 对话框 MSAA 控件、`max_nodes_clamped`、`empty_reason`；
- 文本渲染改为消费 `SnapshotNode` record，输出格式逐字符一致。

## 8. 横切机制

### 8.1 错误模型

- `ErrorCatalog` 原样迁入 `Abstractions/Errors`，错误码字符串、`retryable`、`stage`、`hint` 全部不变。
- `ToolException` 改名为 `VspException`，公开字段不变（`Code/Details/Retryable/Hint/Stage`）。
- **JsonNode 边界**：`Details` 仍是 `JsonNode?`，但 `JsonObject` 的构造只允许发生在 `Abstractions/Errors` 的工厂方法内。`Automation` 只调用强类型工厂（如 `VspException.InvalidArg(field, expected, actual)`、`VspException.Busy(holder, heldMs, retryAfterMs)`），不直接 `new JsonObject`。这样既保持外部负载逐字段一致，又满足“Automation 不引用 `System.Text.Json.Nodes`”的约束。
- 复杂 details（候选窗口数组、`before_live`/`after_live`、`allowed_roots`）通过 `IReadOnlyList<string>`/`IReadOnlyDictionary<string, object?>` 传入工厂，由 Abstractions 负责序列化形状；工厂单测锁定每个错误码的 details 结构。
- `ErrorCatalog.Normalize` 的映射（COM HRESULT、AggregateException、UnauthorizedAccess、OperationCanceled）逐条保留。
- `Platform` 不抛 `VspException`：只返回 `bool`/`nullable`/标准异常（`Win32Exception`、`COMException`），由 `Automation` 映射为稳定错误码。

### 8.3 工具描述符与策略

```csharp
public sealed record ToolDescriptor(
    string Name,
    string Title,
    string Description,
    JsonNode InputSchema,
    JsonNode OutputSchema,
    ToolPolicy Policy,
    Func<ToolContext, JsonElement, ToolResult> Handler);

public sealed record ToolPolicy(
    bool ReadOnly,
    bool Destructive,
    bool Mutating,
    Func<ToolContext, JsonElement, bool> RequiresScreenLease,
    SessionAccess Access,                 // None / Read / Exclusive
    int TimeoutMs);
```

`RequiresScreenLease` 用委托而不是三值枚举，因为现状是**按参数**判断：

- `snapshot` 仅在 `include_screenshot || annotate` 时；
- `wait_for` 仅在条件为 `color/pixel_diff/visual` 时；
- `get_environment` 仅在 `ensure=true` 时；
- `release_environment` 仅在有 live apps 时；
- 其余写/视觉工具恒为 true。

`ToolContext` 是工具能看到的全部依赖，显式传入：

```csharp
public sealed class ToolContext
{
    public required ClientSession Client { get; init; }
    public required AutomationSession Session { get; init; }
    public required VspOptions Options { get; init; }
    public required ILog Log { get; init; }
    public required IMetrics Metrics { get; init; }
    public required IClock Clock { get; init; }
    public required IProgressReporter Progress { get; init; }
    public required CancellationToken CancellationToken { get; init; }
}
```

`ToolExecutor` 额外持有 `ScreenLease`、`WriteScheduler`、`SessionGuard`、`RateLimiter`、`ITrace`，这些不暴露给单个工具。

`ToolRegistry` 从 `ToolDescriptor[]` 构建，启动时校验：

- 名称唯一且与 `Definitions/<name>.json` 一致；
- schema 可解析、`type=object`；
- 策略组合合法（如 `Exclusive` 仅允许 `release_environment`）；
- `tools/list` 仍按名称 `Ordinal` 排序；
- `openWorldHint = !ReadOnly`、`idempotentHint = ReadOnly` 仍由只读标志派生，不单独配置。

**部署约束**：Server 以单文件发布，`Definitions/*.json` 必须以 `EmbeddedResource` 嵌入程序集并通过 `GetManifestResourceStream` 读取；禁止运行时依赖磁盘文件（否则绿色版/安装版行为改变）。

`ToolExecutor` 的流程与现状逐步对齐：

```
限流 → 解析 ClientSession → 屏幕租约（含 keep_foreground 延长）
→ 写调度（release 6s 等待 + 旁路）→ CancellationTokenSource(timeout)
→ SessionGuard 读/写 → progress(started) → handler
→ 超时：写锁与租约交给 handler 继续持有；epoch 校验
→ progress(completed) → trace/metrics → 响应
```

所有 `E_BUSY`/`E_SCREEN_LEASED`/`E_TIMEOUT`/`E_CANCELLED` 的 `details` 字段与 `retry_after_ms` 保持不变。

错误路径：`handler`/绑定层抛 `VspException` 时，`ToolExecutor` 用 `ErrorCatalog` 补全字段并返回 `IsError=true` 的 `ToolResult`；未知异常映射 `E_INTERNAL`。仍由工具层返回结构化错误，绝不让 SDK 转成无结构文本。

**必须照搬的时序/阈值**（外部可观察）：

| 项 | 值 |
|---|---|
| 限流 | 300 突发 / 100 每秒；daemon 内所有连接共享 |
| 写调度等待 | 普通写 30s；`release_environment` 6s |
| 写调度旁路 | `release_environment` 在写锁已持 ≥5s 时旁路 |
| release 读锁等待 | 3s，超时返回 `E_BUSY`（`retry_after_ms=500`） |
| 屏幕租约 TTL | 默认 60s；`VSP_SCREEN_LEASE_WAIT_MS` 默认 0；`keep_foreground` 延长 30s |
| 工具超时 | 各工具 `TimeoutMs` 原值（15s–130s） |
| 进度 | 开始时 `(0,1,"started")`，结束 `(1,1,"completed")` |
| 取消 | 超时后写锁/租约交给 handler；客户端取消同样不立即释放 |
| epoch | `release_environment` 校验通过后递增；在途结果返回 `E_CANCELLED` |

### 8.4 结果与响应

```csharp
public abstract record ToolResult
{
    public abstract object UntypedPayload { get; }
    public IReadOnlyList<ToolAttachment> Attachments { get; init; } = [];
    public bool IsError { get; init; }
}

public sealed record ToolResult<TPayload> : ToolResult
{
    public required TPayload Payload { get; init; }
    public override object UntypedPayload => Payload!;
}

public sealed record ToolAttachment(AttachmentKind Kind, string? Uri, string? Name,
    string? MimeType, long? Size, byte[]? Png);
```

`ToolDescriptor.Handler` 返回基类 `ToolResult`；具体工具用 `ToolResult<SnapshotView>` 构造。`ToolResponseWriter` 只读 `UntypedPayload`，不反射。

`ToolResponseWriter`：

1. 将 `Payload` 序列化一次为 `JsonNode`（或 `JsonDocument`）；
2. 注入 `request_id`；
3. text = 同一个节点的紧凑 JSON；structuredContent = 同一节点；
4. 按附件顺序追加 image/resource_link；
5. 不 `DeepClone`、不二次序列化。

**字段顺序**：视图模型属性按现有 JSON 拼装顺序声明；JSON 对象键顺序不构成语义契约，但 golden 测试仍对比原始 text，确保保守兼容。

### 8.5 参数绑定

`ToolArgumentReader` 是唯一实现：

```csharp
reader.RequiredInt("x");
reader.OptionalInt("max_depth", 4);
reader.OptionalNullableInt("pid");
reader.OptionalBool("interactive_only", true);
reader.OptionalDouble("scale", 0.5);
reader.Region();                     // 返回 Region?，统一 region 校验
reader.Enum("name_match", "exact", allowed);
```

- 错误码统一 `E_INVALID_ARG`，`details.field/expected/actual` 结构不变；
- 每个工具保留自己的提示文案（通过 `toolName` 与可选 `hint` 参数）；
- 三处调用方（MCP、CLI、ctl）共用；ctl 的宽松解析单独封装为 `LenientReader`；
- 底层类型读取放在 `Abstractions/Json/JsonArgReader`，`ToolArgumentReader` 只叠加工具名/文案；这样 P2 拆分后 `Automation` 不会反向依赖 Server；
- 绑定结果是每个工具自己的 typed request record（如 `ClickRequest`、`SnapshotRequest`），`Automation` 层不接收 `JsonElement`。

### 8.6 并发

- `SessionGuard`：保留 `ReaderWriterLockSlim` 语义（`EnterRead/ExitRead/TryEnterExclusive/ExitExclusive`）与 per-client epoch。
- `WriteScheduler`、`ScreenLease`：原样迁移，去掉静态 provider。
- 细分锁：`VirtualDisplayController._displayGate`、`TrackedAppRegistry._appsGate`、`ElementRefStore._refGate`、`SnapshotBuilder._snapshotGate`、`ArtifactStore._artifactGate`、`FocusGuard._focusActionGate`。
- 禁止跨组件锁嵌套；规定唯一顺序：`SessionGuard` → 组件锁。任何组件不得在持锁时回调另一个组件。
- 后台任务统一 `IHostedService` 风格（`StartAsync/StopAsync`），Dispose 时有界等待 + 取消。

### 8.7 日志、追踪、指标

- `LogRing` 去掉静态 `ClientIdProvider`，改为构造注入 `IClientIdAccessor`（由 Server 提供，线程安全）。`LogRing` 早于 `ClientSessionRegistry` 创建，访问器在 registry 就绪前返回 `null`，与现状一致。
- `TraceLog`、`Metrics` 通过接口注入工具执行器；测试可用内存实现。
- `TraceLog` 直接读取结构化结果（`ToolResult`/`VspException`）中的 `code`/`stage`，不再解析 text；`SummarizeArguments` 的脱敏字段清单（`text/value/code/args/password/window/path/save_path/target_path`）保持不变。
- 日志文案保持不变（审计与排障依赖）；新增日志只用于原本空捕获的位置。

## 10. 进程与组合根

### 10.1 `Program`

```
Main
 ├─ SetDpiAwareness / UTF8
 ├─ CommandLine.Parse
 ├─ help/version → 直接输出
 ├─ profile 预解析（写回环境变量）

 ├─ --daemon → ServerHost.RunDaemon

 ├─ 无实例 → 尝试 spawn daemon → 失败则 ServerHost.RunInProcess
 └─ 进程事件注册（ProcessExit/Ctrl+C/SIGTERM）统一在 ServerHost
```

`Program` 目标 ≤200 行，不含业务分支。

### 10.2 `ServerHost`

统一持有并管理：

- `VspOptions`、`LogRing`、`TraceLog`、`Metrics`
- `AutomationSession`（含全部组件）
- `InstanceRegistry`、`MutexGuard`、`JobObject`
- `WriteScheduler`、`ScreenLease`、`RateLimiter`
- `PipeHost`、`ControlServer`

提供 `RunStdioAsync`、`RunInProcessAsync`、`RunDaemonAsync`，共享：

- 启动顺序：Session 创建 → `Lifecycle.Initialize()`（清理/恢复/维护）→ Registry(ready=false) → ControlServer → PipeHost → Registry(ready=true) → 预热 → 父进程监听；
- 关闭顺序：PipeHost → ControlServer → Session → Registry → Trace → Log → Job → Mutex；
- 空闲退出与首连宽限；
- 退出码。

`DaemonHost` 退化为 `ServerHost.RunDaemonAsync` 的薄包装。

### 10.3 CLI 与 ctl

- `CliCommand` 接口：`Task<int> ExecuteAsync(CliContext ctx)`。
- `ControlInvoker`：封装管道连接、重试、超时、JSON 响应（原 `ControlClient`）。
- `LocalSessionInvoker`：无实例时构造临时会话的 env/snapshot/screen（原 `Program.RunCli`）。
- `ControlServer` 复用 `SessionDiagnostics`、`ArtifactStore`、`ILeaseState`；`admin_view` 与 legacy 字段保留。

对比规则（`compare_baseline.py`）：

- 根目录文件逐字段对比；易变 key（`request_id`/耗时/PID/日志路径/doctor 运行时快照）按 key 掩码；
- 字符串中的绝对路径、日期、时间戳先归一化再比较；
- 子目录只对比 `id → ok` 的用例通过集，不对比耗时、字节数、临时路径；只有“通过 → 失败”判定为回归，“失败 → 通过”不阻塞（改进不算破坏契约）。
- `manifest.json` 不参与对比；
- 对比必须同机、同驱动版本、同 Office；跨机器只对比 `--only server.json --only errors.json`。

`run_all.ps1` 的约定：

- 默认使用独立 profile（`-Profile`，默认 `vspaudit`），不碰用户正在用的 `default`；
- 缺少审计目标程序（`tools/audit/targets/bin/UiTarget/UiTarget.exe`，需 dotnet 构建）时跳过 `bench_protocol` 并记录原因；
- `-RecordOnly` 用于抓基线：失败项照常记录，但不以退出码判定整轮失败。
