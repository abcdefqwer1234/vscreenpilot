## 0. 摘要

第一轮重构已经完成验收：工程拆成 4 个程序集，`SessionManager` 从 10,919 行降到 1,774 行，22 个工具定义文件化，静态可变状态清零，单测从 84 个方法增加到 165 个方法，基线 diff 为 0，GUI / protocol / stability / UIA 审计全部通过。

但第一轮解决的是“**去巨石**”，还没有解决“**模块化**”。当前工程仍有五类结构性问题：

1. 命名空间与程序集错位，`InternalsVisibleTo` 全开，程序集边界只是编译方向，不是封装边界。
2. `SessionManager` 仍是能力中心：18 个 `I*Host`、187 个成员，组件通过宿主接口反向依赖门面。
3. 文件级拆分完成，方法级没有：**16 个 >150 行的方法（最大 `AppLauncher.Launch` 542 行）**，27 个 ≥120 行；9 个文件 >600 行。
4. 错误处理仍有生产盲区：34 处无类型静默 `catch`，83 处宽捕获只写 `Debug.WriteLine`（Release 下被编译掉）。
5. 测试金字塔倒置：18 个组件只有 4 个有直接单测，编排主要靠需要 VDD 的 Python 审计。

第二轮的目标是：**在不改变外特性的前提下，把“物理分层 + 门面中心”推进到“逻辑分层 + 组件可独立测试”**。预计 4 周（19–26 个工作日），分 8 个阶段，每个阶段独立可交付、可回滚。

## 2. 当前工程存在的问题

### 2.1 P1：命名空间与程序集错位，边界不成立

**事实**

| 命名空间 | 分布 |
|---|---|
| `VScreenPilot.Session` | Server 43 文件 + Automation 6 文件 |
| `VScreenPilot.Infrastructure` | Abstractions 2 + Platform 2 + Server 10 |
| `VScreenPilot.Mcp` | Abstractions 4 + Server 10 |
| `VScreenPilot.Ui` | Automation 2 + Server 1 |
| `VScreenPilot.Apps` | Automation 1 + Platform 1 |

`Automation` 的 27 个文件里 **0 个 public 类型**，但通过 `InternalsVisibleTo("VScreenPilot")` 把全部内部类型暴露给 Server；Abstractions 和 Platform 也各自对 Server/Automation 开了 IVT。

**典型错位**

- `ArtifactStore`、`FrameStore`、`SessionGuard`、`ClientSessionRegistry` 位于 Automation，但只被 Server 使用；
- `TrackedApp`/`TrackedAppRegistry` 位于 Automation，只被 Server 使用；
- `WindowManager` 位于 Platform，却使用 `VScreenPilot.Apps` 命名空间；
- `SnapshotTextFormatter` 位于 Server，却使用 `VScreenPilot.Ui` 命名空间；
- `MetricsRegistry`/`BuildInfo` 位于 Abstractions，却使用 `VScreenPilot.Infrastructure` 命名空间。

**影响**

- 看命名空间无法判断代码属于哪一层，新人只能靠项目文件推断；
- `internal` 不构成跨程序集边界，任何 Server 代码都能直接使用 Automation/Platform 内部实现；
- 想复用 Automation/Platform 时没有公开契约，必须先做一轮 API 设计；
- 架构评审只能靠人工，无法用测试阻止新的错位。

### 2.2 P1：门面仍是能力中心

**事实**

- 18 个 `I*Host` 共 187 个成员，全部由 `SessionManager` 实现；
- 组件对宿主的调用密度：`InputRouter` 79 次、`ElementOperations` 54 次、`EnvironmentReporter` 47 次、`AppLauncher` 38 次；
- 18 个组件中只有 `EnvironmentReleaser`、`SessionStateKeeper`、`AppAllowlistPolicy`、`MaintenanceService` 有直接单测，其余主要靠 GUI 审计。

**影响**

- 组件不是“可独立使用的模块”，而是“类 + 一个 20 多方法的宿主接口”；
- 写一个组件单测要先实现一个很重的 fake，测试成本高，导致测试金字塔倒置；
- 门面的行数降了，但接口面和依赖中心没有降；任何跨组件能力都要经过门面。

### 2.3 P1：方法级巨石

| 方法 | 行数 | 位置 |
|---|---|---|
| `Launch` | 542 | `Session/AppLauncher.cs` |
| `SnapshotCore` | 385 | `Session/SnapshotBuilder.cs` |
| `Ensure` | 330 | `Session/VirtualDisplayController.cs` |
| `ExecuteAsync` | 295 | `Tools/ToolExecutor.cs` |
| `GetEnvironment` | 294 | `Session/EnvironmentReporter.cs` |
| `Gesture` | 289 | `Session/InputRouter.cs` |
| `EvaluateCondition` | 277 | `Session/WaitService.cs` |
| `DoctorReportBuilder.Run` | 246 | `Diagnostics/DoctorReportBuilder.cs` |
| `Release` | 210 | `Session/EnvironmentReleaser.cs` |
| `MatchTemplate` | 205 | `Session/VisualMatchService.cs` |
| `TypeText` | 201 | `Session/InputRouter.cs` |
| `Click` | 201 | `Session/InputRouter.cs` |
| `Find` | 200 | `Session/ElementFinder.cs` |
| `SetElementValue` | 198 | `Session/ElementOperations.cs` |
| `Program.Main` | 176 | `Program.cs` |
| `ControlInvoker.Run` | 160 | `Cli/ControlInvoker.cs` |

**影响**

- 文件级拆分完成，但最复杂的逻辑仍集中在单个方法里，阅读、评审、单测都困难；
- 这些方法内部混合了协议解析、状态读取、副作用和错误映射，任何改动都可能影响多个分支；另有 11 个 120–150 行方法，完整清单由 `arch_metrics` 输出；
- 后续要拆组件时，先要面对这些方法，拆分成本被低估。

### 2.4 P2：错误处理仍有生产盲区

- 83 处宽捕获改为 `System.Diagnostics.Debug.WriteLine`：Release 下 `[Conditional("DEBUG")]` 会把整行编译掉，生产环境没有诊断。
- 34 处无类型 `catch { }` 静默返回默认值，例如 `OcrService`、`ScriptRunner`、`InstanceRegistry`、`ControlClient`、`WindowManager`。
- `catch (Exception` 共 134 处，其中一部分虽然有日志，但日志级别、错误码和 `stage` 不统一。

**影响**

- 现场问题只能靠“工具返回了默认值”猜测，无法从日志定位；
- 宽捕获掩盖的是“预期异常”还是“代码缺陷”无法区分；
- 与第一轮建立的 `ToolException`/`ErrorCatalog` 体系不一致。

### 2.5 P2：测试金字塔倒置

- 165 个单测主要覆盖视图序列化、策略、路径、拓扑、租约；编排层没有 xUnit 测试。
- 真正的编排验证依赖 `bench_gui.py`、`bench_protocol.py`、`bench_stability.py`、`bench_uia_stress.py`，需要 VDD 和自托管 runner。
- 主 CI 只跑 build/unit/contract/smoke/baseline diff；stability 与 UIA 压测还没有进 CI。
- `GUI-15`（应用被杀后按 exe 重定位到另一个同名窗口）仍是已知失败，没有回归测试锁住“应该失败还是应该恢复”的语义。

**影响**

- 组件级回归要等到夜间或人工跑审计才发现；
- 拆分组件时缺少快速反馈，容易把问题带到 GUI 阶段；
- 测试数量看起来不少，但关键路径覆盖不足。

### 2.6 P2：架构文档过期

`docs/architecture.md` 仍写着：

- “`SessionManager` 仍 4,408 行、20 个 partial”；
- “22 个工具中 5 个已走强类型视图”；
- “会话组件正在从 Server 迁入 Automation”。

与当前 1,774 行 / 17 partial / 22 个视图不一致。执行报告是准确的，但新人先读的是 architecture.md。

### 2.7 P3：其他结构性问题

- `SessionManager.ArtifactRootFor`、`ArtifactRetentionEnv`、`IsLiveTrackedApp` 是挂在门面上的静态工具，被 CLI/Doctor/Control 直接调用。
- `CliEnvironment` 与 `DoctorReportBuilder` 各自组装一份 artifact root/retention 摘要。
- `UiaHost` 用 `GetAwaiter().GetResult()` 同步等待 worker；`MsaaService`/`ScriptRunner` 也有 `Wait/Result` 超时；`UiaHost` 没有“调用超时自动换代”，`ResetUia` 仍是卡死时唯一恢复入口。
- `Server` 程序集 88 个文件、约 19.4k 行，承担 MCP、工具、会话、CLI、IPC、诊断、验证；这是应用层组合根，暂时合理，但后续增长需要垂直切分。
- `SessionManager.cs` 746 行仍 >600；R2 以“全仓最大文件 ≤800”为门槛，R3 再拆 partial。
- `VirtualDisplayController` 757、`McpTransport` 721、`ToolHandlers` 659、`SnapshotBuilder` 645、`VisualMatchService` 609 未进入 R2-3，列为 R3。
- `ToolContext` 仍持有 `SessionManager`；handler 的“独立可测”仍受门面约束。
- `Program` 与 `ServerHost` 各构造一次 `SessionManager`，组合根有两条 wiring 路径。

## 4. 目标架构

### 4.1 程序集与依赖方向

```
Server ──────> Automation ──────> Platform ──────> Abstractions
   │                │                  │
   └────────────────┴──────────────────┴──────────> Abstractions
```

规则：

1. 一个命名空间只能属于一个程序集；命名空间与目录同名。
2. `Automation` 不引用 Server/MCP SDK；`Platform` 只引用 Abstractions。
3. 程序集之间的 `internal` 访问必须出现在 `InternalsVisibleTo` allowlist 中。
4. 组件之间不得直接 `new` 另一个组件；跨组件协作通过宿主接口或组合根注入。

### 4.2 组件归属（目标）

| 层 | 组件 |
|---|---|
| Abstractions | 错误模型、`JsonArgReader`、`VspJson`、`Views/*`、`BuildInfo`、`MetricsRegistry` |
| Platform | Win32/COM 原语、`DisplayTopology`、`VddDevice`、`WindowManager`、输入注入/消息/键位/剪贴板、`JobObject`、`IntegrityCheck` |
| Automation | `UiaService`/`UiaHost`、`MsaaService`、`ScreenCapture`、`PngWriter`/`PngReader`、`TemplateMatcher`、`OcrService`、`ScriptRunner` |
| Server | MCP 传输/工具层、会话组合根、`Session` 组件、CLI、IPC、诊断、验证 |

Session 组件（Server）：

```
SessionManager（组合根/锁/生命周期）
├── VirtualDisplayController     显示与 VDD
├── AppLauncher / AppReleaser    应用生命周期
├── InputRouter                  输入编排（R2 拆分）
├── SnapshotBuilder              快照
├── ElementFinder/Resolver/Operations  元素
├── EnvironmentReporter/Releaser 环境
├── RegionVerifier/WaitService   断言/等待
├── VisualMatchService/ScreenTextService  视觉/OCR
├── FocusGuard/TrackedAppTracker 焦点/追踪
├── SessionStateKeeper/AppAllowlistPolicy  状态/白名单
└── MaintenanceService           周期清理
```

### 4.3 错误与日志

- Server 组件：通过宿主注入的 `LogRing` 记录 `Warn`/`Info`；宽捕获必须写明“为什么可以继续”。
- Platform/Automation：无 logger 的路径使用 `Trace.WriteLine`（Release 可见），或在调用方补充 `ToolException`。
- 所有对外错误继续走 `ToolException` + `ErrorCatalog`，不新增错误码。
- `catch` 规则：能确定预期类型的收窄类型；不能确定的记录日志并保留宽捕获；禁止无注释、无日志的空 `catch`。

### 4.4 测试策略

| 层级 | 内容 | 运行环境 |
|---|---|---|
| 单元 | 纯函数、视图、策略、路径、拓扑、拆分出的 helper | 主 CI |
| 组件 | fake host + 组件逻辑（输入路由、元素值写入、文档就绪、环境 section） | 主 CI |
| 契约 | schema/annotations/基线 diff | 主 CI |
| 集成/审计 | GUI、protocol、stability、UIA、hotplug | 自托管 VDD runner |

不在 xUnit 中启动真实 VDD；GUI 审计保持 Python 脚本，但纳入 nightly。
