1. **14 条全部有明确处置，没有“不处理”的条目。**

   - 替代修复（原现象属外部应用/系统限制，提供不依赖该现象的新路径）：**1 条** —— I-07。
2. **新增 5 个工具**：`read_table`、`lease_input`、`run_actions`、`select_tab`、`close_tab`。
3. **变更 10 个既有工具的 schema**（只增字段/参数，不删不改名）：`find_element`、`click`、`click_ref`、`click_text`、`press_keys`、`type_text`、`launch_or_place_app`、`capture_screen`、`read_screen_text`、`get_environment`。
4. **7 项无法在工具侧 100% 消除的残留**（见 §7.3），其中最关键的是：
   - `input` 通道仍会移动真实光标（虚拟 HID/独立输入桌面不在本版范围）；
   - OCR 对中文小字的识别率无法保证；
   - 窗口消息通道没有 ACK，只能靠命中/焦点/像素三证推断；
   - 已被加入 Job Object 的进程无法事后脱离（Windows 限制），只能新启动时选择 `detached`。
5. 建议按 **6 个阶段 / 5 个可独立合入的 PR** 交付，P0（I-01、I-02）先合入。

## 1. 设计原则与兼容策略

1. **默认安全、危险能力 opt-in**：`allow_destructive`、`lifecycle=detached`、`lease_input(exclusive=true)` 都必须显式开启。
2. **只增不改**：响应字段只增不删；新参数全部可选；除 §9.2 列出的默认行为变化外，旧调用语义保持不变。
3. **可观测优先**：命中元素、快照来源、输入租约、恢复来源都必须出现在返回值里，避免“看起来成功但对象不对”。
4. **单一事实来源**：前台/光标租约统一由新的 `ForegroundLease` 管理；`FocusGuard`、`CursorGuard`、click/type/press 不再各自维护暂停标志。
5. **不引入第三方依赖**：仅使用现有 Win32 / UIAutomation / MSAA / GDI 能力；新增 P/Invoke 只补 `DwmGetWindowAttribute`。
6. **批处理不绕过安全门**：`run_actions` 只能调用白名单内的既有工具，逐步骤复用相同的护栏、租约和只读检查。

## 4. 逐条详细方案

### I-01 `find_element` 返回过期快照数据

**现状与根因**

- `ElementFinder.Find` 每次都实时遍历进程所有可见顶层窗口（`ElementFinder.FindAcrossAppWindows`），**不读取快照缓存**。
- `snapshot_id` 来自 `EnsureSnapshot()`，只复用当前代标签，不推进代际（`ElementFinder.cs:133`）。
- 真正的偏差是“查询范围 ≠ 快照根”：`snapshot` 根只取当前活动弹窗（`SnapshotBuilder.cs:132` → `WindowManager.GetActivePopup`），而 `find_element` 搜索所有顶层窗口，`include_offscreen=true` 时还保留离屏控件。
- 因此旧控件数据可能来自快照根之外的窗口/离屏元素，而 `snapshot_id` 仍是旧代，调用方无法察觉。

**方案**

1. `ElementRefStore` 增加快照元数据：
   ```csharp
   internal readonly record struct SnapshotMeta(
       string SnapshotId, long Generation, long CreatedAtTicks, IntPtr RootHwnd);
   ```
   - `BeginSnapshot(clientId, IntPtr rootHwnd = default)` 记录创建时间与根；
   - 新增 `SetSnapshotRoot(clientId, hwnd)`，供 `SnapshotBuilder` 在解析根后回填；
   - 新增 `GetSnapshotMeta(clientId)`；`EnsureSnapshot` 首次创建时用当前 app 主窗口作为根。
2. `find_element` 新增参数：
   - `new_snapshot`（bool，默认 false）：为 true 时先解析 app 根/活动弹窗，`BeginSnapshot(clientId, hwnd)`，再执行查询；保证结果与代际一致。
   - `scope`（enum `app` | `snapshot`，默认 `app`）：`snapshot` 只查询 `snapshot_root_hwnd`，不跨窗口。
3. 响应新增字段（单元素与 `all=true` 都带）：
   - `snapshot_id`（已有）、`snapshot_age_ms`、`snapshot_root_hwnd`、`scope`；
   - `outside_snapshot`（bool）：任一结果来自非根窗口即为 true；
   - `sources: [{hwnd, pid, count, outside_snapshot}]`；
   - 每个元素增加 `hwnd` 与 `outside_snapshot`。
4. 排序：`scope=app` 时先按“属于快照根”分组，再按现有 `prefer` 规则排序，避免旧窗口元素抢占 `index=0`。
5. 文档：技术文档 6.5 增加“find_element 复用当前 generation；结果可能来自 root 之外的窗口，用 `outside_snapshot`/`sources` 判断；需要一致视图时用 `new_snapshot=true` 或 `scope=snapshot`”。

**测试**

- 单测：`SnapshotMeta` 创建/回填/过期；`outside_snapshot` 计算。
- 手工（CCW）：按 issues 的最小复现执行，断言旧行返回时 `outside_snapshot=true`；`new_snapshot=true` 返回新代与新数据。

**残留**：默认仍会跨窗口搜索（为了兼容 Office 对话框）；`outside_snapshot` 让调用方可判别，`new_snapshot` 提供强制一致路径。

### I-02 坐标点击不报告实际命中元素

**现状与根因**

- `ClickView` 没有 `hit_element`；`InputUiaGuardOps.TryUiaInvoke` 内部已拿到 `UiaElementInfo`，但用 `out _` 丢弃。
- `click.json` 的 `destructive=true` 只用于只读会话拦截和客户端提示（`ToolCallPipeline.cs:66,101`），没有目标级护栏。
- 自定义绘制标签页的 `✕` 可能根本不在 UIA 树里，单靠“命中元素名称”无法覆盖。

**方案**

1. **命中测试**
   - `UiaService.DescribeAtPoint(x, y, expectedPid, timeoutMs=500)`：`ElementFromPoint` + `Describe`，不触发任何动作；超时返回 null。
   - `TryInvokeAtPoint(..., out UiaElementInfo? info)` 已存在，`InputUiaGuardOps.TryUiaInvoke` 改为把 `info` 透传。
   - `click` 流程：
     - `auto`/`uia`：复用 UIA Invoke 返回的 info，避免二次查询；
     - `message`/`input`：注入前调用 `DescribeAtPoint`；
     - 超时/失败：继续点击，`hit_element=null`、`hit_source="window"`，并写 warning，不阻塞主流程。
   - `hit_source`：`uia` | `window`；`hit_element` 字段：`name/automation_id/control_type/bounds/enabled/destructive`。
2. **破坏性目标护栏**（新文件 `Session/DestructiveTargetGuard.cs`）
   - 策略来自 `VSP_DESTRUCTIVE_GUARD`：
     - `standard`（默认）：拦截 close/delete/remove/discard/clear/uninstall/overwrite/erase/reset 及中文“关闭/删除/移除/清空/放弃/卸载/覆盖/重置”；
     - `strict`：额外拦截 save/apply/confirm 及“保存/应用/确定”；
     - `off`：只返回 `hit_element.destructive`，不拦截。
   - 判定来源优先级：`hit_element.name` → `automation_id` → `control_type`（Button/MenuItem/Hyperlink/TabItem）。
   - **标签页关闭热区**：若 `hit_element.control_type == TabItem` 且点击点落在右缘 `min(24px, 15% 宽度)` 内，按“疑似关闭”处理（直接覆盖 issues 的实测场景）。
   - 未传 `allow_destructive=true` 时抛 `E_DESTRUCTIVE_TARGET`：
     ```json
     { "code":"E_DESTRUCTIVE_TARGET", "retryable":false, "stage":"security",
       "details":{"hit_element":{...},"reason":"name|tab_close_hotzone","policy":"standard"},
       "hint":"确认要执行破坏性操作时传 allow_destructive=true；或改用 select_tab/close_tab" }
     ```
3. **语义标签页动作**（两个新工具）
   - `select_tab(name, name_match?, index?, pid?)`：跨窗口找 `TabItem`；优先 `SelectionItemPattern.Select`，失败回退 `Invoke`，再回退中心点击；多命中返回候选（`E_ELEMENT_AMBIGUOUS`），用 `index` 指定。
   - `close_tab(name, name_match?, index?, pid?, allow_destructive?)`：
     - 先选中目标 tab；
     - 在 tab 子树中找 `Button` 名称匹配 `close/关闭/✕/×` 的子控件并 `Invoke`；
     - 找不到则选中后发送 `Ctrl+W`（仅对已知支持的应用，工具描述里写明）；
     - 必须 `allow_destructive=true`；返回 `closed`、`tab`、`method`。
4. `click_ref`/`click_text` 同样接入命中测试与护栏（`click_ref` 的元素名称已知，可直接判定）。

**测试**

- 单测：破坏性分类器（中英文、TabItem 热区、strict/standard/off）。
- 手工（CCW）：点击标签页右缘 `✕` 必须被拦截；`allow_destructive=true` 后关闭并返回 `hit_element`；`select_tab` 切换正确。
- 回归：普通“确定/取消”按钮不被误拦；只读会话仍整体拒绝 click。

**残留**：破坏性判定是启发式，未知语言/自绘控件可能漏判；`hit_element` 是兜底可观测信号。自定义 `✕` 若连 TabItem 都不暴露，仍无法拦截。

### I-04 消息点击静默失效

**现状**

- 当前 `ClickView.Verified` 直接等于 `observed?.Changed ?? false`，所以 issues 里“`verified=true` 但 `changed=false`”在当前代码中已不可能。
- 仍缺：命中元素、焦点变化、消息通道投递保证。

**方案**

1. 接入 I-02 的 `hit_element`。
2. 焦点探针（`UiaService.GetFocusedElement()`）：
   - 注入前、注入后各取一次，按 pid 过滤；
   - `ClickView` 增加 `focus_before`/`focus_after`（`{pid,name,automation_id,control_type,runtime_id}`）、`focus_changed`。
3. `delivery` 字段：`uia-invoked` | `message-posted` | `input-sent` | `input-fallback`；`message-posted` 明确表示“只投递，无 ACK”。
4. `suspect_noop` 计算：
   ```
   method ∈ {message, input, input-fallback}
   && !observed.changed
   && !focus_changed
   && (hit_element != null || hit_source == "window")
   ```
   为 true 时附 hint：“可能未命中或应用忽略消息；可换 channel=input、调整坐标，或先 get_element_text 验证”。
5. 不自动重试（避免双重点击）；由调用方根据 `suspect_noop` 决定。

**测试**

- 手工（CCW 属性面板）：默认 auto 点击值格，若无效则 `suspect_noop=true`；换 `channel=input` 后 `focus_changed=true`。
- 单测：`suspect_noop` 组合表（uia 成功不置位；message 无变化置位；input 有焦点变化不置位）。

**残留**：消息通道没有 ACK，仍无法 100% 证明“应用已处理”；三证只能提高判别率。

**现状**

**残留**：检测与实际点击之间存在毫秒级窗口；已通过 `settle_ms` 与逐击重解析降低概率，不能数学消除。

### I-06 缺少表格读取接口

**方案：新增 `read_table`**

参数：

| 参数 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |

| `name` / `name_match` | string/enum | 无/exact | 表格名称匹配 |
| `control_type` | string | 无 | `Table`/`DataGrid`/`List` |
| `automation_id` | string | 无 | AutomationId |

| `max_rows` | int | 100 | 1–500 |
| `include_header` | bool | true | 是否返回表头 |

**测试**

- 25 行表：`max_rows=10` 截断；`row_start` 生效。
- 列名不存在：`E_INVALID_ARG` + 可用列名。
- 回归：普通 `find_element(all=true)` 不变。

**残留**：完全自绘、不暴露行/列的表格只能走树回退，结果可能近似。

### I-08 会话中途重置 / 应用生命周期不独立

**现状**

- `AppLaunchFlowOps.TrackWindow` 在 `Started && Dedicated` 时把进程加入 Job（`AppWindowOps.AssignWindowProcessToJob`），`JobObject` 使用 `KillOnJobClose`。
- daemon 退出/崩溃 → 作业句柄关闭 → 应用被操作系统杀掉。
- `SessionStateKeeper.Recover` 只还原窗口 placement，不恢复 `apps` 列表，然后 `Store.Clear()`。
- 没有 detach 选项；`state.json` 文档写了 `ownerClientId`，代码未保存。

**方案**

1. **生命周期选项**
   - `launch_or_place_app` 新增 `lifecycle`：`session`（默认，旧行为）/ `detached`。
   - `LaunchOptions.Lifecycle`、`LaunchState.Detached`、`TrackedApp.Detached`/`Recovered`。
   - `detached` 时：
     - `TrackWindow` 不调用 `AssignWindowProcessToJob`；
     - `EnvironmentReleaser` 永不 `kill` 进程，只按 `close_on_release` 关闭窗口/归位；
     - `get_environment.apps[].detached=true`。
   - **限制如实写入文档**：Windows 不支持把已加入 Job 的进程移出；`detached` 只对新启动生效。
2. **state.json v2**
   - 增加 `savedAt`（UTC），`apps[]` 增加 `ownerClientId`、`clientKey`、`dedicated`、`detached`、`tempProfile`；
   - 保留读取 v1 的兼容路径（缺字段给默认值）。
   - `clientKey = SHA256(cwd + "|" + roots)` 的短哈希；同一工作目录/根集合的重连可自动认领。
3. **崩溃恢复**
   - `SessionStateKeeper.Recover`：
     - 校验 hwnd/pid/进程名后，构造 `TrackedApp { OwnerClientId="", Owned=false, Recovered=true }` 加入 `TrackedAppRegistry`；
     - 保留原来的 placement 还原；
     - 旧规则“恢复只还原位置、不恢复归属”改为：校验通过的窗口以 `recovered=true, owned=false` 重新登记；`state.json` 可清理，恢复清单留在内存中供报告与接管。
   - 新客户端连接时：
     - `clientKey` 匹配 → 自动认领（设置 owner，`Owned` 仍按 `launchedByUs` 规则）；
     - 不匹配 → 保持 `owned=false, recovered=true`，调用方可用 `launch_or_place_app(hwnd=...)` 接管。
4. **可观测**
   - `get_environment.session` 增加：`previous_pid`、`previous_started_at`、`state_age_ms`、`recovered_apps`；
   - daemon 启动日志：`从上一次会话恢复 N 个窗口（pid=..., 结束于...）`；
   - `session.job_object` 已有，`apps[].detached` 补充说明。
5. **空闲退出**
   - 保持 Unreleased 的 300s 默认；文档说明 `VSP_DAEMON_IDLE_MS` 只影响“空闲退出”，崩溃仍按 Job 语义处理。

**测试**

- 手工 A：`lifecycle=detached` 启动记事本 → 强杀 daemon → 进程仍存活；重启 → `recovered_apps>0`，可接管。
- 手工 B：`lifecycle=session` 启动 → 强杀 daemon → 进程被杀（旧行为，文档写明）。
- 单测：state v1/v2 读写；clientKey 匹配/不匹配；hwnd 复用校验。

**残留**：默认仍是 `session`，崩溃会杀应用；已入 Job 的进程无法事后脱离。长任务需显式 `detached`（见 §10 决策 4）。

### I-10 窗口大于虚拟屏 / 越界读取

**方案**

1. **窗口尺寸夹取**
   - 新增 `WindowManager.GetVisibleBounds(hwnd)`：`DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`，失败回退 `GetWindowRect`。
   - `launch_or_place_app` 新增 `fit`：`clamp`（默认）/ `keep`。
   - `PresentWindow` 在 `place=true` 且 `fit=clamp` 时：
     - 若可见宽/高超过虚拟屏，`MoveResize` 到 `display` 尺寸；
     - 若应用有最小尺寸导致仍超出，记录 `warning="fit_limited_by_app_min_size"`，不反复重试；
     - 返回 `fit_adjusted`、`requested_bounds`、`applied_bounds`。
2. **越界读取裁剪**
   - `VisualSupport` 增加 `ResolveRegion`：
     ```csharp
     internal readonly record struct ClampedRegion(
         int X, int Y, int Width, int Height,
         int RequestedX, int RequestedY, int RequestedWidth, int RequestedHeight,
         bool Clipped, string? Reason);
     ```
     - 区域与 `display` 求交；完全无交集 → `E_OUT_OF_BOUNDS`；
     - 部分相交 → 返回裁剪后的区域。
   - 适用范围：
     - `capture_screen`、`read_screen_text`、`click_text`：默认 `on_out_of_bounds=clip`；
     - `assert_region`、`match_visual`、`wait_for(pixel/text/color)`：默认 `error`，保持基线语义；如需裁剪显式 `clip=true`。
   - 响应增加 `clipped`、`requested_region`、`region`（实际）。
3. `set_display` 可选 `fit_windows=true`：重排时对仍超出的窗口做一次 `MoveResize`；默认 false。
4. 文档：技术文档 8.6、6.3、6.19；errors.md 的 E_OUT_OF_BOUNDS 说明“读类工具可裁剪”。

**测试**

- 手工：1936 宽窗口 → `fit=clamp` 后可见宽度 ≤1920，`fit_adjusted=true`。
- `capture_screen(x=4290,w=200)` → 返回 `clipped=true`，实际宽 190；完全越界仍 `E_OUT_OF_BOUNDS`。
- 回归：`assert_region` 越界仍报错，避免误判。

**残留**：应用最小尺寸大于虚拟屏时无法真正夹取；读类工具用裁剪兜底。

### I-11 OCR 对中文小字识别差

**方案**

1. 新 `Automation/Perception/BitmapOps.cs`：`Upscale(bgra, width, height, factor)`（bilinear，>`VSP_OCR_UPSCALE=nearest` 可切最近邻）。
2. `read_screen_text` / `click_text` 新增 `upscale`：
   - `0 = auto`（默认）：`min(region.Width, region.Height)` ≤160 → 4x；≤300 → 3x；≤600 → 2x；否则 1x；
   - `1..4` 强制。
3. OCR 前放大；OCR 返回的行框/中心点除以 factor 再映射回屏幕绝对坐标。
4. 输出增加 `upscale`、`ocr_source_size`、`ocr_scaled_size`。
5. 文档 9.7：明确“中文小字优先 UIA；OCR 建议 `upscale=2..3`，识别率仍不保证”。

**测试**

- 单测：坐标映射（factor 2/3/4）；auto 选择边界。
- 手工：issues 中的“4 - 报警/诊断”区域，1x vs 2x/3x 对比；`click_text` 命中中心。

**残留**：OCR 精度无保证；本方案只改善输入质量并给出文档边界。

### I-12 前台守卫导致每次点击都要显式 `keep_foreground`

**现状**

- `keep_foreground=true` 只是 `PauseFocusGuard(30000)`；`input` 点击在 `finally` 里 `ResumeFocusGuard()`，会提前清掉暂停。
- 没有会话级前台租约。

**方案：`ForegroundLease` + `lease_input`**

1. 新 `Server/Infrastructure/ForegroundLease.cs`：
   ```csharp
   internal sealed record InputLeaseView(
       string LeaseId, string ClientId, int Pid, long Hwnd,
       long ExpiresAt, bool Exclusive, string Source);

   internal sealed class ForegroundLease
   {
       InputLeaseView Acquire(string clientId, int pid, long hwnd, int ttlMs, bool exclusive, string source);
       bool Renew(string clientId, int ttlMs);
       bool Release(string clientId, bool restoreForeground);
       InputLeaseView? Status(string clientId);
       bool IsActive(string clientId);
       bool IsActiveForPid(int pid);
       void OnClientDrop(string clientId);
   }
   ```
   - TTL：1s–600s，默认 30s；
   - 同一客户端重复 acquire → 续期并更新 pid/hwnd；
   - 其他客户端持有不同 pid 的租约 → `E_INPUT_LEASE_CONFLICT`（details 返回 holder），`force=true` 可抢占。
2. `lease_input` 工具：
   - `action=acquire|release|renew|status`；
   - `pid?`、`ttl_ms?`、`exclusive?`、`force?`；
   - 返回 `lease_id/pid/hwnd/expires_at/active/exclusive/source`。
3. 统一接入：
   - `FocusGuard.GuardOnce`：租约活跃时直接返回，不归还前台；
   - `CursorGuard`：租约活跃时保持暂停（引用计数，避免 input 操作结束后恢复）；
   - `InputClickOps.SettleFocus`/`InjectInput`：租约活跃时跳过 `RestoreForeground` 与 `ResumeFocusGuard`；
   - `keep_foreground=true` 改为 `lease.Acquire(..., source:"keep_foreground")`，不再直接操作 `_paused`。
4. 生命周期：
   - `release_environment`、客户端断开、daemon 退出 → `lease.Release(restoreForeground:true)`；
   - 过期自动失效，下一次工具调用清理。
5. `get_environment.session.input_lease` 暴露当前租约（没有则 null）。

**测试**

- 单测：acquire/renew/expire/conflict/onClientDrop；`keep_foreground` 与 `lease_input` 互操作。
- 手工：acquire 60s → 连续 5 次 click（不传 keep_foreground）→ 每次之间 `foreground` 仍是 CCW；release 后回主屏。

**残留**：租约只解决“工具调用之间不归还前台”，不改变“真实前台是全局资源”的事实；用户主动切走仍会生效（`exclusive=true` 时由守护线程抢回，见 I-13）。

### I-13 `input` 通道移动真实光标、跨调用不保持前台

**方案（与 I-12 同一模块，分两条验收）**

1. **租约内输入**
   - `lease_input` 活跃期间：
     - FocusGuard 不归还前台；
     - CursorGuard 保持暂停，`input` 点击结束后不立即弹回光标；
     - `input` 点击/按键结束不恢复前台（不再依赖 `keep_foreground`）。
2. **真实光标仍会移动**
   - 保留现有 `SendInput` + 结束后 `SetCursorPos` 还原；
   - 文档显著标注：“`channel=input` 会移动真实光标；用户正在主屏操作时不要用。需要长时间无人值守时先 `lease_input`，或改用 UIA/消息通道。”
3. **可选独占**
   - `lease_input(exclusive=true)` 启动 200ms 守护：检测前台偏离租约 hwnd 时 `ForceForeground` 抢回；
   - 默认 false；开启时返回 `warning="exclusive_lease_may_fight_user"`。
4. **不做的部分**
   - 虚拟 HID / 独立输入桌面不在本版范围（需要驱动/系统级改动，风险与工期都超出 P3）。
5. 与 I-14 联动：`run_actions` 在整批步骤外只 acquire 一次租约，天然消除“5 次调用抢 5 次前台”。

**测试**

- 手工：租约内 5 步操作，主屏光标不弹回（但仍会短暂跳到虚拟屏）；释放后前台/光标归还。
- 单测：CursorGuard 引用计数；exclusive 守护线程启动/停止。

**残留**：真实光标移动无法在用户态消除；文档与租约只能降低打扰频率。

### I-14 缺少批量执行通道

**方案：新增 `run_actions`（白名单动作序列）**

参数：

| 参数 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `steps` | array | 必填 | 1–50 步 |
| `steps[].action` | string | 必填 | 白名单动作名 |
| `steps[].args` | object | {} | 传给该动作的参数 |
| `steps[].continue_on_error` | bool | false | 单步失败是否继续 |
| `steps[].timeout_ms` | int | 15000 | 单步协作式超时；不响应取消的 handler 仍可能跑完预算 |
| `stop_on_error` | bool | true | 全局失败策略 |
| `lease_ms` | int | 30000 | 整批共享的输入租约 |
| `dry_run` | bool | false | 只校验不执行 |

白名单（不含会改变会话/显示/安全边界的工具）：

```
click, click_ref, click_text, invoke_element, set_element_value, get_element_text,
press_keys, type_text, wait_for, assert_region, match_visual,
read_table, find_element, snapshot, capture_screen
```

实现：

1. 新 `Session/ActionBatchService.cs`：顺序调度；每步构造与单工具相同的参数对象，调用现有 service 方法（不经过 MCP 传输，避免递归）。
2. 整批：
   - 开始 `lease.Acquire(..., source:"run_actions")`（若已有租约则续期，不重复抢）；
   - 结束 `Release(restoreForeground:true)`（异常路径同样释放）。
3. 只读会话：任一步骤的 descriptor `destructive || mutates` → 整批 `E_READ_ONLY`，不执行任何一步。
4. `dry_run`：校验动作名、参数必填项、refs 是否属于当前客户端；返回计划，不执行。
5. 输出：
   ```json
   { "ok":true,"completed":5,"aborted_at":null,
     "steps":[{"index":0,"action":"click","ok":true,"elapsed_ms":42,"result":{...}}],
     "lease":{"lease_id":"L3","expires_at":"...","source":"run_actions"},
     "elapsed_ms":312 }
   ```
6. 文档：技术文档新增 6.30；`README` 工具表；`errors.md` 说明步骤错误保留原错误码。

**测试**

- 手工（CCW）：`click` 选中对象 → `set_element_value` 改 4 个属性 → `press_keys` 确认，一次调用完成；前台只抢一次。
- 单测：白名单拒绝 `run_script`/`release_environment`；`stop_on_error`；`dry_run`；只读拒绝。
- 回归：单工具调用行为不变。

### 7.2 与 issues.md 原文的差异（方案需同步纠正）

1. I-01 的“返回上一代快照缓存”不成立；实际是“跨窗口查询范围与快照根不一致”。方案按后者修。
2. I-04 的“`verified=true` 但 `changed=false`”在当前代码已不成立（`verified == observed.changed`）；方案改为 `suspect_noop`。
3. I-13 的“`keep_foreground` 完全不跨调用”不准确：暂停 30s 本来跨调用有效，但会被下一次 `input` 点击清除；方案用租约统一。
4. I-07 不是工具缺陷；方案不修应用复制行为，只提供替代读取。

### 7.3 不可 100% 消除的残留（必须在发布说明中写明）

1. **`input` 通道仍移动真实光标**：用户态无法隔离；虚拟 HID/独立输入桌面不做。
2. **OCR 精度无保证**：放大只改善输入质量，中文小字/低对比度仍可能失败。
3. **消息通道无 ACK**：只能靠命中元素/焦点/像素变化推断，`suspect_noop` 是启发式。
4. **已入 Job 的进程无法事后脱离**：Windows 不支持移出 Job；`detached` 仅对新启动生效。
5. **破坏性分类是启发式**：自绘控件、非中英文名称、未知关闭图标可能漏判；`hit_element` 是可观测兜底。
6. **多击窗口检测存在毫秒级竞态**：检测与实际点击之间仍可能插入新窗口；`settle_ms` 可降低概率。
7. **崩溃恢复的归属依赖 clientKey**：同一 cwd/roots 的多个客户端可能争用；不匹配时保持 `owned=false`，需显式接管。

### 7.4 方案间的相互影响

| 交互 | 处理 |
| --- | --- |
| 破坏性护栏 vs `close_tab` | `close_tab` 必须 `allow_destructive=true`；内部调用走同一护栏 |
| 破坏性护栏 vs 正常“确定/取消” | `standard` 不拦截确定/取消；`strict` 才拦截保存/应用 |
| 多击中止 vs 用户本意“双击打开后继续点” | 中止只停止后续点击并返回 `opened_dialog`，不报错；调用方可显式关闭 |
| `lease_input` vs `keep_foreground` | `keep_foreground` 只是 `lease.Acquire(source=keep_foreground)` 的别名，不维护第二套状态 |
| `run_actions` vs 只读会话 | 整批预检，任一步 destructive/mutates 即 `E_READ_ONLY` |
| 区域裁剪 vs `assert_region` | 断言类默认 `error`，避免“裁剪后仍判定通过”的假阳性 |
| `find_element(new_snapshot)` vs 旧 ref | 推进代际会让更老 ref 失效；文档写明，仅在同一调用内强制新鲜 |
| 新增工具 vs 基线 | 0.4.0 基线冻结 30 工具；0.3.1-dev 基线保留用于回归 |

### 7.5 结论

- **所有 14 条都有可执行方案与验收判据，不存在“无解”条目。**
- 但“解决”不等于“彻底消除”：6 条根因消除，7 条通过可观测/开关满足 issue 的验收目标，1 条以替代路径满足；§7.3 的 7 项残留是系统/应用边界，不应在发布说明中承诺为“已彻底修复”。
- 如果要求 I-13 的“真实光标不移动”也必须解决，则需要单独立项（虚拟 HID/独立输入桌面），本方案不含。

### 9.2 默认行为变化（需在 CHANGELOG 明示）

1. `click` 默认执行命中测试，返回值多字段；破坏性目标默认拦截（`standard`）。

3. `keep_foreground=true` 改为 30s 输入租约；不再被后续 input 点击提前清除。
4. `capture_screen`/`read_screen_text` 对部分越界区域默认裁剪而不是报错。
5. `launch_or_place_app` 默认 `fit=clamp`，超大窗口会被缩到虚拟屏（可用 `fit=keep` 保持旧行为）。
6. `press_keys`/`type_text` 默认 `target=app`，与旧行为一致。
7. `find_element` 默认仍跨窗口，但返回 `outside_snapshot`；`scope=snapshot` 可选。

### 9.3 灰度与开关

| 开关 | 默认 | 用途 |

## 10. 风险与待决策

### 10.1 待确认的 6 个决策点（推荐值已给）

| # | 决策 | 推荐 | 影响 |
| --- | --- | --- | --- |
| 1 | 破坏性护栏默认策略 | `standard`（拦截关闭/删除/清空；保存/确定放行但返回 `destructive_hint`） | `strict` 会拦住安装器“保存/下一步”类按钮，影响无人值守安装 |
| 2 | 是否接受工具数 25 → 30 | 接受（`read_table`/`lease_input`/`run_actions`/`select_tab`/`close_tab`） | 也可合并为 `tab_action`，但语义清晰度下降 |
| 3 | `lease_input` 是否默认独占 | 否（`exclusive=false`，只在调用之间不归还） | 默认独占会与主屏用户抢前台 |
| 4 | `lifecycle` 默认值 | `session`（兼容旧行为），长任务显式 `detached` | 若默认 `detached`，崩溃不再杀应用，但孤儿进程清理变弱 |
| 5 | `find_element` 默认 scope | `app` + `outside_snapshot` 标记（兼容） | 若默认 `snapshot`，跨对话框查找会退化 |
| 6 | 版本号/基线 | `0.4.0` 新基线，`0.3.1-dev` 冻结 | 若坚持 0.3.1-dev，需覆盖旧基线，历史对比丢失 |

### 10.2 风险登记

| 风险 | 概率 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 破坏性护栏误拦正常按钮 | 中 | 中 | `standard` 保守词表；`allow_destructive`；一键 `off` |
| 命中测试拖慢点击 | 中 | 中 | 500ms 超时 + pid 熔断 + 不阻塞 |
| 多击中止误伤合法双击 | 中 | 中 | 只中止+报告；`abort_on_window_change=false` 可回退 |
| 租约导致前台被长期占用 | 低 | 高 | TTL 上限 600s；断开即释放；默认非独占 |
| `detached` 留下孤儿进程 | 中 | 中 | 文档写明；`get_processes/list_windows` 可发现；不默认开启 |
| 恢复归属串客户端 | 低 | 中 | clientKey 匹配；不匹配保持 `owned=false` |
| 表格回退结果不精确 | 中 | 低 | `source:"tree"` + warning；优先 pattern |
| 放大导致内存峰值 | 低 | 中 | 40MP 上限；按区域截图 |

## 附录 B CCW 手工验收脚本（摘要）

1. **准备**：`launch_or_place_app(path=CCW, lifecycle=detached)`；`snapshot` 确认主窗口。
2. **I-01**：按 issues 步骤打开 A 的状态框 → snapshot → 关闭 → 打开 B → `find_element(name contains "标题文本 行", all=true, include_offscreen=true)`；记录 `outside_snapshot`；再 `new_snapshot=true` 重查。
3. **I-02**：`click(x=标签页右缘, y=标签页中心)` → 期望 `E_DESTRUCTIVE_TARGET`；`allow_destructive=true` 重试 → 期望关闭且 `hit_element` 指向关闭按钮/TabItem。
4. **I-03**：打开状态框 → `press_keys(keys="Esc", target="current_dialog")`；重复打开/关闭两次。
5. **I-04**：在属性面板值格 `click(channel="auto")` → 检查 `suspect_noop`；`channel="input"` 重试 → 检查 `focus_changed`。
6. **I-05**：画布对象 `click(clicks=2, interval_ms=140, settle_ms=150)` → 检查 `clicks_done=1` 与 `opened_dialog`；确认对话框内表格未被点击。
7. **I-06**：`read_table(columns=["数值","标题文本"], max_rows=10)` → 与 `find_element` 的 `value` 对照。
8. **I-07**：全程不发送 `Ctrl+A/C`，仅用 `read_table` 完成读取。
9. **I-08**：另起一个 detached 记事本；`taskkill /F` daemon → 记事本存活；重新连接 → `get_environment` 的 `recovered_apps`；再用 `launch_or_place_app(hwnd=...)` 接管。
10. **I-09**：`capture_screen(x,y,200,100,scale=4)` → 检查输出 800×400；`save_path` 后人工阅读。
11. **I-10**：把 CCW 窗口拉到 1936 宽 → `launch_or_place_app(fit=clamp)` → 检查 `applied_bounds`；`capture_screen(x=4290,w=200)` → `clipped=true`。
12. **I-11**：`read_screen_text(query="报警", upscale=3)` → 对比 1x；`click_text(text="报警", upscale=3)` → 检查命中。
13. **I-12/13**：`lease_input(action="acquire", ttl_ms=60000)` → 连续 5 次 `click`（不传 keep_foreground）；每次后 `get_environment.foreground`；`lease_input(action="release")`。
14. **I-14**：`run_actions(steps=[click, set_element_value ×4, press_keys], lease_ms=60000)` → 检查 5 步结果与前台只抢一次。
