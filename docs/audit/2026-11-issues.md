## I-01 `find_element` 返回过期快照数据（P0）

**期望**：在“状态”对话框换成另一个对象后，`find_element` 要么重新遍历，要么明确报 `E_STALE_SNAPSHOT`。

**实际**：返回旧对话框的行数据，`snapshot_id` 仍是旧代（`s4`），无任何警告。

**最小复现**

1. 双击对象 A，打开其“状态”对话框；`snapshot` → `snapshot_id = s4`。
2. 关闭对话框，双击对象 B，打开新的“状态”对话框。
3. 直接调用：
   `find_element(name="标题文本 行", name_match="contains", all=true, include_offscreen=true)`
4. 返回值为对象 A 的行（例如“空闲 / 抬笔 / 绘制中…”），`snapshot_id` 仍为 `s4`。
5. 先调用 `snapshot`（生成 `s6`），再执行同样的 `find_element`，才返回对象 B 的行（“无 / 状态不允许 / 图案无效…”）。

**影响**：读到的数据看起来完全正常，但属于另一个控件；自动化结论会被污染。

**建议**
- `find_element` 增加 `new_snapshot` 参数，或检测到顶层窗口/焦点变化时强制重走。
- 返回值里带 `age_ms` / `stale` / `root_hwnd`，调用方可校验。
- 文档显著标注“find_element 复用当前 generation”。

## I-02 坐标点击不报告实际命中元素（P0，安全）

**期望**：点击后返回真实命中的元素（名称/automation_id），或在目标为 `✕`/关闭/删除类控件时拒绝/二次确认。

**实际**：只返回 `clicked=true` 与截图 diff，不告诉你点到了什么。

**实际案例**：点击标签页“画面: 3 - 图案”的坐标 (3365,123)，落在文字右侧的 `✕` 上，标签页被关闭（未保存内容为空，无数据损失）。在“不得修改目标程序”的任务里，这类误触后果不可控。

**建议**
- 点击前用 `WindowFromPoint` + UIA element-at-point 做命中测试，返回 `hit_element`。
- 破坏性目标（`Close`/`删除`/`保存`）需要显式 `allow_destructive=true`。
- 提供 `select_tab(name)` / `close_tab(name)` 语义动作，避免坐标切标签。

## I-03 模态对话框 hwnd 不稳定（P1）

**期望**：`press_keys(hwnd=...)` 能一直指向“当前活动对话框”，或提供 `target="current_dialog"`。

**实际**：同一个“状态”对话框每次打开 hwnd 都不同（本次观测：394568 → 67384 → 132944 → 133018 → …）。用旧 hwnd 调用直接 `E_WINDOW_NOT_FOUND`；不带 hwnd 又因主窗口被模态禁用而 `E_BLOCKED`。

**影响**：每读一张表多 2~3 次调用（查环境 → 取 hwnd → 发 Esc）；批量巡检成本翻倍。

**建议**
- `press_keys` / `click` 支持 `hwnd="dialog"`（取当前进程的模态顶层窗）。
- `E_BLOCKED` 的 `dialogs[0].hwnd` 可被后续调用直接引用（例如 `dialog_ref`）。

## I-04 消息点击静默失效（P1）

**期望**：`channel=auto/message` 失败时明确返回 `method=message_failed` 或自动降级并标注。

**实际**：返回 `clicked=true`、`verified=true`，但 `observed.changed=false`；属性面板未获得焦点，值格未进入编辑。

**复现**：在 WinForms 属性面板的值格上用 `click(x,y)`（默认 auto）点击；再换 `channel=input, keep_foreground=true`，仍无变化；换一个 y 坐标才成功。

**建议**
- 返回实际使用的 `method` 与命中元素。
- `observed.changed=false` 时区分“元素未命中”和“命中但无视觉变化”。

---

## I-05 双击竞态（P1）

**期望**：双击是原子动作；第一击导致新窗口出现时，第二击不应落到新窗口上。

**实际**：`click(clicks=2, interval_ms=140)` 在画布对象上会打开模态对话框，第二击可能落在对话框的表格/按钮上；随后读取到的仍是上一个对话框（与 I-01 叠加）。

**建议**：新增 `double_click`，两击之间检测顶层窗口变化，变化则中止并返回 `opened_dialog=hwnd`；或提供 `settle_ms`。

## I-06 缺少表格读取接口（P2，Feature）

**现状**：DataGridView 暴露为 `Table → Custom(行) → DataItem(列)`，每行 22 列。6 行表的整树快照 JSON 约 15k 字符，25 行表更大；无法只取某列。

**建议**
- `read_table(root_ref, columns=[...], max_rows=N)` → 返回 `[{row:0, 数值:"0", 标题文本:"..."}]`。
- 支持按列名过滤、按行号排序（当前 `find_element` 返回顺序是按可见性，不是行号）。

**临时规避**：`find_element(name contains "标题文本 行")` 一次拿所有行的 `value`（本次最有效的手段，建议写进文档）。

## I-07 表格内剪贴板复制不完整（P2）

**现象**：状态表格中 `Ctrl+A` 后 `Ctrl+C`：
- 第一次读回的是用户原有剪贴板内容；
- 第二次只得到 `0\t1625` 两列，数值疑似被截断。

**建议**：不依赖系统剪贴板；用 `read_table` 或 UIA `ValuePattern` 批量读。

## I-08 会话中途重置（P1，因果未证实）

**现象**：约 17:40，守护进程 pid 从 2288 变为 11884，`session` 重新初始化，`apps` 列表清空；同时被测宿主进程已不存在。

**影响**：已接管窗口、屏幕租约、前台状态全部丢失，需重新接管。

**说明**：无法判定是工具导致、宿主自行退出还是外部操作，仅记录为“会话不持久”的风险。

**追加观测（2026-11-25 18:18）**：在一次写操作（改 CCW 画面对象的 左/上/宽/高）进行中，CCW 第二次退出；因尚未保存，内存里的改动全部丢失（磁盘 `.cha` 未变）。两次退出都发生在 MCP 会话/守护进程变动的时间窗内，应用生命周期没有独立于 MCP 会话。

**影响（写场景）**：长任务无法“边改边保存”以外的任何方式保证进度；一旦会话重置，正在编辑的工程直接回退到上次保存点。

**建议**：重启后保留上次的已接管窗口清单与最后状态；日志记录重启原因；应用进程不要挂在 MCP 会话的 Job Object 下（或提供 `detach` 选项）。

## I-09 截图不支持放大（P3，Feature）

`capture_screen.scale ≤ 1`，12px 中文在 1x 下 OCR 失败、肉眼也吃力。本次只能先 `save_path` 存 PNG，再用 System.Drawing 放大 4 倍阅读。

**建议**：允许 `scale > 1`（超采样），或提供 `crop + upscale`。

---

## I-10 窗口大于虚拟屏（P3）

宿主窗口 1936px 宽 > 虚拟屏 1920px，右侧约 16px 被裁；读取区域 `x=4290,w=200`（右边界 4490 > 4480）直接 `E_OUT_OF_BOUNDS`。

**建议**：接管时自动夹到工作区；或允许读取被裁区域并提示裁剪。

## I-11 OCR 对中文小字差（P3）

项目树 OCR 将“4 - 报警/诊断”识别为“0 4 一 报 / 诊 断”，`click_text` 无法命中，只能改用 UIA/坐标。

**建议**：文档明确“中文小字不要依赖 OCR”；或对区域先放大再 OCR。

---

## I-12 前台守卫的操作摩擦（P3，Feature）

共享桌面上前台频繁被抢，几乎每次点击都要显式 `keep_foreground=true`；`press_keys` 不带 hwnd 又会被模态框拦。

**建议**：提供“会话级前台租约”（一次申请、N 秒内所有调用有效），或批量动作脚本接口。

## I-13 `input` 通道移动真实光标、跨调用不保持前台（P1，Bug/设计）

**背景**：工具的核心目的是“不占用主屏，不影响用户观察和操作”。本次实测发现，这个隔离只做到**显示层**，没做到**输入层**。

**期望**：窗口放到虚拟屏后，点击/按键也应留在虚拟屏内；或在一次“输入租约”内完成整段操作，不打扰主屏用户。

**实际**：
1. CCW 的画面编辑器忽略窗口消息，`click`/`press_keys` 直接返回 `E_INPUT_UNSUPPORTED`，必须改用 `channel=input`。
2. `input` 会**移动真实光标**并抢真实前台；主屏用户能看到光标跳到副屏、前台被切走。
3. `keep_foreground=true` 只“暂停焦点守卫 30 秒”，**跨工具调用不保持**；两次调用之间 `foreground` 已经变回主屏的 Code，下一次点击又要重新抢。
4. 一次“选中对象 + 改 4 个属性”需要 5 次调用，每次都可能重新抢前台；批量改 47 个对象因此不可行。

**复现**：在 CCW 画布上选中对象 → 改 左/上/宽/高 → 下一次 `click` 前观察 `get_environment.foreground`，已不是 CCW；`input` 点击时真实光标坐标落在虚拟屏。

**影响**：与“不影响用户操作”的核心目的直接冲突；对忽略消息的 WinForms/Chromium 应用尤其明显。用户在主屏打字时，光标会被抢走。

**建议**
- 增加会话级输入租约：`lease_input(pid, ttl)`，租约内光标/前台由 Agent 独占，结束或超时归还。
- 或提供不移动物理光标的 `input` 实现（虚拟 HID / 独立输入桌面）。
- 文档显著标注：“`input` 会移动真实光标，用户正在主屏操作时不要用”。

## I-14 缺少批量执行通道，`run_script` 默认关闭（P2，Feature）

**期望**：一个进程内连续完成“点选 → 改属性 → 确认”，避免调用之间前台被抢。

**实际**：`run_script` 需 `--allow-script` 才启用，默认关闭；MCP 每次调用只做一个动作，而 CCW 改一个对象要 5 次调用。批量脚本只能绕过 MCP、用宿主 PowerShell + UIA 自己实现（即仓库里的 `tools/ccw`），而它又受 I-13 的焦点问题影响；本次批量脚本运行 10 分钟无输出，最后只能强杀。

**建议**
- 开放受限的批量动作接口（`click → set_value → key` 序列，白名单参数），一次调用完成一串动作。
- 或允许 `run_script` 以只读/白名单模式启用，并在脚本内复用工具的前台租约。

## 已验证正常、无需改动的部分

- `E_BLOCKED` 会在 details 里直接给出模态对话框 hwnd，定位很快。
- `find_element` 能返回 DataItem 的 `value`，是读状态表最有效的手段。
- `E_FOREIGN_WINDOW` 能拦住落在任务栏等非会话窗口上的点击，安全护栏有效。
- 虚拟屏挂载/租约/`snapshot` 的语义树结构整体可用，`click_ref` 调按钮（如“取消”）稳定。

## 建议修复优先级

1. **I-01**（正确性）与 **I-02**（安全）——直接影响自动化结论与目标程序完整性。
2. **I-13 / I-08**——决定“不打扰主屏用户”和“长任务可持久”这两个核心承诺能否成立。
3. **I-03 / I-04 / I-05**——决定批量巡检是否可用。
4. **I-06 / I-07 / I-14**——决定表格类任务与批量写操作的上限。
5. 其余按版本节奏处理。
