1. 以真实工程场景检验工具实用性，产出需求级改进意见；
2. 探测能力边界，找出"实际必需但缺失"的能力；

### 阶段 2 · 安装 CCW 23（15:57–16:10，受阻）

1. `launch_or_place_app` 直接启动 `Setup.exe /s` → 报 `E_INTERNAL`，底层 `Win32Exception 740 请求的操作需要提升`。**工具不会触发 UAC**。

3. 又在项目根目录执行 `cmd /c cd /d <DVD> & start "" Setup.exe /Q /IAcceptAllLicenseTerms` 重试，同样 `E_WINDOW_TIMEOUT`，无后续进程。
4. 从 `Setup.exe` 二进制中提取官方命令行说明：`/Q`（全静默）或 `/QS`（无交互但有进度/错误 UI）必须二选一，且必须配 `/IAcceptAllLicenseTerms`；另有 `/IgnoreWarning`、`/SetupLanguage`、`/AutoRestart`。
5. 事实核验：CCW 仍为 12.00.00，`Product.ini` 未更新，`Program Files (x86)\Rockwell Automation` 下 2 小时内无新增文件。
6. 事件日志定位根因：15:58:03 与 15:58:26 两次 CBS 记录 `NetFX3` 按需功能安装失败，`0x800f0912 CBS_E_ONDEMAND_LOCALSOURCE_NOT_FOUND`；本机未安装 .NET Framework 3.5（无 `NDP\v3.5` 键），且无本地安装源。
7. 结论：CCW 23 安装器的前置检查尝试在线启用 NetFx3 失败，导致 Setup 中止；这一步需要管理员权限与安装源，属于环境问题，不是 VSP 工具问题，但暴露了工具无法观测安装进程与安装器窗口（提权）的边界。

**后续**：NetFx3 已由管理员 PowerShell 在线启用（见下文"阶段 2 续三"），安装继续。

### 阶段 2 续（16:00–16:10）

### 阶段 2 续二（16:09–16:13）

- **定位到客户端断连的真正原因**：`%USERPROFILE%\.local\share\opencode\log\opencode.log` 记录
  `mcp transport error server=vscreenpilot error="Received a progress notification for an unknown token: {\"method\":\"notifications/progress\"...}"`。
  即：VSP 在长任务（启动、等待窗口）期间发送 `notifications/progress`，OpenCode 客户端不认识该 token，直接判为传输错误并断开 MCP 连接；重连后本会话的工具注册未刷新，表现为 `No tool named "vscreenpilot_..."`。
- 可用规避：执行 `opencode reload`（会重建 MCP 连接）后工具立即恢复；一次调用后大概率再次掉线。
- 事件日志佐证：16:10:08–09 又完成一轮 Rockwell 组件 MSI 安装（`Controller - Micro800 23.00.00` 等），16:10:13 再次报 `0x800F0912 The payload is missing`，Setup 随即中止。说明安装器确实被执行，只是被 NetFx3 前置挡住。
- 我方 DISM 尝试在 16:03:39 初始化后无后续 CBS 记录，怀疑提权子进程随调用超时被作业对象回收。

### 阶段 2 续三（16:14–16:24）：NetFx3 已就绪

- 用户授权后，用管理员 PowerShell 执行 `Start-Process dism -Verb RunAs -Wait`（`dism /online /enable-feature /featurename:NetFx3 /all /norestart`），退出码 0。
- 核验：注册表 `HKLM\SOFTWARE\Microsoft\NET Framework Setup\NDP\v3.5` → `Install=1, SP=1, Version=3.5.30729.4926`；`C:\Windows\Microsoft.NET\Framework\v3.5` 有 39 个条目。
- 结论：CCW 23 的前置阻塞已解除，可重新发起静默安装。
- 再次确认：MCP 断连后当前轮次的工具清单不会自动刷新，必须新轮次或 `opencode reload` 后新轮次才能拿到可用工具。

- 编译结果：`生成结束 / 生成时间 2.8 秒 / 成功 1 个，失败 0 个`，**0 错误**。

### 任务 4：仿真测试 —— 放弃（用户决定，按缺陷结案）
- 已通过工具栏"启动模拟器"拉起 `Micro800Sim.exe`（VSP 已接管到虚拟屏），电源开启，模拟器 IP `192.168.159.132`，状态"控制器状态: 开"。
- "设备 → 设置连接路径"填入 `192.168.159.132` 与 `AB_VBP-1\192.168.159.132` 后点"下载"，均弹出"连接到设备：连接失败"。
- 根因（注册表核实）：RSLinx Classic 当前只配置了 `AB_ASA`、`SAFEGUARD` 两个驱动；`AB_VBP` 等**驱动未配置**，仿真器没有可用连接路径。
- 配置驱动需要打开 RSLinx 的"配置驱动程序"界面，而 RSLinx 的"连接浏览器"窗口出现在**主屏**（x=560,y=262），超出虚拟屏矩形，VSP 拒绝截图/点击（`E_TARGET_OFFSCREEN`），只能 `PostMessage(WM_CLOSE)` 关闭。
- **结论**：按用户决定，本项作为**工具缺陷**结案（A7/A8），不计为逻辑失败。ST 逻辑本身已通过编译；仿真下载被"第三方配置界面在主屏 + 工具无跨屏操作能力"阻断。
- 若要继续：在 RSLinx 中配置 `AB_VBP`（虚拟背板）驱动后，CCW 的连接路径即可选到仿真器，随后"下载 → 上电 → Data Watch 打点"执行 T1–T5。
- 追加尝试（18:20）：用 `launch_or_place_app` 启动 `RSLINX.EXE`（RSLinx Classic Lite），窗口被成功接管到虚拟屏，工具栏可见 `Configure drivers`；但 UIA 引用随即失效（RSLinx 进程自行退出，`alive=false`），说明同一时刻 CCW 已占用 RSLinx 会话，独立 RSLinx 无法并存。
- 另：把 CCW 托管的"连接浏览器"窗口用 Win32 `MoveWindow` 从主屏 (560,262) 挪到虚拟屏 (2600,120) 后，VSP 立刻可以 `snapshot` 并读到其 UIA 树（证明 A7 的技术障碍只是"窗口位置"而非能力缺失）；该树只列出 `Workstation, MYWINDOWS` 与 `Linx Gateways, Ethernet`，确实没有 AB_VBP，佐证"驱动未配置"的结论。

## 10. 结论（对应 6 项目标的横评）

### 10.1 实用性
- 能独立完成真实交付：解压 4.3GB 安装包、装 CCW 23（约 34 分钟）、建 Micro850 工程、写 ST 并编译通过；
- 全程 444 次调用、错误率 4.28%，除 UAC 与 RSLinx 驱动配置外无需人工点鼠标。

### 10.2 能力边界（实际必需但缺失）
1. 提权启动（A1）——安装器类的第一道门；
2. 进程/安装进度观测（A3）——静默安装期间完全盲飞；
3. 运行期改虚拟屏几何（A4）——只能改配置重启；
4. 自绘树的双击/右键（A6）——CCW 变量表因此差点打不开；
5. 跨屏窗口（A7/A8）——第三方弹窗落到主屏即失去操作能力。

### 10.3 易用性 / 稳定性 / 性能
- 易用性：标准控件上体验很好（`click_ref`/`set_element_value`/`snapshot` 语义清晰，`E_DESTRUCTIVE_REQUIRED` 提示到位）；但错误码粒度不够（`E_INTERNAL` 掩盖真实原因），长任务无进度。
- 稳定性：最大问题是 MCP 连接因 `notifications/progress` 反复断开（C1），需 `opencode reload` + 新回合恢复；其次是启动超时杀进程树 + 作业对象 `KILL_ON_JOB_CLOSE` + daemon 空闲 5 秒退出共同导致的子进程消失（C2，代码复核后已明确机制）。
- 性能：截图 12–100 ms、语义树 150–1500 ms；瓶颈在窗口/输入时序，"输入丢字"需要二次补字，实际调用量被放大 2–3 倍。

### 10.4 冗余/绕弯设计
- `launch_or_place_app` 把"启动"与"摆放"耦合：目标不可摆放（提权、控制台）时连启动都失败；
- 分辨率能力已具备（VDD 动态挂载）却没有 `set_display` 入口；
- 进度通知只在客户端给了 `progressToken` 时发送，但客户端无法关联自己给出的 token，属于"有机制、无合同"；触发点是 `wait_for` 的高频轮询与 `type_text` 的逐块上报，不是"启动/等待窗口"本身。

### 10.5 对用户的实际影响
- 虚拟屏独立挂载，正常操作不抢主屏鼠标；
- 三类干扰真实存在：①挂载/卸载黑屏；②焦点护栏导致按键被吞（同时是输入不稳的根因）；③提权窗口与第三方弹窗落在主屏，遮挡用户且工具无法接管。

### 10.6 总评
"通用、尽量不打扰"的定位成立，标准控件场景已可用；但要让"安装→配置→仿真"这类工控闭环真正无人值守，必须补齐：提权启动、进程观测、自绘控件双击/右键、跨屏窗口处理、长任务进度。这五项补齐后，本次任务 4 的阻塞即可消除。

复核方法：以已安装的 0.3.0（commit `db0d7bc`）为基线，对照仓库 `src` 实现；工作区另有 58 个未提交文件（0.3.1-dev），单独标注。复核只读代码，不改变前文的实测记录。

### 11.2 关键修正

1. **C1 归因**：服务端只在客户端提供 `progressToken` 时才发 `notifications/progress`，并非"擅自发送"；真正的触发点是 `wait_for`（每 100–500ms）与 `type_text`（每块），不是启动/等待窗口。修复方向仍是"默认关闭、可显式开启"。
2. **C2 机制**：不是"疑似作业对象回收"这么模糊。代码保证三条会杀掉子进程的路径：①启动等待窗口超时后显式 `KillProcessTree`；②`JobObject` 设置 `KILL_ON_JOB_CLOSE`；③daemon 在最后一个客户端断开后默认 5 秒退出，退出即关闭作业对象，连带杀掉本会话启动的应用。提权子进程只是其中一种受害者。
3. **A6 细分**：右键路径只发 `WM_RBUTTONDOWN/UP`，从不发 `WM_CONTEXTMENU`，这是自绘树弹不出菜单的直接原因；双击在 API 层是支持的（消息通道发 `WM_LBUTTONDBLCLK`，input 通道两次点击间隔 50ms），"双击无效"证据不足，更可能是该控件/坐标问题。
4. **A2 风险被低估**：不只是"控制台窗口跟踪不到"，超时路径会杀掉已启动的进程树，对安装器/长任务有实际破坏性。
5. **B3 / F1 不成立**：B3 是应用行为（报告自己也承认）；F1 的描述与代码不符——`VSP_DISPLAY_WIDTH/HEIGHT` 的范围 800–3840 已在帮助文本中写明，1280×720 只是默认值。
6. **数据一致性**：§10.1 原写"386 次 / 3.63%"，与 §9 的 444 次 / 4.28% 冲突，已按最终指标统一。

### 11.3 复核时已存在但当时未部署的修复（已在 §12 部署）

### 12.4 使用建议（与工具改动配套）

1. 一个窗口状态只 `snapshot` 一次，后续用 ref；只有树/窗口变化才重拍。
2. 同步用 `wait_for`（text/element/window/process），不要用截图轮询。
3. 菜单用 `press_keys(sequence=…)` 或 `invoke_element(select_text=…)`；自绘网格用 `type_text(chunk_chars=1, pace_ms=15, verify=false)`，写完用 `get_element_text` 回读；代码会在小 chunk 时自动把校验间隔拉到 10 块，但关掉 verify 更快。
4. 第三方弹窗先 `list_windows(scope="unmanaged")` 拿 hwnd，再 `launch_or_place_app(hwnd=…)`。
5. 安装器/控制台交给宿主提权；MCP 只负责有窗口的 GUI，启动后用 `get_processes`/`wait_for` 观察。无窗口时默认 `on_no_window=leave`，不会随 daemon 退出被杀；要清理传 `kill`。
6. `set_display` 会独占会话锁并重排跑出屏的受管窗口；改完几何先看一眼 `repositioned`。

### 12.5 第二轮修复（静态复查后）

1. `set_display` 改为会话写锁（`sessionWrite + bypassWriteLock`），避免与 `capture_screen`/`snapshot` 并发撕裂；`Resize` 增加失败回滚、位置被忽略时置 `PositionFallback`、以及 `reposition` 重排窗口。
2. `get_processes` 改为一次枚举窗口并按 pid 建表，`include_windows` 默认 false，`elevated` 按 pid 缓存；无过滤调用实测 48–64ms。
3. 小窗口不再 450ms 就接管：先等最多 3 秒看有没有更大的主窗口，超时才接受当前小窗，避免把 splash 当主窗口。
4. 无窗口进程不再提前加入作业对象：`on_no_window=leave` 时 daemon 退出也不会杀；`kill` 时显式终止。控制台程序 1.2 秒判定无窗口，不再等满 `wait_ms`。
5. `type_text` 在 `chunk_chars<=4` 时自动把回读间隔提高到 10 块；`pace_ms` 不在最后一块空等。
6. `launch_or_place_app(hwnd=…)` 只接受顶层窗口；`click(context_menu=true)` 只允许 `button=right`。
7. `list_windows` 只认本会话的虚拟屏设备，`elevated` 按 pid 缓存，新增 `total`；`wait_for(type=process)` 不再挂载虚拟屏。
8. 文档同步：daemon 空闲默认 5000→300000，补 `VSP_PROGRESS`/`VSP_REF_GENERATIONS`。
9. `launch_or_place_app` 只有确实拿到窗口才挂载虚拟屏；纯控制台/启动器不会为了执行一条命令把屏挂起来（实测 `cmd` 启动前后 `virtual_display.enabled` 均为 false）。

实测补充：把 Notepad 移到主屏后 `set_display(1600×900, reposition=true)` 返回 `repositioned=1`，窗口被挪回虚拟屏且保留原尺寸；`set_display(1234×777)` 返回 `E_DISPLAY_MODE`，几何保持 1920×1080，说明回滚生效。控制台无窗口（`cmd /c ping`）1.26 秒返回，客户端退出后进程仍存活；`on_no_window=kill` 立即终止。
