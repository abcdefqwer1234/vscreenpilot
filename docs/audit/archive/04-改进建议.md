# VScreenPilot 改进建议

> 依据：[01-静态审查报告](01-静态审查报告.md)、[03-实际测试报告-Word.md](03-实际测试报告-Word.md)
> 范围：只给可落地的修复方案与验证方法，不修改生产代码（本轮仅用临时补丁构建做对照实验）。

---

## 0. 结论先行

VScreenPilot 的**架构和工具设计明显好于实现细节**。动态测试确认了三类问题：

1. **两个会直接阻断 AI 使用的问题**（P0）：`mode=input` 坐标错误、全屏截图在连续调用后跌到 ~1.9s；
2. **一组“能用但会误导调用方”的契约问题**（P1）：参数类型不校验、错误码退化成 `E_INTERNAL`、baseline 跨区域复用、UWP/多标签应用不可接管；
3. **可观测性与兜底能力不足**（P1/P2）：作业对象绑定失败率 85%、`adopted_orphan` 永远为 false、`run_script` 中文乱码。

建议按 P0 → P1 → P2 顺序修，每项都给出可复现的验收用例（可直接复用 `tools/audit/` 脚本）。

## 1. P0：必须先修

### P0-1 `mode=input` 缺少 `MOUSEEVENTF_VIRTUALDESK`

**证据**：`src/VScreenPilot.Server/Input/InputInjector.cs:250-265`，`AbsoluteMoveInput` 用整个虚拟桌面做归一化，却只传 `MOUSEEVENTF_MOVE | MOUSEEVENTF_ABSOLUTE`。
**实测**：`tools/audit/verify_virtualdesk.py` —— 原始构建点击虚拟屏 `(2240,240)`，ClickProbe 记录到的屏幕坐标落在主屏；补丁构建（加 `0x4000`）落点误差 ≤2px。详见测试报告第 8 节。

**修复**：

```csharp
// Interop/NativeMethods.cs
internal const uint MouseVirtualDesk = 0x4000;

// Input/InputInjector.cs
NativeMethods.MouseMove | NativeMethods.MouseAbsolute | NativeMethods.MouseVirtualDesk
```

同时：

- `AbsoluteMoveInput` 应基于 `GetSystemMetrics(SM_XVIRTUALSCREEN/SM_CXVIRTUALSCREEN)` 的**物理像素**计算，并在 DPI 变化后重建缓存；
- 为 `gesture`/`click(mode=input)` 增加同一坐标对照用例，纳入 CI（不需要真实 GUI，ClickProbe 即可）。

**验收**：`python tools/audit/verify_virtualdesk.py --original <old> --patched <new>` 两项都通过；`mode=message` 不受影响。

### P0-2 全屏截图性能悬崖（累计截图后 ~1.9s/次）

**证据**：`bench_perf.py` 200 次 `capture_screen`：前 20 次 60–100ms，第 24 次起稳定在 1.7–2.1s；同会话内 `capture_screen(region=320x180)` 始终 30–35ms；`encode_ms` 仅 20–70ms。说明瓶颈在 `ScreenCapture.Capture` 的 GDI 路径，而不是 PNG 编码。
**补充表征（run2）**：干净会话第 19 次起变慢；先做 200 次区域截图后，全屏第一次就已是 1.9s——触发与累计截图/时间相关，不是严格的第 24 次；120 次全屏后 RSS 峰值 418MB。
**对照**：用同样的 GDI 代码在主屏 1920×1440 连续抓 40 次，稳定在 **45–76ms**，无悬崖。说明这是 **Parsec IDD + 全屏 GDI 回读** 的组合问题，不是 DWM/GDI 普遍问题。
**代码**：`Perception/ScreenCapture.cs` 每次调用都 `CreateCompatibleDC` + `CreateDIBSection(3.7MB)` + 全屏 `BitBlt(SRCCOPY|CAPTUREBLT)` + `Marshal.Copy`，无复用、无限流。

**修复方向（按推荐顺序）**：

1. **复用 GDI 资源**：进程内缓存 `screenDC / memoryDC / DIB`，只在尺寸变化时重建；`BitBlt` 去掉 `CAPTUREBLT`（除非确实需要分层窗口）。
2. **改 DXGI Desktop Duplication**（Parsec VDD 是 IDD，支持 DXGI）：一次初始化，按帧 `AcquireNextFrame` + GPU 回读；比 GDI 稳定。
3. **加降级与限流**：连续截图间隔 <50ms 时合并请求；检测到单次 >500ms 时记录一次 `WARN` 并在 `capture_screen.meta` 返回 `slow_capture=true`，避免 AI 端误以为工具挂死。
4. 提供 `capture_screen.cached=true`：屏幕未变化时复用上一帧（可用 `GetUpdateRect`/帧序号判断）。

**验收**：新增 `bench_perf.py --shots 500`，要求 P95 ≤ 50ms、无单调上升；在物理屏与 VDD 各跑一次。

### P0-3 作业对象绑定失败（崩溃兜底失效）

**证据**：服务端日志 62 次接管里 53 次出现“未能加入作业对象，崩溃兜底不可用”（85%）。这是 `REG-10` 的动态证据。
**影响**：服务端崩溃/被杀时，`release_environment` 不会执行，应用窗口可能残留在虚拟屏；只能靠 `--parent-pid` 或人工清理。

**修复**：

- 在**创建子进程前**创建 Job（`CreateJobObject` + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`），用 `STARTUPINFO`/`AssignProcessToJobObject` 绑定；
- 若父进程已在 Job 中（OpenCode/VSCode 常见），用 `CREATE_BREAKAWAY_FROM_JOB`；失败时尝试 `IsProcessInJob` 判断并降级为“记录 PID + 退出时按 PID 树清理”；
- 把结果写入 `get_environment.session.job_object`（`assigned|unavailable|not_supported`），让调用方知道兜底是否有效；
- 绑定失败必须 `WARN` 且**只记录一次**，避免日志刷屏（当前 53 行）。

**验收**：`bench_stability.py` 的 `residual` 在强杀服务端后仍为 0 进程；日志中 `job_object=assigned`。

## 2. P1：会误导 AI、造成隐性失败

### P1-1 参数类型不校验（静默忽略/误用）

**证据**：

- `launch_or_place_app.args` schema 是 `string`；传数组时被静默忽略（GUI-01 首次失败的直接原因）。
- `pid:"123"`、`max_nodes:"abc"` 返回 `E_INTERNAL`；`find_element.name=123` 被接受。
- `new_instance:"false"`（字符串）被当作真值。
- `capture_screen.scale=0/10`、`get_log.level="nonsense"` 被接受。

**修复**：

- 所有工具入口统一走 `JsonSchema` 校验（`JsonNode` → 强类型 + 错误码 `E_INVALID_ARG`，附 `field/expected/actual`）；
- `args` 改 `oneOf: [string, array]`，数组时逐项 quoting；文档给示例；
- 数值参数在 schema 中写 `minimum/maximum`，服务端再钳制一次并返回 `clamped` 字段（比静默接受更诚实）。

**验收**：`bench_regressions.py` 的 REG-03/REG-08/REG-13/REG-18 全部返回 `E_INVALID_ARG`。

### P1-2 错误码退化：`E_INTERNAL` 吞掉可操作信息

**证据**：`pid:"123"`、`assert_region` 非法 region、`invoke_element` 目标退出，都会返回 `E_INTERNAL` + `AggregateException`。GUI-04/08 中 `invoke_element` 抛 `0x80070003`，随后目标应用消失，后续所有用例 `E_NO_TARGET`（连锁失败）。

**修复**：

- 在 `McpServer` 的工具分发外层把 `AggregateException` 拆到 `InnerException`，映射为 `E_UIA_FAILED` / `E_APP_GONE` / `E_INVALID_ARG`；
- `invoke_element` 捕获 UIA COM 异常后先探测窗口/进程是否存活，再决定错误码；
- 错误响应统一包含 `stage`、`target`、`retryable`、`hint`（目前部分工具有，部分没有）。

**验收**：构造“目标进程被杀后 invoke”场景，期望 `E_APP_GONE` 且 `hint` 指向 `launch_or_place_app`。

### P1-3 `baseline_frame_id` 跨区域静默复用

**证据**：`SEC-09b`：先截 `(1940,20,120,90)` 得到 `f23`，再对 `(2240,220,120,90)` 用同一 baseline 断言，返回 `passed=false`、`changed_ratio=0.3825`，并在响应里显示 baseline 仍是 `(1940,20)`。也就是说它**没有拒绝区域不一致**，而是拿另一块区域的像素做了比较。

**修复**：`FindFrame` 后校验 `x/y/width/height` 与请求区域一致，不一致返回 `E_NO_BASELINE`（附 `baseline.region` 与 `requested.region`）；`baseline=last_same_region` 已有该语义，`baseline_frame_id` 也必须一致。

**验收**：`verify` 用例同区域通过、跨区域 `E_NO_BASELINE`。

### P1-4 `launch_or_place_app` 对单实例/多标签与 UWP 不可靠

**证据**：

- Windows 11 Notepad（11.2609）是单进程多标签：连续 launch 会复用旧实例，`args` 被丢弃（标题“记事本”），`type_text.verified=false`，`Ctrl+S` 静默无动作（文件 0 字节）。留下的“另存为”模态框会让下一会话的 `invoke_element` 失败。
- Calculator（UWP，宿主 `ApplicationFrameHost`）：`launch_or_place_app {window:"计算器"}` 返回 `E_WINDOW_NOT_FOUND`；`find_element` 也无法命中。

**修复**：

- `launch_or_place_app` 增加 `pid` 参数（按进程接管）；对 UWP 解析 `ApplicationFrameHost` 的子窗口/`CoreWindow`；
- 对已知单实例应用（Notepad/Explorer/Office）默认“新建标签/文档”，并在返回里给 `reused=true` 与 `hint`；
- 启动后检测**模态对话框**（`#32770` / `Dialog` 控件），在 `launch` 结果里返回 `dialogs[]`；`release_environment` 关闭本会话创建的对话框；
- `type_text` 的 `verified=false` 应升级为明确错误或 `warning` 字段（目前只有 `warning`，AI 容易忽略）。

**验收**：新增 `GUI-16`：连续 3 次启动 Notepad 并写入不同文件，每次 `verified=true` 且文件 oracle 正确。

### P1-5 系统键变体漏拦截

**证据**：`SEC-03`/`REG-07`：`Alt+Shift+Tab`、`Ctrl+Alt+Tab` 返回 `E_NO_TARGET`（因为没有目标窗口），而不是 `E_SYSTEM_KEY_BLOCKED`；一旦有目标窗口，它们可能真的发到系统。

**修复**：把按键黑名单校验移到“目标解析”之前；黑名单补齐 `Alt+Shift+Tab`、`Ctrl+Alt+Tab`、`Win+Ctrl+*`、`Alt+Esc`、`Ctrl+Shift+Esc` 的变体（大小写/顺序归一化后再匹配）。

**验收**：无目标窗口时也返回 `E_SYSTEM_KEY_BLOCKED`；`allow_system_keys=true` 时行为不变。

### P1-6 视觉断言的非法阈值被接受

**证据**：`coverage=1.5`、`coverage=-0.5`、`threshold=-1`、`threshold=2` 均执行；`coverage=-0.5` 恒真，`threshold=2` 恒假。

**修复**：`coverage ∈ [0,1]`、`threshold ∈ [0,1]`，越界 `E_INVALID_ARG`；响应里区分“阈值”和“实际覆盖率”（已有 `coverage_semantics`，保留）。

### P1-7 `run_script` 中文输出乱码

**证据**：`REG-09`：返回 `stdout` 为 `\uFFFD...OK\r\ngb2312`，即服务端按 UTF-8 解码了 GBK 输出。

**修复**：脚本前缀设置 `[Console]::OutputEncoding=[Text.Encoding]::UTF8; $OutputEncoding=[Text.Encoding]::UTF8`，或按 `chcp`/`$OutputEncoding` 选择编码；响应加 `encoding` 字段。

**验收**：`REG-09` 通过，中文与 emoji 均正确。

### P1-8 安全桌面/UAC 之后输入与截图永久失能
**证据**：15 分钟 soak 中，第 107 次迭代（与一次 UAC 安全桌面事件重合）起，`capture_screen` 持续 `E_INTERNAL`、`type_text` 持续 `E_NO_INTERACTIVE_DESKTOP`，直到结束（538 次），**没有恢复**。
**影响**：用户点一次 UAC、锁屏或切换安全桌面，AI 会话就报废；而错误提示只说明“没有交互桌面”，不告诉调用方如何恢复。

**修复**：

- 检测到 `OpenInputDesktop` 失败时，区分 `secure_desktop`（当前是 Winlogon/UAC）与 `session_disconnected`；前者可等待并重试（例如 2s 后指数退避，最多 30s），后者提示需要用户登录；
- `get_environment` 增加 `session.input_desktop` 与 `last_desktop_error`；
- 恢复后重建 `ScreenCapture` 的 DC/DIB 缓存；
- `capture_screen` 在该状态下返回 `E_NO_INTERACTIVE_DESKTOP`（与输入工具一致），不要用 `E_INTERNAL`。

**验收**：人工触发一次 UAC 后，等待安全桌面关闭，`capture_screen` 与 `type_text` 在 ≤5s 内恢复。

### P1-9 非标准模态对话框不可达（Word 实测阻断）

**证据**：Word 的“查找和替换”是 `bosa_sdm_msword` 顶层窗口（owner=主窗口），**不在 UIA 树**；`find_element`/`get_ui_tree` 看不到，`type_text` 偶尔落入正文、偶尔无效果，行为不稳定。相反，Notepad 的“另存为”（经典 `#32770`）**在 UIA 树中可达**。说明问题集中在 Word 这类自绘/非标准对话框，而不是所有模态框。

同时，Word 在 AutoSave 开启时 `Ctrl+S` **不弹保存框**，直接写 OneDrive；`release_environment` 在有未保存内容时返回“未找到保存对话框”。

**修复**：

1. 接管应用时枚举其 **owned windows**（`GetWindow(GW_OWNER/GW_ENABLEDPOPUP)`），无论 UIA 是否暴露都加入会话；
2. `find_element`/`get_ui_tree` 默认覆盖“主窗口 + 当前活动弹窗”，返回 `window` 字段；
3. `type_text`/`press_keys` 以**当前前台窗口**为目标；对“输入成功但目标不在正文”的情况给 `E_TARGET_MISMATCH` 而不是 ok；
4. 提供 `list_dialogs` / `dismiss_dialog`，或在 `launch_or_place_app` 返回 `dialogs[]`；
5. `release_environment` 把“未识别的保存对话框”当成明确错误，而不是仅 warn。

**验收**：Word 查找替换/另存为可纯 MCP 完成；Notepad 另存为不回归；`release` 不再出现“未找到保存对话框”。

### P1-10 保存路径语义与 AutoSave 陷阱

**证据**：

- `capture_screen.save_path` 传相对路径时按**服务端 cwd**（`artifacts/server`）落盘，文件不在客户端预期位置；
- Word 的现代保存框**不接受完整路径**（保存按钮变灰），只接受文件名；
- Word 默认 AutoSave 到 `OneDrive - 个人`，而 OneDrive 客户端未运行：标题显示“已保存”，本地却找不到文件。

**修复**：

- 所有 `save_path` 强制解析为绝对路径并在响应里回显；
- 提供 `save_file`/`assert_file` 工具（或文档化的“文件名 + 目录”两步式）；
- 检测“云占位”路径（OneDrive/Dropbox）并提示 `saved_to_cloud`，避免 AI 误判成功。

**验收**：`capture_screen(save_path="rel.png")` 的文件落在客户端 cwd；Word 保存后 `assert_file` 能读到本地文件。

### P1-11 长任务期间 GUI 工具 5s 后返回 `E_BUSY`

**证据**：CONC-03：`wait_for` 活跃时，并发 `get_ui_tree` 等待约 **5018ms** 后返回 `E_BUSY`；`wait_for` 结束/取消后同一调用立即成功。8/16 线程短调用无失败。

**影响**：AI 在等待元素期间调用其他 GUI 工具会失败，若不会重试就会误判“应用没反应”。

**修复**：

- `E_BUSY` 响应增加 `retry_after_ms` 与 `holder`（哪个工具持有闸门）；
- 对只读工具（`get_environment`/`get_log`/区域截图）允许绕过闸门（本轮实测 `get_environment` 已可绕过）；
- 文档明确“长任务期间并发 GUI 工具会失败”，并给出重试范式。

**验收**：`bench_concurrency.py` 中 `wait_for` 期间 `get_ui_tree` 返回可重试错误，且按 `retry_after_ms` 重试后成功。

| P2-2 | `adopted_orphan` 永远 false（`_adoptedOrphan` 无赋值点），但日志确实发生了接管 | 在接管分支置位，并在 `get_environment` 暴露 `adopted_from_pid/at` |
| P2-3 | 重复 JSON-RPC `id` 被正常响应两次 | 维护 `seenIds`（有界 LRU），重复返回 `-32600` |
| P2-4 | `progress` 只在 `wait_for` 里发；截图/建树/模板匹配没有进度 | 对 >1s 的操作按 100–250ms 发 `notifications/progress` |
| P2-5 | `get_ui_tree` 无 progress、`max_nodes` 截断信息不足 | 返回 `truncated_at`、`dropped_children`，并在 hint 里建议 `root` 裁剪 |
| P2-6 | `find_element.all` 的 `count` 语义不稳定 | 统一 `count/matches[]`，与 `all=false` 时字段一致 |
| P2-7 | Windows 11 Notepad 的 `Ctrl+S` 无反馈 | 提供 `save_file`/`assert_file` 辅助工具（或文档化的 oracle 流程） |
| P2-8 | 单实例互斥导致无法并行跑两个客户端（测试/多 agent 场景） | 文档写清；或提供 `--session <name>` 让不同 profile 并行（需重新评估驱动/光标护栏） |
| P2-9 | 日志出现 53 次“未能加入作业对象”，无聚合 | 只记录一次 + `get_environment` 暴露状态 |
| P2-10 | 长文本 `type_text`（2600 字符）9.8s 且 `verified=false`，无分段进度 | 返回 `chunks_verified/typed`，失败时给 `E_VERIFY_FAILED` 而不是仅 `warning` |
| P2-11 | `capture_screen.save_path` 传相对路径时按**服务端 cwd**（`artifacts/server`）落盘，返回成功但文件不在客户端预期位置 | 相对路径明确相对“工作目录”并在 `meta.path` 返回绝对路径；或只接受绝对路径 |
| P2-12 | 作业对象失败不记录 `GetLastWin32Error`，无法定位是嵌套 Job 还是权限 | 记录 Win32 错误码与 `IsProcessInJob` 状态；必要时提供 `--no-job` 开关 |
| P2-13 | 外部摘屏会触发自动重挂，但 `get_environment` 不暴露“刚发生过重挂” | 返回 `display_recreate_count`/`last_recreate_reason`，便于 AI 判断画面是否重置 |
| P2-14 | 120 次全屏截图后 RSS 峰值 418MB（基线 89MB），释放后回落 | 复用 DIB/限制帧缓存；在 `capture_screen.meta` 返回 `rss_mb` 便于监控 |

## 4. 兼容性建议（按目标应用）

| 应用类型 | 现状 | 建议 |
| --- | --- | --- |
| Win32/WinForms/WPF | 可用（UiTarget 全流程通过） | 保持；补 `pid` 接管与对话框检测 |
| Windows 11 Notepad（单实例多标签） | 不稳定（args 丢失、Ctrl+S 无动作） | 强制新实例/新标签；文件 oracle 校验 |
| UWP/Store（Calculator） | 不可接管 | AppFrameHost 解析 + `pid` 接管 |
| Chromium/CefSharp（CCW 12） | 消息注入被拒绝，UIA 仅 `Custom` | 增加 CDP 通道（Electron/CEF 可开 `--remote-debugging-port`）或 `IAccessible2`；至少提供 `E_CHROMIUM_UNSUPPORTED` 与可行替代路径提示 |
| Office / Word | **半自动可用**：启动、输入、格式、表格、本地保存、多应用、长文本通过；查找替换/另存为因模态对话框失败 | 优先修 P1-9；补 `role=document_body` 分页合并（Word 每页一个 Body，`count=2`） |

> CCW 12 的阻断属于**应用不兼容 + 工具缺少 Chromium 兜底**的叠加，不能简单归因于 VScreenPilot 缺陷；但“只返回 E_INPUT_UNSUPPORTED，没有下一步”是工具侧可改进的体验问题。

## 5. 工程与交付建议

1. **CI**：把 `tools/audit/bench_protocol.py`、`bench_regressions.py`、`verify_virtualdesk.py` 接入 CI（无 GUI 的 PRT/SEC 部分可跑在 Windows runner；GUI/驱动部分 nightly）。
2. **基准看板**：把 `bench_perf.py` 的 P50/P95、截图悬崖阈值、RSS/句柄写入 `docs/bench/`，每次 release 对比。
3. **错误码目录**：`docs/errors.md` 列出所有 `E_*`、触发条件、可操作下一步；工具描述里直接引用。
4. **版本与发布**：当前 `0.1.0` + 80.7MB self-contained；建议提供 `framework-dependent` 小包（~10MB）与 `--version --json`，并在 README 写明 Parsec VDD 0.41/0.45 差异。
5. **文档**：补“AI 使用范式”（何时 `mode=input`、何时 `pid`、release 时机、截图/树裁剪），这些正是本轮 AI 直接调用时最容易踩的坑。
6. **测试隔离**：在 README 明确“单实例互斥 + 共享桌面”，避免用户同时开两个会话；测试脚本默认 `VSP_NO_INPUT=1`。
