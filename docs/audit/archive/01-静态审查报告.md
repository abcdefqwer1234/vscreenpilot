## 1. 执行摘要

VScreenPilot 的核心思路是：把 Windows 桌面应用放到一块按需挂载的 Parsec 虚拟显示器上，让 AI 通过 MCP 工具完成截图、语义定位、输入和验证，同时不干扰用户物理桌面。这个隔离层在同类开源项目中很少见，是本工程最有价值的设计。

静态审查发现的主要问题不是“代码写得乱”，而是“工程化外围不足 + 少数关键路径有硬缺陷”：

1. **P0 输入坐标缺陷**：`click/gesture mode=input` 的绝对鼠标坐标缺少 `MOUSEEVENTF_VIRTUALDESK`，Windows 会把坐标映射到主屏，而不是右侧虚拟屏。CefSharp/ag-grid 恰好只能依赖 `mode=input`，因此 CCW 场景可能在第一步点击就失败。
2. **P0 兼容性缺口**：CCW 的 WebView/ag-grid 在 UIA 中只是 `Custom` 容器；窗口消息注入又被 `MessageInput.IsInputHostile` 主动拒绝；工程没有 CDP/IAccessible2/OCR 兜底。目标场景缺少可靠的语义或点击通道。
3. **P1 并发与生命周期缺陷**：UIA 调用没有完全串行化；`get_environment` 又旁路工具闸门；EOF/Dispose 可能被卡死的 UIA 或 `_gate` 阻塞；`release_environment` 可以在超时后旁路清理，与旧 handler 竞态。
4. **P1 正确性缺陷**：`get_ui_tree` 最大 2000 节点，但 element_ref 容量只有 1024；显式 `baseline_frame_id` 不校验 x/y；非法 `control_type` 被静默忽略。
5. **P2 成熟度缺口**：没有 CI、没有单元测试、没有发布产物/registry release、npm 未发布、没有 `global.json`、没有英文文档和社区治理文件；MCP 的 `outputSchema` 全部是泛化的 `{"type":"object"}`，也没有速率限制/访问控制。

第二轮逐文件复核又补充了 18 项可静态确认的缺陷/风险（见 8.13）；其中多数是 P1/P2 外围与兼容性问题，不改变“主干设计强、外围不成熟”的结论。综合评分仍约 **65/100**：属于“设计良好的准生产原型”，不是“成熟 MCP 项目”。

## 4. 架构与代码质量

### 4.1 优点

1. **职责分层清楚**：Core 只做 VDD/显示拓扑，Server 做会话、MCP、UIA、输入、感知；没有把 Win32 细节散落到工具层。
2. **契约意识强**：`ToolException` 统一错误码；`ToolResponse` 同时给 text 和 structuredContent；工具描述明确写了限制和回退方式。
3. **生命周期设计完整**：互斥体、Job Object、孤儿屏接管、state.json、心跳、焦点/光标护栏，覆盖了“准备—运行—清理—崩溃恢复”。
4. **安全默认值合理**：`run_script` 默认关闭；越界坐标拒绝；落点必须是 tracked 窗口；输入前强制切前台；覆盖非空内容需要 `allow_destructive`；系统键默认拒绝。
5. **UIA 工程化**：缓存请求、树裁剪、时间/节点预算、runtime_id + 指纹重定位、UIA2 连接/事务超时、按 pid 熔断。
6. **感知层自研且克制**：GDI 内存截图、纯托管 PNG、灰度金字塔 + 早期退出 SAD、4 连通域，没有引入 OpenCV/System.Drawing 等重依赖。
7. **文档质量高**：README 面向使用者，技术文档面向维护者，需求文件面向契约；错误码表较完整。

### 4.2 结构性不足

1. **手写 MCP 协议**：没有使用官方 C# SDK，协议演进、分帧、错误码、能力协商都要自己维护；当前只覆盖 tools，没有 resources/prompts/completions 的实际能力。
2. **手写 UIA COM 封装**：没有采用 FlaUI 这类成熟封装，线程模型、UIA2/UIA3 回退、元素缓存、COM 释放都要自己保证；当前已经出现并发与超时边界问题。
3. **单闸门串行化**：所有 GUI 工具串行，简单可靠，但截图/UIA/输入无法并行；长工具会阻塞后续调用，靠 `release_environment` 旁路恢复。
4. **没有可注入的时钟/取消抽象**：大量 `Thread.Sleep`、`Task.Wait`、`DateTime.UtcNow` 直接写在业务里，单元测试困难。
5. **没有单元测试工程**：README 自己承认 PNG/KeyMap/region/ref 注册/协议分帧没有纯单元测试覆盖。

## 5. MCP 协议符合性

### 5.1 已实现且基本正确的部分

- `initialize`：协商 2025-06-18 / 2025-03-26 / 2024-11-05；未知版本回退到最新支持版本（`McpServer.cs:299-348`）。
- `tools/list`：按名称排序、稳定输出、18 个工具、inputSchema（`McpServer.cs:53-71`、`713-790`）。
- `tools/call`：参数对象、未知工具、重复 id、后台执行、超时、取消、progress（`McpServer.cs:350-540`）。
- `ping`、`notifications/initialized`、`notifications/cancelled`、`resources/list`、`prompts/list`、`logging/setLevel`。
- 工具执行错误通过 `isError: true` 返回，错误体包含 `code/message/retryable/hint/stage`（`ToolResponse.cs:57-103`）。
- 图片通过 MCP image content 返回，`capture_screen` 同时返回 meta 和 PNG（`ToolResponse.cs:105-114`）。
- 输出编码 UTF-8 无 BOM，stdout 只写 JSON-RPC，日志走文件/内存（`McpServer.cs:115-123`、`695-711`）。

### 5.2 与规范的差距

| 项 | 现状 | 影响 |
| --- | --- | --- |
| `outputSchema` | 所有工具统一 `{"type":"object"}`（`McpServer.cs:60-62`） | 客户端无法做有意义的 schema 校验；与规范“提供 output schema 时应提供符合 schema 的结构化结果”的精神不符 |
| 错误分类 | 很多无效参数以 `isError` 工具错误返回，而不是 JSON-RPC `-32602` | 客户端无法在协议层区分“参数错误”和“工具执行失败” |
| `title` | 工具定义没有 `title` | 客户端展示不友好；非阻断 |
| `idempotentHint` | annotations 只设置了 readOnly/destructive/openWorld | 客户端无法判断重试安全性 |
| 分页 | `tools/list` 不支持 cursor | 18 个工具暂时无影响；扩展后会暴露 |
| 速率限制 | 没有 | MCP 规范安全建议要求服务器实施访问控制/速率限制；本地 stdio 可接受，但不算成熟 |
| 传输 | 仅 stdio | 没有 HTTP/SSE、没有认证/TLS；Windows-MCP 已支持三种传输 |
| 日志通知 | `logging/setLevel` 返回成功但不真正改变级别，也不发 `notifications/message` | 客户端以为日志级别生效，实际没有 |
| 资源/提示 | 返回空列表，但未声明 resources/prompts 能力 | 客户端一般不会调用；不影响核心 |

### 5.3 并发与取消

- 工具闸门是 `SemaphoreSlim(1,1)`；非优先工具等待 5s，优先工具等待 2s；`get_log`/`get_environment` 完全旁路（`McpServer.cs:34`、`410-446`、`603-606`）。
- 超时后 `TrackStalled` 把闸门交给 handler 的延续任务释放；`release_environment` 完成后 `ResetToolGate` 换新闸门（`McpServer.cs:487-548`、`570-601`）。
- 取消通过 `notifications/cancelled` 找到 `_activeCalls` 中的 CTS；但 UIA COM 调用本身不会被打断，只能等它返回或超时。
- 这套机制“能恢复”，但不是“能并发”；对单用户 GUI 自动化是合理取舍，对吞吐量是限制。

### 6.2 安全缺口与风险

1. **没有速率限制**：Agent 可以无限循环截图/点击；GUI 闸门只保证串行，不限制频率。
2. **没有访问控制/认证**：本地 stdio 由宿主进程信任；如果未来加 HTTP，需要认证/TLS。
3. **`run_script` 是任意 PowerShell**：默认关闭、无沙箱；启用后风险由使用者承担。文档已明确，但这是高风险工具。
4. **`VSP_APP_ALLOWLIST` 不覆盖窗口接管**：按标题接管用户已开窗口不受白名单限制，可能移动/关闭用户窗口。文档已说明，但模型可能误用。
5. **`state.json` 保存窗口标题**：`StateStore.Save` 把 `Title` 落盘（`StateStore.cs:96-128`），与“不泄露用户窗口标题”的隐私口径不完全一致；本地文件仍可能包含敏感标题。
6. **路径限制不是沙箱**：`ValidatePngPath` 允许工作目录/临时目录下的任意 `.png`，不解析符号链接；本地可信场景可接受。
7. **大输入没有行长度上限**：`McpServer.Run` 用 `ReadLine` 读 JSON-RPC；恶意/失控客户端可发超大 base64/文本，造成内存峰值。工具层各自有上限，但协议层没有。
8. **没有审计事件**：日志有工具耗时和错误码，但没有请求 id/调用者/参数摘要，难以做安全审计。

## 7. 感知与输入审查

### 7.1 截图与 PNG

- `ScreenCapture` 使用 `GetDC(NULL)` + `CreateDIBSection` + `BitBlt(SRCCOPY|CAPTUREBLT)`，内存级，不落盘（`ScreenCapture.cs:64-140`）。适合 1280×720 级别。
- `PngWriter` 纯托管 RGBA8、filter=None、`CompressionLevel.Fastest`；1:1 时省一份中间缓冲，缩放时用 box filter（`PngWriter.cs:15-142`）。
- `PngReader` 限制 16M 像素、8bit、非隔行、不支持调色板（`PngReader.cs:23`、`96-119`）。
- 截图帧注册表最多 16 张/64MB，按区域保留；release 时清空（`Capture.cs:111-143`、`SessionManager.cs:954-958`）。

风险：

- `BitBlt` 对某些 DirectComposition/硬件加速内容可能得到黑帧；CCW 的 CefSharp 通常可截，但需要实测。
- 全屏颜色匹配/连通域是 CPU 同步计算，1280×720 约 92 万像素；大区域/多连通域会明显增加耗时。
- 模板匹配是 1:1、同 DPI、无旋转；CCW 的 DPI/缩放变化会直接失效。
- PNG 解码的大模板可造成数百 MB 临时分配（16M 像素 × RGBA），与“空闲 ≤40MB”的目标冲突。

### 7.2 UIA

优点：

- `IUIAutomation2.ConnectionTimeout=500ms`、`TransactionTimeout=1500ms`，避免单个 provider 拖死整个循环（`UiaService.cs:277-291`）。
- 缓存请求只缓存元素自身，避免每个命中元素缓存整棵子树（`UiaService.cs:296-330`）。
- 树构建有深度/节点/时间/访问预算，裁剪滚动条/进度条/分隔条（`UiaService.cs:1180-1401`）。
- `element_ref` 先按 runtime_id 定位，失败按指纹唯一重定位，仍失败返回 `E_ELEMENT_STALE`，不猜（`SessionManager.Elements.cs:205-310`）。
- `TryUiaInvoke` 3s 超时后熔断该 pid，后续 `auto` 直接走消息（`SessionManager.Input.cs:605-661`）。

问题：

1. **线程安全不完整**：类注释说“非线程安全，调用方需串行化”（`UiaService.cs:191`），但 `TryInvokeAtPoint`（751-798）、`BuildTree`（1180-1268）没有进入 `_sync`；`GetText/GetValue/TrySetValue`（923-1047）也没有。`get_environment` 是旁路闸门的优先工具，可能并发调用 `GetFocusedElement`，与 `get_ui_tree`/`set_element_value` 竞争同一个 `IUIAutomation`。
2. **非法 control_type 静默忽略**：`BuildCondition` 解析失败就不加条件（`UiaService.cs:1459-1465`），`find_element(control_type="Buton")` 会返回未过滤元素。
3. **`FindAll` 最多扫描 5000 个元素**（`UiaService.cs:453`），超过部分静默丢弃，没有 `truncated` 标记。
4. **单次 `FindAllBuildCache` 本身可能很慢**，500ms/1500ms 超时只覆盖 provider 连接/事务，不覆盖本地枚举/缓存读取。
5. **`ResetUia` 故意不 Dispose 旧实例**（`SessionManager.cs:106-113`），长时间运行反复超时可能累积 COM 对象/线程。
6. **UIA2 回退缺失**：没有 FlaUI 那种 UIA3 失败切 UIA2 的策略；WinForms/旧控件在 UIA3 下可能异常。

### 7.3 输入

- 键盘使用 `SendInput` + `KEYEVENTF_UNICODE`，支持非 ASCII；`type_text` 默认 32 字符分块，按 TextPattern/ValuePattern 回读（`InputInjector.cs:120-165`、`SessionManager.Input.cs:176-274`）。
- 鼠标默认 UIA/窗口消息，不移动光标；只有 `mode=input` 才 `SendInput`（`SessionManager.Input.cs:17-174`）。
- 系统键黑名单覆盖 `Win+*`、`Alt+Tab`、`Ctrl+Esc`、`Ctrl+Shift+Esc` 等（`KeyMap.cs:111-190`）。
- 多击、拖拽、滚轮都有实现；`MessageInput.IsInputHostile` 对 Chromium/Electron/WinUI 直接拒绝，避免“成功但没效果”。

问题：

1. **P0：绝对坐标缺少 `MOUSEEVENTF_VIRTUALDESK`**（详见 8.1）。
2. **键盘代理对/IME**：`TypeText` 按 UTF-16 码元逐个发 `KEYEVENTF_UNICODE`，`SplitTextChunks` 只避免跨块拆分代理对，没有把 high/low surrogate 作为同一组事件发送；emoji/部分 IME 场景可能失败。需要实测。
3. **没有 key down/up 租约**：`press_keys` 每次都是完整组合，不能“按住 Shift 点击多个点”；复杂选择操作需要多次调用。
4. **没有鼠标相对移动/原始输入**：部分游戏/3D 应用只接受 Raw Input，`SendInput` 无效。
5. **`MessageInput.Scroll` 使用屏幕坐标**：`WM_MOUSEWHEEL` 的 lParam 确实是屏幕坐标，这一点是正确的；但 `Click/Drag/Move` 使用 client 坐标，代码分别处理了，需在测试中确认不同 DPI/子窗口下无偏移。
6. **`type_text` 的 `verify=true` 依赖 TextPattern/ValuePattern**：CCW 的 CefSharp 编辑器通常没有，回读只能靠截图，`verified=false` 是预期结果。

## 8. 关键缺陷清单

### 8.1 P0：`mode=input` 绝对鼠标坐标映射到主屏

**证据**

`src/VScreenPilot.Server/Input/InputInjector.cs:250-265`：

```csharp
private static NativeMethods.INPUT AbsoluteMoveInput(int x, int y)
{
    int vx = NativeMethods.GetSystemMetrics(NativeMethods.SmXVirtualScreen);
    int vy = NativeMethods.GetSystemMetrics(NativeMethods.SmYVirtualScreen);
    int vw = Math.Max(1, NativeMethods.GetSystemMetrics(NativeMethods.SmCxVirtualScreen));
    int vh = Math.Max(1, NativeMethods.GetSystemMetrics(NativeMethods.SmCyVirtualScreen));

    int nx = (int)Math.Round((x - vx) * 65535.0 / Math.Max(1, vw - 1));
    int ny = (int)Math.Round((y - vy) * 65535.0 / Math.Max(1, vh - 1));

    return MouseInput(
        Math.Clamp(nx, 0, 65535),
        Math.Clamp(ny, 0, 65535),
        0,
        NativeMethods.MouseMove | NativeMethods.MouseAbsolute);
}
```

`NativeMethods` 只定义了 `MouseMove=0x0001` 和 `MouseAbsolute=0x8000`（`NativeMethods.cs:206-217`），没有 `MOUSEEVENTF_VIRTUALDESK=0x4000`。

Microsoft `MOUSEINPUT` 文档明确：绝对坐标 `0..65535` 在**多显示器系统默认映射到主显示器**；只有指定 `MOUSEEVENTF_VIRTUALDESK` 才映射到整个虚拟桌面。

**影响**

- 虚拟屏在主轴右侧时（默认 `ExpectedPosition = primary.X + primary.Width`，`SessionManager.cs:580-586`），`click/gesture mode=input` 的点击会落到主屏的错误位置。
- CefSharp/Electron/WinUI 会被 `MessageInput.IsInputHostile` 拒绝（`MessageInput.cs:181-207`），只能走 `mode=input`；因此这些区域**没有可用的鼠标点击路径**。
- 既有测试可能没有暴露：`focusWindow` 的 `mode=input` 点击即使失败，后续 `type_text` 仍会通过 `EnsureForeground` 把窗口切前台，测试继续通过（`tools/TestTool/flows/tasks.mjs:26-43`）。
- `gesture drag/scroll/move` 同样受影响。

**修复建议**

- 增加 `MouseVirtualDesk = 0x4000`，在 `AbsoluteMoveInput` 中 `MouseMove | MouseAbsolute | MouseVirtualDesk`。
- 保留按虚拟桌面尺寸归一化；加回归测试：虚拟屏在主轴右侧，UiTarget 记录 `WM_LBUTTONDOWN` 坐标，`click mode=input` 必须命中。
- 在不修复的情况下，文档必须明确“`mode=input` 只支持主屏或 (0,0) 起始的虚拟屏”，否则会误导使用者。

**优先级**：P0。它直接破坏“虚拟屏隔离 + 不干扰主屏”的核心卖点。

### 8.2 P0：CCW/CefSharp/ag-grid 缺少可靠语义/点击通道

**证据**

- `MessageInput.IsInputHostile` 对 `Chrome_WidgetWin`、`Chrome_RenderWidgetHost`、`CefSharp`、`Electron` 等直接返回 true，`Click/Drag/Scroll/Move` 返回 `E_INPUT_UNSUPPORTED`（`MessageInput.cs:181-207`、`28-69`）。
- 技术文档 15.4 明确：CCW 的变量表、程序编辑器、WebView 区域在 UIA 中只有 `Custom` 容器，无法语义读写；只能靠 `Alt+S` 等访问键。
- README “当前限制”也写明无法语义化所有自绘/WebView 控件（如 CCW 的 ag-grid 变量表）。
- 工程没有 CDP/DevTools 桥、没有 IAccessible2 回退、没有 OCR/视觉模型；只有截图 + 模板/颜色匹配 + 坐标/键盘。

**影响**

- 目标项目“创建 ST 程序并编译”至少需要：新建项目、选择设备、添加 ST 程序、点击代码编辑器、输入代码、点击 Build。项目树/对话框可能 UIA 可做；代码编辑器和变量表大概率只能坐标/键盘。
- 叠加 8.1 的 P0，`mode=input` 在虚拟屏上又不可用；CCW 的核心交互可能完全无法通过当前 MCP 完成。
- 这是“目标场景兼容性”问题，不是“代码小 bug”；改进需要新增通道，而不是改一行。

**修复建议**

- 短期：修复 8.1；为 CEF 增加“强制 `mode=input`”的明确路径；提供 `click` 的“主屏/虚拟屏坐标转换”诊断。
- 中期：集成 CDP（CefSharp 可开 remote debugging port）或 IAccessible2；为 WebView 提供 DOM/可访问性快照。
- 长期：增加 OCR/视觉定位兜底（如 Windows-MCP 的 Screenshot + 视觉模型路线），并明确“像素操作不可承诺语义正确”。
- 测试计划必须把 CCW 每一步标记为“UIA / 消息 / 键盘 / 像素 / 不可用”，不要笼统写“成功”。

### 8.3 P1：UIA 线程安全不完整

**证据**

- `UiaService` 类注释：“非线程安全，调用方需串行化”（`UiaService.cs:191`）。
- `FindElement/FindElements/FindByRuntimeId/FindByFingerprint/GetFocusedElement/TryInvoke/FocusElement` 使用 `lock (_sync)`。
- `TryInvokeAtPoint`（751-798）、`BuildTree`（1180-1268）、`GetText`（1016-1047）、`GetValue`（991-1010）、`TrySetValue`（923-975）没有统一进入 `_sync`。
- `get_environment` 是 `PriorityTools`，完全旁路工具闸门（`McpServer.cs:410-412`、`603-606`），会调用 `Uia.GetFocusedElement()`（`SessionManager.cs:806-821`）。
- `get_ui_tree`/`set_element_value` 在工具闸门内运行，但可以和旁路的 `get_environment` 并发。

**影响**

- 可能出现 `RPC_E_WRONG_THREAD`、COM 调用挂起、`E_INTERNAL`、偶发崩溃。
- 难以稳定复现，容易在长会话/高并发下暴露；对“进程绝不崩溃”的契约是风险。

**修复建议**

- 所有 UIA COM 访问统一走一个专用 STA/MTA 工作线程或统一 `_sync`；不要在 `Task.Run` 里直接调用。
- 明确 `IUIAutomation` 的 apartment 模型；参考 FlaUI 的 UIA3 单线程调度。
- 对 `get_environment` 的 UIA 读取做“非阻塞快照”或超时降级，避免旁路工具与主工具竞争。

### 8.4 P1：element_ref 容量与 `get_ui_tree` 节点上限不一致

**证据**

- `ElementRefCapacity = 1024`（`SessionManager.Elements.cs:45`）。
- `RegisterElement` 在超过容量时 `EvictOldestElement()`（`SessionManager.Elements.cs:67-70`）。
- `get_ui_tree` 的 `max_nodes` 允许到 2000（`McpServer.cs:733-735`）。
- `ConvertTreeNode` 为每个节点注册 ref（`SessionManager.Elements.cs:425-492`）。

**影响**

- 当树节点超过 1024 时，返回 JSON 中较早的 `ref` 可能已经被淘汰；模型随后 `invoke_element` 会得到 `E_ELEMENT_STALE`。
- 这是“返回成功但引用已失效”的隐蔽错误，难以诊断。

**修复建议**

- 将 `max_nodes` 上限降到 `ElementRefCapacity` 以下，或在构建树时保留本轮所有 ref，不淘汰本轮新增项。
- 返回 `refs_truncated`/`capacity` 字段，明确告知模型。
- 增加 1500 节点 UiTarget 回归用例。

### 8.5 P1：显式 `baseline_frame_id` 不校验区域 x/y

**证据**

`SessionManager.Verify.cs:667-680`：

```csharp
if (source.ValueKind == JsonValueKind.Object &&
    source.TryGetProperty("baseline_frame_id", out JsonElement frameIdElement) &&
    frameIdElement.ValueKind == JsonValueKind.String)
{
    FrameSnapshot? frame = FindFrame(frameIdElement.GetString() ?? string.Empty);
    return frame is not null &&
           frame.Width == width &&
           frame.Height == height

```

只比较 `Width/Height`，没有比较 `frame.X == x && frame.Y == y`。

**影响**

- 两个同尺寸但不同区域的截图可以互相作为基线，`assert_region changed`/`pixel_diff` 会给出错误结论。
- 默认 `last_same_region` 路径会校验 x/y，所以只有显式传 `baseline_frame_id` 时触发；但这是文档推荐的用法之一。

**修复建议**

- 显式 frame id 也必须校验 x/y；如需跨区域比较，增加显式 `allow_cross_region=true`。
- 错误信息中返回 `frame.x/y` 和请求的 `x/y`，便于诊断。

### 8.6 P1：非法 `control_type` 被静默忽略

**证据**

`UiaService.cs:1459-1465`：

```csharp
if (!string.IsNullOrWhiteSpace(controlType))
{
    if (TryParseControlType(controlType, out int controlTypeId))
    {
        condition = And(condition, _automation.CreatePropertyCondition(ControlTypePropertyId, controlTypeId));
```

解析失败时什么都不加，继续查询。

**影响**

- `find_element(control_type="Buton")` 会返回所有元素中的第一个，而不是报错；Agent 可能点错控件。
- 与 `name_match`、`prefer`、`role` 的严格校验不一致。

**修复建议**

- 解析失败抛 `E_INVALID_ARG`，列出支持的 control type。
- 在 `find_element`/`get_ui_tree` 的 schema 中加 enum 或至少文档写明大小写/拼写要求。

### 8.7 P1：EOF/Dispose 可能被 `_gate` 或卡死 UIA 阻塞

**证据**

- `McpServer.Run` 在 stdin EOF 后取消活动调用，最多等 3s，然后 `_session.Dispose()`（`McpServer.cs:149-177`）。
- `SessionManager.Dispose` 调用 `ReleaseEnvironment(keepDisplay:false)`（`SessionManager.cs:1631-1652`）。
- `ReleaseEnvironment` 在 `lock (_gate)` 内清理应用、帧、UIA 状态，并可能调用 UIA 关闭对话框（`SessionManager.cs:825-1002`）。
- 如果某个工具 handler 卡在 UIA COM 调用里并持有 `_gate`，`Dispose` 会一直等锁；3s 的 drain 不会终止 handler。

**影响**

- 宿主退出可能超过契约的 5s，甚至永久挂起；用户只能强杀。
- 与“进程绝不崩溃、资源随进程销毁自动释放”的核心契约冲突。

**修复建议**

- `Dispose` 使用带超时的 `Monitor.TryEnter`，拿不到锁时跳过应用清理，直接摘屏/关 Job；
- 为 UIA 调用建立可取消的工作线程；EOF 后超时直接 `Environment.Exit` 前完成最小清理；
- 增加“UIA 卡死 + EOF”的故障注入用例，测实际退出时间。

### 8.8 P1：`release_environment` 旁路与旧 handler 竞态

**证据**

- `McpServer.ExecuteToolAsync`：优先工具 2s 拿不到闸门就旁路执行（`McpServer.cs:422-440`）。
- `release_environment` 完成后 `ResetToolGate`，旧 handler 仍可能持有旧闸门并在运行（`McpServer.cs:515-548`）。
- `ReleaseEnvironment` 清空 `_apps`、`_elements`、`_frames`（`SessionManager.cs:950-960`）。

**影响**

- 旧 handler 可能访问已清空的 `_elements`/`_apps`，或使用已释放的 UIA 句柄，返回 `E_INTERNAL` 或误清理。
- 旧 handler 可能仍在向应用注入输入，而 release 已经开始关闭应用。

**修复建议**

- release 旁路前设置“会话代际”/epoch，旧 handler 在关键步骤检查 epoch，过期就中止；
- 清理时不要立即释放旧 handler 仍可能引用的对象，延迟到 handler 结束；
- 增加“卡死工具 + release”并发用例。

### 8.9 P2：`outputSchema` 泛化、无速率限制

**证据**

- `McpServer.cs:60-62`：所有工具 `outputSchema = {"type":"object"}`。
- 没有 `rate limit`、没有 `auth`、只有 stdio。
- MCP 规范 2025-06-18 的 Security Considerations 明确要求服务器验证输入、实施访问控制、速率限制、清理输出。

**影响**

- 客户端无法做有意义的输出校验；模型只能看 text。
- 本地可信场景风险可控，但不符合“成熟 MCP”的工程标准。

**修复建议**

- 为每个工具定义具体 `outputSchema`（至少公共字段：`ok/code/message` + 工具特有字段）。
- 增加可配置的调用频率限制/并发上限；HTTP 传输时增加认证/TLS。
- 增加 `title`、`idempotentHint`。

### 8.10 P2：多显示器假设过强

**证据**

- `ExpectedPosition` 固定 `primary.X + primary.Width`（`SessionManager.cs:580-586`）。
- `SetModeAndPosition` 直接设置位置（`DisplayTopology.cs:160-193`）。
- 没有检查右侧是否已有物理显示器，也没有冲突处理。

**影响**

- 右侧已有显示器时，虚拟屏会覆盖/挤占物理屏，导致拓扑重排、黑屏或设置失败。
- 主屏位置变化时，几何校验会反复重建。

**修复建议**

- 选择空闲区域（右侧、左侧、下方）并检测冲突；
- 允许显式 `VSP_DISPLAY_POSITION=right|left|below|absolute`；
- 在 `get_environment` 返回冲突诊断。

### 8.11 P2：输入文本/IME/代理对覆盖不足

**证据**

- `InputInjector.TypeText` 对每个 `char` 发 down/up（`InputInjector.cs:120-165`）。
- `SplitTextChunks` 只避免跨块拆分代理对（`SessionManager.Input.cs:869-888`）。
- 没有 IME 组合、没有 key down/up 租约、没有相对鼠标。

**影响**

- emoji/部分中文输入法/非美式键盘布局可能失败或乱码。
- 复杂选择、Shift 连点、拖选等需要多次调用，效率低。

**修复建议**

- 对代理对发送同一组事件（high+low，中间不插 keyup），或使用 `WM_CHAR`/UIA TextPattern 写值；
- 增加 `key_down`/`key_up` 或 `hold_keys` 参数；
- 增加 emoji/中文/日文/韩文回归用例。

### 8.12 P2：测试与工程化外围

**证据**

- 仓库有 6 个提交，tag `v0.1.0`；`git remote -v` 为空；没有 `.github/workflows`。
- `tools/TestTool` 有 8 个任务、9 个故障用例；`测试方案.md` 写的是 12 项故障注入，实际未完全对齐。
- README 明确“纯单元测试尚未覆盖 PNG/KeyMap/region/ref 注册/协议分帧，当前以集成脚本验收为主”。
- `csproj` 目标 `net10.0-windows`，没有 `global.json`。
- npm 包未发布到 registry；没有代码签名。

**影响**

- 干净机器构建依赖手工安装 SDK；SDK 版本漂移可能直接编译失败。
- 没有 CI 回归，改动容易破坏协议/生命周期。
- 没有发布产物/代码签名/registry release，用户接入成本高，安全信任度低。

**修复建议**

- 加 `global.json` 固定 SDK；加 GitHub Actions（build + smoke + protocol tests + 可选 GUI runner）。

- 发布 npm/PyPI/MCP Registry；加代码签名/SBOM/CHANGELOG/SECURITY.md。

## 9. 性能审查

### 9.1 设计上的优点

- 截图路径是内存级 GDI + 纯托管 PNG，没有“落盘再读回”。
- 模板匹配用灰度金字塔 + 早期退出 SAD + NMS，避免全分辨率暴力搜索（`TemplateMatcher.cs:16-73`、`75-127`、`180-214`）。
- 颜色匹配用 `ArrayPool` 复用 mask/visited/queue，减少 GC（`SessionManager.Visual.cs:480-577`）。
- 日志异步写文件，工具调用不被磁盘 IO 拖慢（`LogRing.cs:58-66`）。
- release 后裁剪工作集，降低空闲内存（`SessionManager.cs:479-543`）。

### 9.2 风险

- README/技术文档的 50 轮压测数据（启动 116ms、挂屏 1952ms、截图 30ms、release 2098ms、EOF 229ms）不是 CI 可复现基准；机器、驱动、桌面状态都会影响。
- 全屏颜色匹配/模板匹配是 CPU 同步，1280×720 约 92 万像素；大模板/大区域可能几百毫秒到数秒。
- 帧注册表保存原始 BGRA（1280×720 ≈ 3.7MB/张），16 张约 59MB，接近 64MB 上限；频繁截图会增加内存压力。
- `ScreenCapture` 每次分配新数组；`PngWriter` 再分配 raw/compressed/png；峰值内存高于稳态。
- `TrimIdleMemory` 清空工作集后，下一次调用可能因缺页变慢；这是用延迟换内存。
- `Thread.Sleep(50)`/`Thread.Sleep(120)` 在点击/按键路径上固定增加延迟（`SessionManager.Input.cs:142`、`333-339`）。
- 没有性能基准工程/CI 门槛；README 的数字只能当历史参考。

### 9.3 建议的度量

- 截图：P50/P95/P99、PNG 字节数、峰值 RSS。
- UIA：`find_element`/`get_ui_tree` 的 P50/P95/P99、节点数、truncated 比例。
- 输入：`type_text` 每 1k 字符耗时、`press_keys` 每组合耗时。
- 生命周期：启动握手、挂屏、release、EOF 退出、50 会话成功率。
- 并发：8/16 线程下的 E_BUSY、超时、串行化比例。

### 10.3 可维护性

- 代码风格统一，命名清晰，中文注释充分。
- 大部分 Win32 常量/结构体集中，便于审查。
- 但手写 COM/P/Invoke 较多，缺少自动化静态分析（P/Invoke 签名、结构体布局、CA 规则）。

- 没有依赖锁定（NuGet `packages.lock.json`），`Interop.UIAutomationClient` 版本固定但传递依赖未锁。

### 11.1 关键差距

1. **社区与发布成熟度**：Windows-MCP 有 PyPI、uvx、MCP Registry、Scheduled Task、CI、频繁 release；VScreenPilot 只有本地 npm 打包脚本，未发布、无签名、无 CI。
2. **协议成熟度**：Playwright/Chrome DevTools 使用官方 SDK/成熟协议栈；VScreenPilot 手写 JSON-RPC，`outputSchema` 泛化，缺少 HTTP/鉴权/限流。
3. **语义通道**：Playwright 的可访问性树、Chrome DevTools 的 CDP 是结构化语义；VScreenPilot 对 CEF/WebView 只有 `Custom` 容器。Windows-MCP 也提供 DOM 模式和统一 Snapshot。
4. **UIA 实现**：FlaUI 提供 UIA2/UIA3 双实现、专用调度、成熟测试；VScreenPilot 手写 COM，线程安全需要补。
5. **测试工程**：Windows-MCP/Playwright/Chrome DevTools 都有 CI 测试；VScreenPilot 只有 E2E 脚本，且依赖真实桌面。
6. **安全治理**：Windows-MCP 有桌面控制权门闩、工具白名单、HTTP 认证/TLS、Scrape SSRF 防护；VScreenPilot 的安全边界更“窄”（只在虚拟屏），但缺少速率限制/鉴权/审计。

### 11.2 VScreenPilot 的相对优势

1. **真正的隔离**：高 star 桌面 MCP 基本都在用户桌面操作；VScreenPilot 的虚拟屏 + 焦点/光标护栏是独有设计。
2. **生命周期完整**：互斥体、Job Object、孤儿屏接管、心跳、state.json、崩溃恢复，覆盖度高于多数同类项目。
3. **安全默认值**：`run_script` 默认关闭、越界拒绝、tracked 窗口校验、破坏性写入保护，比“直接给 PowerShell/鼠标键盘”的 MCP 更克制。
4. **Token 友好**：UIA 树默认裁剪、截图支持缩放、`element_ref` 精简输出；比全量 DOM/截图更省上下文。
5. **中文文档**：对中文用户/教学场景友好；但国际化不足。

### 15.3 新引入风险（需要在下一轮盯住）

1. `snapshot` 会清空旧 ref；并发 `find_element` 可能拿到已被清空的 ref → `E_ELEMENT_STALE`。这是快照作用域的预期行为，但文档必须写清。
2. `release_environment` 与只读截图仍可并发；epoch 会丢弃结果，但摘屏瞬间的截图可能报 `E_INTERNAL`。
3. `ToolResponse.Text` 同时做 `DeepClone` 和 `ToJsonString`，大结果有双份内存；下一步改为单次序列化。
4. 超时 handler 仍会继续运行并持有写锁；`E_TIMEOUT` 之后的重试可能得到 `E_BUSY`。
5. 全屏截图默认返回预览而不是完整图；模型需要理解 `resource_uri`/`path`，否则会误以为“看不清”。
