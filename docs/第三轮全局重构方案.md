## 0. 摘要

第二轮把“单文件行数、单方法行数、命名空间 SPLIT、无类型 catch”压到了目标值，外特性审计（protocol / GUI / stability / UIA）也全部通过。但审查发现，这些指标主要靠 **partial 文件搬运**和 **方法体提取**达成，真正的架构问题没有被解决：

- 最大的设计单元仍是 1,300–1,900 行的巨型类型：`UiaService`、`SessionManager`、`InputRouter`、`McpTransport`、`AppLauncher`；
- 18 个 `I*Host` 不是接口隔离，而是同一个会话上下文复制了 18 份（`EnsureDisplay` 出现在 10 个接口里）；
- 工具层仍然直接依赖 `SessionManager`，`Tools → Session`、`Session → Mcp/Diagnostics` 等反向依赖没有约束；
- 组件仍缺少 fake-host 单测，“组件可独立测试”没有兑现；
- 主 CI 的 `arch_metrics --selftest` 当前是 **0/15**，最终报告却仍写着 15/15；
- `ToolExecutor` 的拆分引入了一个屏幕租约泄漏回归；
- `architecture.md` 多处与代码不一致，格式化也没有闸门。

第三轮的目标不是再压一轮行数，而是把工程推进到 **可验证的组件架构**：类型有明确职责、边界有硬规则、每个组件可独立测试、CI 能在合并前拦住架构退化。

本轮成功定义：

1. 所有“架构级缺陷”由 `tools/audit/arch_rules.json` 定义，并由 `arch_metrics.py --enforce` 与 `ArchitectureFitnessTests` 双重执行；
2. 退出时 **架构规则零 allowlist、零例外、零“已接受偏差”**（IVT 白名单属于安全边界，保留）；
3. 外特性基线 diff 为 0，全部协议/GUI/稳定性/UIA/并发/热插拔审计通过；
4. 文档数字由脚本生成并校验，不再手写；
5. 不新增 public 类型（`Automation` 保持 0 个 public 类型）。

预计 **75–95 个工作日**（约 15–19 周），分 9 个阶段，拆成两个可独立验收的波次。

## 2. 当前架构问题分析

### 2.1 文件变小了，类型没有变小

`arch_metrics.py` 只按“文件”统计，partial 文件把同一个类型拆到多个文件后，单文件指标自然达标，但类型的总职责没有变化。按类型跨度统计（含 partial，不含 using/namespace，T3-1 用 fixture 锁定）：

| 类型 | 类型行数 | 文件数 |
|---|---:|---:|
| `UiaService` | 1,869 | 8 |
| `SessionManager` | 1,591 | 18 |
| `InputRouter` | 1,519 | 6 |
| `McpTransport` | 1,456 | 8 |
| `AppLauncher` | 1,308 | 8 |
| `ElementOperations` | 960 | 3 |
| `VirtualDisplayController` | 753 | 4 |
| `SnapshotBuilder` | 647 | 3 |
| `VisualMatchService` | 637 | 3 |
| `MsaaService` | 543 | 1 |
| `TemplateMatcher` | 512 | 1 |
| `ControlServer` | 501 | 1 |
| `LogRing` | 451 | 1 |
| `VddDevice` | 428 | 1 |
| `ToolExecutor` | 418 | 1 |

共 **15 个类型 >400**。以下类型按 400 规则不强制拆分：`AppReleaser`（400）、`UiaHost`（398）、`WindowManager`（390）、`EnvironmentReporter`（375）；如方法收敛需要，可顺带拆分，但不作为门槛。

### 2.2 18 个 `I*Host` 不是接口隔离

`SessionManager` 通过 18 个宿主接口向组件暴露能力，但这些接口大量重复：

- `EnsureDisplay`：10 个接口；`Log`：9 个；`Uia`：8 个；`Apps`/`Gate`：各 5 个；`EnsureForeground`：3 个。
- 187 个成员声明中只有 108 个唯一名字。
- `EnsureForeground` 同时出现在 `IAppLaunchHost`、`IElementOperationsHost`、`IInputHost`，实现却在 `SessionManager.Input.cs`；`IElementOperationsHost.EnsureForeground` 又在 `SessionManager.Lifecycle.cs` 实现。
- 组件要写一个 fake，需要实现 20 多个成员，因此 `InputRouter`、`ElementOperations` 无法补单测。

结论：这不是接口隔离，而是把同一个 `SessionContext` 复制了 18 份。第三轮要用 **共享原语 + 窄端口** 替代。

### 2.3 工具层与会话层耦合

- `ToolContext` 直接持有 `SessionManager`；
- `ToolExecutor` 依赖 `SessionManager.Lease`、`Scheduler`、`Epoch`、`SetCancellation`、`Clients`；
- 22 个 handler 直接调用 `_session.*`；
- `McpTransport` 同时承担传输、目录、handler、资源、遥测、限流，文件还叫 `ToolHandlers.cs`/`ToolCatalog.cs`。

结论：工具层没有“应用服务”边界，handler 无法脱离真实会话来测试；`McpTransport` 仍是协议 + 业务的混合体。

### 2.4 Server 内部依赖没有规则

当前实际存在但不应存在的边：

| 方向 | 例子 | 问题 |
|---|---|---|
| `Session → Mcp` | `ToolProgress`、`WriteScheduler`/`ScreenLease` | 会话层依赖协议层 |
| `Session → Diagnostics` | `PrivacyRedactor` | 会话层依赖诊断层 |
| `Tools → Session` | `ToolContext`、`ToolExecutor`、3 个 handler 文件 | 工具层依赖具体门面 |
| `Mcp → Session` | `McpTransport` 4 个 partial | 协议层直接拿具体门面 |
| `Ipc → Session` | `ControlServer`、`PipeHost` | IPC 直接拿具体实现 |
| `Cli → Session` | `LocalSessionInvoker` | CLI 直接拿具体实现 |
| `Infrastructure → Session` | `StateStore` 使用 `ISessionStateStore` | 最底层反向依赖会话 |
| `Infrastructure → Ipc` | `InstanceRegistry` 使用 `PipeNames` | 最底层反向依赖 IPC |
| `Infrastructure → Mcp` | `InputLease` 的未使用 using | 最底层反向依赖协议 |
| `Ipc → Composition` | `DaemonHost` 调用 `ServerHost.RunDaemon` | 与组合根成环 |
| `Diagnostics → Ipc` | `DoctorReportBuilder` 使用 `ControlClient` | 允许图未声明 |
| `Apps → Session` | `TrackedAppRegistry` 的未使用 using | 叶子模块反向依赖 |

第二轮只校验了“程序集之间”的方向和命名空间归属，没有校验 **Server 内部模块之间** 的方向。

### 2.5 方法、参数、复杂度仍有大量存量

按当前解析口径（T3-1 会用 fixture 校准）：

- 743 个方法中，约 **48 个 >80 行**；
- 约 **32 个 >12 个判断点**（`if/for/foreach/while/case/catch/when/&&/||/??/?:`）；
- 约 **39 个方法参数 >6**，最大 12 个；
- 典型：`SnapshotCore` 120 行、`ClickText` 119、`WriteTextVerified` 118、`CreateNewDisplay` 116、`HandleAsync` 115、`EnsureDocumentReady` 110 行/21 判断点、`ConnectedComponents` 23 判断点、`FinishUiaWrite` 12 参数。

只拆类型不拆方法，仍然达不到“方法 ≤80 / 判断点 ≤12 / 参数 ≤6”。本轮必须把方法收敛作为独立工作流，而不是隐含在类型拆分里。

### 2.6 测试金字塔仍然倒置

- 176 个测试方法 / 201 个用例，但主要是视图序列化、策略、路径、拓扑；
- `InputRouter`、`ElementOperations`、`SnapshotBuilder`、`EnvironmentReporter`、`WaitService`、`VisualMatchService`、`RegionVerifier` 均无直接单测；
- 编排正确性主要靠需要 VDD 的 Python 审计；
- `ToolExecutor` 的租约泄漏正是这个缺口的直接后果。

### 2.7 度量、CI、文档的可信度不足

- `arch_metrics --selftest` 0/15，主 CI 会红；
- 解析器不统计表达式体方法、本地函数、类型总行数、参数个数、public 类型增量；
- 没有格式化闸门；
- `architecture.md` 与执行报告存在过期数字和自相矛盾；
- `docs link check` 只查链接，不查数字。

### 2.8 外部审计还有两个缺口

- GUI-15 被收窄为“零应用”场景，没有覆盖“指定 pid 被杀、其他应用仍存活”；
- R3 最终基线目录只有 `server.json`，`errors.json` 没有重新抓取；`bench_concurrency.py`、`bench_hotplug.py` 没有在 R3 跑。

### 3.3 “架构级缺陷”的定义

本轮把架构缺陷收敛为可执行规则。以下任意一条不满足，即视为架构缺陷：

1. 程序集数量/方向/IVT 白名单变化，或新增 public 类型；
2. SPLIT 命名空间 >0；
3. Server 内部出现禁止依赖边或环；
4. 类型 >400 行、文件 >450 行、存在 partial 类型、文件名不是该文件行数最多的类型（helper >80 行也算违规）；
5. 方法/构造函数 >80 行、判断点 >12、参数 >6；
6. `I*Host` >0，或 `SessionRuntime`/`SessionResources` >8 成员，或会话端口 >12 或单个 >8，或平台测试缝 >5 或单个 >6；
7. `SessionManager` >350 行或 public 成员 >12；
8. `Mcp` 或 `Tools` 命名空间直接依赖 `Session`，或 `ToolContext` 含 `SessionManager`；
9. 有行为组件缺少直接单测（按 `arch_rules.json` 的组件→测试映射，每组件 ≥3 个测试方法），或测试方法数 <230；
10. `arch_metrics --selftest`/`--enforce`、`dotnet format --verify-no-changes`、docs metrics 任一失败；
11. 文档中的架构数字与实测不一致（数字只允许出现在 `doc_metrics` 生成的区块内）；
12. 每个新类型缺少 XML `<summary>` 职责说明，或类型所属命名空间与允许依赖图的层不一致。

**退出条件：上述 12 条全部为 0 违规，且 `arch_rules.json` 的 allowlist 为空。任何一条做不到，本轮不得标记完成，也不得以“已接受偏差”收尾。**

## 4. 目标架构

### 4.1 程序集

保持 4 个程序集，依赖方向不变：

```
Server (VScreenPilot) ──> Automation ──> Platform ──> Abstractions
        │                     │              │
        └─────────────────────┴──────────────┴──────> Abstractions
```

### 4.2 Server 内部模块与允许依赖

新增 `VScreenPilot.Services` 命名空间（仍在 Server 程序集内），只放 **应用服务接口 + 请求/响应契约**，不放实现。目标依赖图：

```
Program/Composition ──> 所有模块（仅组合根）
Mcp         ──> Tools, Services, Infrastructure, Views
Tools       ──> Services, Infrastructure, Errors, Json, Views
Ipc         ──> Mcp, Services, Infrastructure
Cli         ──> Ipc, Services, Diagnostics, Infrastructure
Diagnostics ──> Ipc, Services, Session, Infrastructure
Session     ──> Services, Apps, Ui, Verification, Infrastructure, Errors, Json, Views, Platform.*, Uia, Perception
Apps/Ui/Verification ──> Infrastructure, Views, Platform.*, Uia；Ui 另可依赖 Apps
Infrastructure ──> Errors, Json, Platform.*
Services     ──> Views, Errors, Json
```

> 命名空间说明：当前 `Tools/` 下的文件实际都声明为 `VScreenPilot.Mcp`。T3-3 必须先把 `VScreenPilot.Mcp` 拆成 `Mcp`（传输/限流/连接）与 `Tools`（catalog/pipeline/handlers/executor），否则“Tools → Session 0”是假绿。拆分前，现有 `Mcp → Session` 的 4 个文件就是 `Tools → Session` 的 4 个文件，不能重复计数。

**禁止边（测试锁定）**：

- `Session → Mcp | Tools | Diagnostics | Ipc | Cli | Composition`
- `Tools → Session | Mcp | Ipc | Cli | Composition`

### 4.3 会话组合：Runtime / Resources / Ports / Services

## 9. 风险与回滚

| 风险 | 应对 |
|---|---|
| SessionContext 变成新神类 | 两个上下文各 ≤8 成员；会话端口 ≤12（每个 ≤8）、平台测试缝 ≤5；架构测试锁定 |
| 服务层变成纯转发 | 10 个应用服务 + 执行控制 + 2 个边界接口；每个接口必须有 ≥2 个调用方（handler/CLI/IPC） |
| UIA 拆分破坏 COM 生命周期 | `UiaSession` 独占同步/缓存；不改线程模型；每步跑 UIA stress 3/3 |
| 输入拆分引入回归 | 先元素后输入；每步跑 GUI 05/07/08/09/10/11/12 |
| 类型 400 行上限导致机械拆分 | 先按职责提取协作对象；禁止 partial；评审共享状态归属 |
| 方法/参数收敛变成搬逻辑 | 参数对象只允许数据字段；提取保持原控制流；每步补测试 |
| 测试没有 VDD 覆盖不到 | 会话端口/平台测试缝 fake；COM/显示用 nightly；纯逻辑上提 |
| VDD 不可用导致阶段阻塞 | T3-0 前置检查；审计按最小集分阶段跑，阶段末跑全套 |
| 文档再次漂移 | `doc_metrics --check` 进主 CI |
| 迁移期指标反弹 | `arch_metrics --check` 每提交执行；每阶段下调基线 |
| 大规模移动产生合并冲突 | 一组件一提交；先 `git mv` 再改内容；不混合逻辑变更 |
| 新增 public 类型 | 架构测试扫描 public 类型数；`Automation` 保持 0 |

回滚：

- 开始前打 tag `t3-baseline`，创建分支 `refactor/t3`；
- 每阶段一个 tag（`t3-m1`…`t3-m8`）；
- 每组件一个提交，可单独 revert；
- 会话上下文/服务接口变更必须整体回滚，不能只回滚一半；
- 波次 A 可独立回滚，不影响波次 B。
